# コーディング規約 — 判断基準と適用例

核（`.claude/rules/coding.md`）の原則を実コードに当てるときの判断基準と例を持つ。
規則の本文は `.claude/rules/` が正で、ここには重ねない。

## 命名の判断基準

- **テスト**: 名前だけ見て、実装を読まずに呼べるか
  呼んだ結果を予想できるか
- 「何の」データか、「どう」処理するかまで名前に押し込む
  汎用語（`data`, `info`, `manager`, `process`, `handle`, `util`）は思考停止の兆候
- ブール値は `is/has/can/should` + 肯定形
  `isNotReady` のような否定形は二重否定 `!isNotReady` を生む
- 単位・型・範囲が誤解を生むなら名前に含める（`timeoutMs`, `maxRetries`）
- 対称性を守る: `open/close`, `begin/end`, `add/remove` の対を崩さずに使う
- ファイル名は、中の関数の集合を一語で言えるものにする
  一語で言えなくなったらファイルを割る

動詞の接頭辞は、同じ意味に同じ語を当てる。
表に無い意味が出たら、表へ足してから使う。

| 接頭辞 | 意味 | 返す形 |
|---|---|---|
| `get` | 鍵で 1 件を取得する | 値か、無ければ欠損値 |
| `list` | 条件に合う全件を取得する | 配列（無ければ空） |
| `find` | 条件に合う 1 件を探す | 値か、無ければ欠損値 |
| `create` / `add` | 新しく作る / 既存へ追記する | 作った値 |
| `set` / `update` | 既存の値を書き換える | 書き換え後の値 |
| `read` | env・設定・ファイルから読んで組み立てる（純関数） | 解決済みの値 |
| `load` | ファイルを読み、検査に通した値を返す | 検査済みの値 |
| `parse` | 外から来た値を検査して型を付ける | 検査済みの値か throw |
| `is` | 型の絞り込み | `value is T` |
| `assert` / `require` | 条件を確かめ、満たさなければ throw する | 無し |
| `format` | 表示用の文字列にする | 文字列 |
| `to` | 別の形へ写す（純関数） | 写した後の値 |
| `with` | 包み直して返す | 包んだ値 |
| `*Of` | 引数から導く（`labelOf`・`yearsOf`） | 導いた値 |
| `run` | 別のプロセスや検査を起動し、終わるまで待つ | 無し（失敗は throw） |

## 関数分割の判断基準

分割する合図（いずれか該当で検討）:
- 関数名に and / or / then が要る
- コメントで内部をセクション分けしている（各セクションが関数候補）
- 抽象度の混在: ビジネスルールの隣に文字列整形やループの添字操作がある
- フラグ引数で内部分岐している（呼び出し側は常にどちらか一方しか使わない）
- テストのセットアップが肥大する（責務が多い証拠）

分割しない合図:
- 一度しか呼ばれず、抽出しても名前が `doStep2` にしかならない
- 抽出すると引数が 5 個になる（データの塊を見落としている可能性。先に構造化）

## 状態設計の判断基準

- **不正状態の表現不能化**: 「A のとき B は null」のような暗黙の相関があるなら、型で分ける（直和型 / サブクラス / 状態ごとの型）
- setter を書く前に問う: 生成後にそれが変わるのは本当にドメインの性質か、それとも生成手順の都合か
  後者ならコンストラクタ/ファクトリに寄せる
- プリミティブ執着: 金額・ID・範囲などドメインの概念が生の int / string で取り回されていたら値オブジェクト化を検討（バリデーションの置き場が定まる）
- 生成時に決まる値（先頭からの位置・合計）は、毎回計算し直さず値オブジェクトが持つ

## 凝集・結合の判断基準

- あるデータを変更するとき、離れた複数ファイルを同時に直す必要がある → ロジックがデータから逸走している（低凝集）
  データ側に引き寄せる
- クラスの一部のフィールドしか使わないメソッド群がある → クラス分割の候補
- 引数に渡したオブジェクトの getter を掘って判断している（尋ねるな、命じよ） → 判断ロジックをオブジェクト側へ移す

### 置き場の規律（型の置き場 / 振る舞いの置き場）

Data Class 臭がロジックの逸走なら、こちらはその裏返しで、**値が型のモジュールへ入り込む**形。

- **型だけを置くモジュール（`types.ts`・`models.py` 等）には型だけを置く。**
  定数・既定値・変換テーブルは、それを使うモジュールへ置く
  型だけのモジュールを import しただけで実行時の依存が付いてくると、型のためだけの参照ができなくなる
- **振る舞いを持つものは、それを扱うモジュールへ置く。**
  寄せる基準は関連でなく、一緒に変わるかどうか
- モジュールを跨いで受け渡す型だけを型のモジュールへ出し、モジュール内に閉じる型はそのモジュールに留める
- クライアント側のコンポーネントが読む定数は、サーバーの道具（`node:*`・DB クライアント）を import しないモジュールへ置く

### 境界の判断基準（スキーマを付けるか）

スキーマ（実行時の検証）を付けるかは、その値が境界を越えるかで決める。

| 値の出所 | スキーマ |
|---|---|
| ネットワーク越し（API の応答・フィード） | 要る |
| ディスク上で人が編集しうるファイル | 要る |
| 内部で組み合わせただけの中間の値 | 要らない（検証済みの値をもう一度検証することになる） |

境界の道具の癖（XML の `#text`・属性の在り処）を均す層と、値の規則（必須・変換）を持つ層は分ける。
道具が変われば前者を、規則が変われば後者を直す。

### Data Class の検出と対処

**構文ではなく構造で判定する。**
`@dataclass`・record・struct を使うこと自体は悪臭ではない（frozen な値オブジェクトの手段としてむしろ推奨）。
悪臭は「データと、それを守る/扱うロジックが別の場所に引き裂かれている」構造の側にある。

兆候（いずれか該当で疑う）:
- フィールドと getter/setter だけのクラスに対し、外部の Manager / Service / Util がそのデータを取り出して計算・検証している
- 同じバリデーション（金額は非負、名前は N 文字以内…）が複数の呼び出し側に重複している
- そのクラスのインスタンスが「生成 → 各所で setter で徐々に組み立て」されている（未初期化の中間状態が野放しになる）

対処:
- 計算・検証ロジックをデータを持つクラス自身のメソッドへ移す
- 完全コンストラクタ + 不変化とセットで行う（生成時に検証、以後は変わらない）
- ドメイン概念なら値オブジェクトへ昇格（金額 + 通貨、氏名、期間など）

許容される例外（悪臭ではないもの）:
- システム境界の DTO（API リクエスト/レスポンス、永続化層のレコード）
  意図的な「運搬役」であり、ドメインロジックを持たせないのがむしろ正しい
  ただし境界を越えたらドメインオブジェクトへ詰め替える
  DTO はアプリケーション内部へ入る前に詰め替える

## エラー処理の判断基準

- catch して log だけ出して続行 = 握りつぶし
  回復できないなら再送出か停止
- null 返却の代替の選択: コレクションなら空を返す / 「無い」が正常系なら Optional 相当 / 異常系なら例外
- 例外は「例外的」な場合に使う
  通常フローの分岐は戻り値で表す
- エラー文は「対象の識別子と値」を含む一文にする
  設定の欠落なら、直し方（変数名と、書き方が載る文書の節）を続ける
- 無いことと、アクセス権が無いことは同じ応答にする
  応答を分けると、識別子を差し替えるだけで存在が読める

## コメントの判断基準

書くべき: 呼び手が踏む誤用を止める前提、外部制約（API の癖、規格）、警告（この順序を変えると壊れる）、安全のための検査が何を防ぐか（パストラバーサル・全インターフェースへの待ち受け）、TODO（期限か条件付きで）。
書くべきでない: コードの逐語訳、変更履歴（git の仕事）、コメントアウトされた死体コード（消す。git にある）、採らなかった代替案（コミットの本文の仕事。ADR の規約5 に当たる決定なら ADR の仕事）。

**定数の JSDoc は、1 行目に何の値かを書く**。
根拠（実測・出所）は空行の下に置く。
用途が先に無いと、読み手は根拠から用途を逆算することになる。

**同じ事実は一箇所にだけ書く**。
複数のファイルが共有する契約は、持ち主の一箇所（URL を組み立てる側）に書き、他所は「書式は `<持ち主のファイル>` が正」の一行にする。
同じ文書の同じ節への参照が四ファイルに散っているなら、それは冒頭コメントでなくその文書の仕事である。

**コメントは設計の代替ではない**: 「この関数は複雑なので順に説明すると」と書きかけたら、それはコメントの要求ではなく分割の要求。
書くのをやめて関数を割る。
逆に、割っても消えない知識（なぜこの順序か、なぜこの値か）はコメントでしか残せない。

### モジュール冒頭コメントの精度

精度が低いときの兆候:
- ファイル名の言い換え（`user_service.py` → 「ユーザーサービス」）
- 中の関数名を並べた目次（grep で足りるうえ、必ず腐る）
- 「〜を管理する」「〜を処理する」で終わり、**何を管理しないか**が無い

書く内容（該当するものだけ、簡潔に）:
1. **責務**: このモジュールが引き受ける一つのこと
   複数書きたくなったら分割の合図
2. **境界**: 引き受けないこと・呼び出し側に委ねること
   依存の向き
3. **why**: なぜこの切り方なのか
   外部制約（プロトコル、既存スキーマ、API の癖）
4. **入口**: 典型的な呼び出し入口が一つあるならそれ（公開 API の全列挙はしない）

長さの目安は 3〜8 行。
超えるならモジュールが複数の責務を抱えている疑い。
コメントを削るのではなく、**モジュールを割る方を先に検討する**。

判定基準: そのファイルを初めて開いた人が、中身を読む前に「自分が探しているものがここにあるか」を決められるか。
決められないなら精度不足。

一文目は次の型で組み立て、実装の説明から書き始めない。
二文目は、隣のモジュールと持ち物を取り違えうるときだけ書く。

- 一文目: 「<概念> の <種類（関数・型・部品・定数・手順）> を置く」
  種類が関数なら「<入力> から <出力> を作る関数」と書いてよい
- 二文目（要るときだけ）: 「<隣が持つもの> は持たず、<隣のモジュール> が持つ」（例: 「DOM の選択範囲の読み取りは持たず、画面の部品が持つ」）
  取り違える相手が無いモジュール（型だけ・取りうる値の並び）は一文目だけでよい

一文目の例を層ごとに置く。

| 層 | 一文目 |
|---|---|
| 純粋な計算 | 本文の文字オフセットから引用の文字列を作る純関数を置く |
| 型だけ | モジュールをまたいで受け渡すドメイン型だけを置く |
| 取りうる値 | `status` の取りうる値と判定を置く |
| 境界 | 問いとセッションの行を読み書きする repo 関数を置く |
| 画面の部品 | 一覧パネルの一区画を描く部品を置く |
| 配線 | 対話画面のフォームを受け取り、一往復を呼んで redirect する Server Action を置く |

一文目の <概念> を「と」で二つ並べることになるなら、モジュールが一つの役割に収まっていない合図なので、コメントを書く前に割る。

### 削除テスト（残すか削るかの一問）

各行に問う: **この行を知らずにこのファイルを触った人は、具体的に何を間違えるか。**
誤りを 1 つ挙げられないなら、その行は削る。

これはレビュアーの道具である。
書き手が自分の行に当てると必ず答えが作れるので、書く側は `.claude/rules/coding.md`「コメント」節の 2 文の上限と語彙の読者定義で止める。

答えられる（残す）:
- **単位・表現の正**
  「オフセットは UTF-16 code unit」を知らなければ、絵文字で位置がずれる
- **依存している不変条件**
  「レコードは追記のみ」を知らなければ、編集機能を足して壊す
- **禁止則**
  「ここに DOM を持ち込まない」を知らなければ、持ち込む
- **外部制約**
  直せない相手の仕様、既存スキーマ、プロトコルの癖

答えられない（削る）:
- **設計の自己弁護**
  「〜は偶然ではない」「〜のための性質である」「だからここへ寄せた」
  読み手ではなく書き手自身に向いた文
- **予言**
  「永続化が X へ移っても影響を受けない」「将来 Y にも使える」
- **中の関数の目次**
  grep で足りるうえ、必ず腐る
- **コードが語ること**
  import が示す依存、シグネチャが示す引数
- **正しいが行動を変えない事実**
  「両画面から使われる」
- **出典**
  理由を本文に書いた上で添えた ADR・issue の番号と、「2026-08-30 に実測」のような確認の記録

### 時間の切り分け

ソースは**現時点のスナップショット**であって、決定の記録ではない。

| 内容 | 置き場 | 時制 |
|---|---|---|
| いま効いている制約・前提・単位・禁止則（局所） | コメント | 現在 |
| 現在の設計の正（全体像・層の切り方・データモデル） | 設計ドキュメント（ARCHITECTURE.md 等） | 現在 |
| なぜそう決めたか・採らなかった案・トレードオフ | コミットの本文。ADR の規約5 に当たる決定なら ADR（無いリポジトリでは設計ドキュメントの決定節） | 過去 |
| モジュールの内側に閉じた設計の選択（式の形・状態の置き場・値の根拠） | モジュール冒頭のコメント（5 文まで）とコミットの本文 | 現在 |
| いつ何を変えたか | git | — |
| これから変える予定 | issue | 未来 |

**過去形を許されるのは ADR とコミットの本文だけ**。
コメントと設計ドキュメントはどちらもスナップショットで、変わったら古い記述を置き換える。
ADR は追記だけで覆すときも消さず新しい ADR で supersede し、コミットの本文は履歴に残る（だから経緯を安全に移せる）。
逃がし先が無いリポジトリで「経緯は ADR へ」とだけ言うと、行き場を失った経緯がコメントへ逆流する。
規約を配る前に、そのリポジトリの経緯の置き場がどれかを決めておく。

**経緯は捨てるのではなく現在の制約へ書き換える**。
必要なのは出来事ではなく、出来事が残した現在の制約:

- ✗「当初 DOM に埋めていたが検証できず切り出した」（履歴）
- ○「オフセット演算はこのファイルに閉じる。DOM 側へ出すと単体テストが書けない」（禁止則）
- ✗「MVP 最大のリスク箇所なのでテストで固めることにした」（判断の記録）
- ○「境界・区間重複・サロゲートペアはテストが正」（現在の運用）

経緯そのものを残したくなったら、それはコメントを伸ばす合図ではなく、コミットの本文へ出す合図である。
ADR の規約5 に当たる決定なら ADR へ出し、本文へリンク一本を貼り、**貼った先の中身を要約し直さない**。

### 書き直しの実例

削る前（16 行。単位・不変条件・禁止則以外はすべて自己弁護と予言）:

```
// メモのアンカー（メッセージ本文中の文字オフセット）を扱う純関数群。
// 本文の分割・オフセット換算・引用生成を行い、対話画面と逆引き画面の両方が使う。
//
// DB / next / DOM のいずれにも依存しない。
// オフセット演算（サロゲートペア・区間の重複・境界）は MVP 最大のリスク箇所で、DOM に埋めると検証できない。
// だからここへ寄せてテストで固める。
// UI 側は DOM から読んだ数値をこの層に渡すだけにする。
// 永続化が Prisma + Postgres へ移っても（issue #11）この層は影響を受けない。
// DB 非依存はそのための性質であって、偶然ではない。
//
// オフセットの正は JS の string index（UTF-16 code unit）。
// コードポイント（サロゲートペアで 2 code unit を使う絵文字等）ではない。
//
// アンカーが腐らない根拠は messages が immutable（追記のみ・編集しない）であること。
// この不変条件が壊れると、保存済みのオフセットが別の位置を指し始める。
// ここの全関数の前提が同時に崩れる（docs/ARCHITECTURE.md データモデル節）。
```

削った後（10 行。踏む地雷は 1 つも減っていない）:

```
// メッセージ本文の文字オフセット（アンカー）を扱う純関数群。
//
// オフセットの単位は JS の string index（UTF-16 code unit）。
// コードポイントではない。
// 絵文字は 1 文字で 2 進む。
// アンカーの有効性は messages が immutable（追記のみ）であることに依存する。
// 編集を許すと保存済みオフセットが別の位置を指す（docs/ARCHITECTURE.md データモデル節）。
//
// DB / next / DOM を持ち込まない。
// オフセット演算をテストで固めるための切り出しで、外部依存が入った時点で検証できなくなる。
```

## テストの判断基準

規則は `.claude/rules/coding.md`「テスト」節が正で、ここは規則を当てるときの例だけを持つ。

- テスト名の例は「ai_b が失敗すると messages は空のままで、pending_messages に本文が残る」
  前提と観測できる結果が一文に入り、実装の関数名は出ない
- 読み直した状態の検証は、公開されている関数を通して行う
  内部の状態を直に読むテストは、公開の経路が壊れても緑のまま通る
- ケースごとの前提（所有者・行）は `beforeEach` で作り、前のケースが残した状態に寄りかからない
- テストダブル（フェイク・スタブ）の冒頭コメントは、本物と違えた振る舞いを一文目に、その違いで何を検査するかを二文目に書く
  本物の実装の説明を書き写した冒頭は、何のためのダブルかを語らない

## 余白と密度の判断基準

空行を入れる位置（PEP 8 の趣旨を言語横断で適用）:
- 定義の間を何行空けるかは言語ごとに違うので、幅は `.claude/rules/languages/<lang>.md` が持つ
  ここでは入れる位置だけを扱う
- 関数内で段落が変わるところ: 準備 → 主処理 → 後始末 / 取得 → 変換 → 返却
- ガード節の塊と本体の間
- 大きなループ・条件ブロックの前後
- 本体が数行以上あるときの `return` の前
- 変数の宣言群と、それを使い始める処理の間
- 一つの意味を持つコメントとその対象の、前後

空行を入れない位置:
- 関数の先頭と末尾（開き括弧の直後、閉じ括弧の直前）
- 1 つの意味をなす連続した数行の内部（分けると塊が壊れる）
- 関数内の 2 行以上の連続空行（2 行はトップレベルの区切り専用）

**リンタは助けてくれない**: ruff の E301–E306 も Prettier / Biome も、見るのは定義の周辺だけで、関数**内部**の論理ブロックの空行は誰も検出しない。
フォーマッタは既存の空行を保存するが、無い空行を足しはしない。
入れるのは書き手の責務。

### エージェント特有の密度最適化（避ける）

生成の都合で短く書く癖は、そのまま人間の読み手へ転嫁される。

| 兆候 | 代わりに |
|---|---|
| 空行ゼロの関数（全行が詰まっている） | 論理ブロックで割る |
| 三項演算子・内包表記の多重ネスト | 中間変数か if 文へ展開する |
| 中間変数を省いた長い式・メソッド連鎖 | 名前付き中間変数に意図を語らせる |
| 引数の中で `await` する | 先に変数へ受けてから渡す |
| why コメントごと削除して行数を減らす | why は残す（コメントの判断基準） |
| 結論を先に立てて理由を後ろへ継ぎ足す | 「B なので A」と理由を前に置き、一文で閉じる |
| 冒頭コメントがファイル名の言い換え | 責務と境界（何をしないか）を書く |
| コメントで設計を弁護する（「偶然ではない」） | 削除テストにかける。経緯ならコミットの本文か ADR へ |
| 1 行に複数文（`;` 連結、1 行 if、複数代入） | 分ける |
| 触っていない箇所の空行・整形まで詰める | 変更は当該論理ブロックに閉じる |
| 早すぎる共通化で呼び出し側を圧縮 | YAGNI。2〜3 例目まで待つ |

原則: **短さは可読性の代理指標ではない**。
迷ったら、初見の人間が上から一度読んで理解できるかで決める。

## レビュー時の適用手順

1. 差分を読む前に目的（何を達成する変更か）を確認する
2. 上の判断基準を **命名 → 分割 → 状態 → 凝集 → エラー** の順に当てる
3. 指摘には必ず理由（どの原則にどう反するか）と改善案を添える
4. 規約に無い好みの問題は「nit:」を付けて強制しない

## 言語別の作法

| 言語 | ファイル | 読み込まれる条件 |
|---|---|---|
| TypeScript / JavaScript | `.claude/rules/languages/typescript.md` | `*.{ts,tsx,mts,cts,js,jsx,mjs,cjs}` を Read したとき |
| Python | `.claude/rules/languages/python.md` | `*.py` を Read したとき |
| Prisma | `.claude/rules/languages/prisma.md` | `*.prisma` を Read したとき |

新しい言語が要るときは同じ構造（原則→言語イディオムへの写像・frontmatter の `paths` で拡張子を縛る）で 1 ファイル足す。
