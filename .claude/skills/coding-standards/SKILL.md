# コーディング規約 — 判断基準と適用例

核（`.claude/rules/coding.md`）の原則を実コードに適用するための判断基準集。
言語固有の作法は `.claude/rules/languages/<lang>.md` が持ち、該当言語のファイルを Read した時点で自動で読み込まれる（全言語を読み込まない）。
隣接ファイルを読まずに新規ファイルを書き始めるときだけ、先に自分で Read する。

## 命名の判断基準

- **テスト**: 名前だけ見て、実装を読まずに呼べるか。
  呼んだ結果を予想できるか
- 汎用語（`data`, `info`, `manager`, `process`, `handle`, `util`）は思考停止の兆候。
  「何の」データか、「どう」処理するかまで名前に押し込む
- ブール値は `is/has/can/should` + 肯定形。
  `isNotReady` のような否定形は二重否定 `!isNotReady` を生む
- 単位・型・範囲が誤解を生むなら名前に含める（`timeoutMs`, `maxRetries`）
- 対称性を守る: `open/close`, `begin/end`, `add/remove` を混ぜて崩さない

## 関数分割の判断基準

分割する合図（いずれか該当で検討）:
- 関数名に and / or / then が要る
- コメントで内部をセクション分けしている（各セクションが関数候補）
- 抽象度の混在: ビジネスルールの隣に文字列整形やループの添字操作がある
- フラグ引数で内部分岐している（呼び出し側は常にどちらか一方しか使わない）
- テストのセットアップが肥大する（責務が多い証拠）

分割しない合図:
- 一度しか呼ばれず、抽出しても名前が `doStep2` にしかならない
- 抽出すると引数が 5 個になる（データの塊を見落としている可能性。先に構造化）

## 状態設計の判断基準

- **不正状態の表現不能化**: 「A のとき B は null」のような暗黙の相関があるなら、型で分ける（直和型 / サブクラス / 状態ごとの型）
- setter を書く前に問う: 生成後にそれが変わるのは本当にドメインの性質か、それとも生成手順の都合か。
  後者ならコンストラクタ/ファクトリに寄せる
- プリミティブ執着: 金額・ID・範囲などドメインの概念が生の int / string で取り回されていたら値オブジェクト化を検討（バリデーションの置き場が定まる）

## 凝集・結合の判断基準

- あるデータを変更するとき、離れた複数ファイルを同時に直す必要がある → ロジックがデータから逸走している（低凝集）。
  データ側に引き寄せる
- クラスの一部のフィールドしか使わないメソッド群がある → クラス分割の候補
- 引数に渡したオブジェクトの getter を掘って判断している（尋ねるな、命じよ） → 判断ロジックをオブジェクト側へ移す

### 置き場の規律（型の置き場 / 振る舞いの置き場）

Data Class 臭がロジックの逸走なら、こちらはその裏返し。
**値が型の側へ逆流する**形。

- **型だけを置くモジュール（`types.ts`・`models.py` 等）に実行時の値を置かない。**
  定数・既定値・変換テーブルは、それを使うモジュールへ置く。
  型だけのモジュールを import しただけで実行時の依存が付いてくると、型のためだけの参照ができなくなる
- **振る舞いを持つものは、それを扱うモジュールへ。**
  寄せる基準は関連でなく、一緒に変わるかどうか。
  「関連しているから」で同じファイルへ寄せない
- 検証は TypeScript のみ（2026-08-16 時点）。
  他言語で同じ形を見たら、そのとき一般化してよいかを判断する

### Data Class の検出と対処

**構文ではなく構造で判定する。
** `@dataclass`・record・struct を使うこと自体は悪臭ではない（frozen な値オブジェクトの手段としてむしろ推奨）。
悪臭は「データと、それを守る/扱うロジックが別の場所に引き裂かれている」構造の側にある。

兆候（いずれか該当で疑う）:
- フィールドと getter/setter だけのクラスに対し、外部の Manager / Service / Util がそのデータを取り出して計算・検証している
- 同じバリデーション（金額は非負、名前は N 文字以内…）が複数の呼び出し側に重複している
- そのクラスのインスタンスが「生成 → 各所で setter で徐々に組み立て」されている（未初期化の中間状態が野放しになる）

対処:
- 計算・検証ロジックをデータを持つクラス自身のメソッドへ移す
- 完全コンストラクタ + 不変化とセットで行う（生成時に検証、以後は変わらない）
- ドメイン概念なら値オブジェクトへ昇格（金額 + 通貨、氏名、期間など）

許容される例外（悪臭ではないもの）:
- システム境界の DTO（API リクエスト/レスポンス、永続化層のレコード）。
  意図的な「運搬役」であり、ドメインロジックを持たせないのがむしろ正しい。
  ただし境界を越えたらドメインオブジェクトへ詰め替える。
  DTO のままアプリケーション内部を旅させない

## エラー処理の判断基準

- catch して log だけ出して続行 = 握りつぶし。
  回復できないなら再送出か停止
- null 返却の代替の選択: コレクションなら空を返す / 「無い」が正常系なら Optional 相当 / 異常系なら例外
- 例外は「例外的」な場合のみ。
  通常フローの分岐に例外を使わない

## コメントの判断基準

書くべき: 呼び手が踏む誤用を止める前提、外部制約（API の癖、規格）、警告（この順序を変えると壊れる）、TODO（期限か条件付きで）。
書くべきでない: コードの逐語訳、変更履歴（git の仕事）、コメントアウトされた死体コード（消す。git にある）、採らなかった代替案（ADR の仕事）。

**理由は 1 関数 2 文まで**。
「コメントは why 専用」「関数には例外なく JSDoc」「理由は結論の前」を同時に守ると、全関数に理由の段落が付く。
削除テストは書き手には効かない（書き手はどの行にも「知らないと間違える」を一つ作れる）ので、書く側は数で止める。
3 文目を書きたくなったら、それは ADR を書く合図で、コメントにはリンク一行を残す。
上限は鈍い道具で、書記素境界の説明のように正当な例外はある。
例外にするときは、その関数の呼び手が実際に踏んだ誤りを挙げられることを条件にする。

**同じ事実は一箇所にだけ書く**。
逆引きリンクの書式のように三ファイルが共有する契約は、持ち主の一箇所（URL を組み立てる側）に書き、他所は「書式は `memos/page.tsx` が正」の一行にする。
同じ文書の同じ節への参照が四ファイルに散っているなら、それは冒頭コメントでなくその文書の仕事である。

**コメントは設計の代替ではない**: 「この関数は複雑なので順に説明すると」と書きかけたら、それはコメントの要求ではなく分割の要求。
書くのをやめて関数を割る。
逆に、割っても消えない知識（なぜこの順序か、なぜこの値か）はコメントでしか残せない。

### 語彙

読者は、このリポジトリの md を読んでいないエンジニアと決める。
比喩と個人語彙は書き手には一意でも、その読者には辞書が無い。
判定は英語への直訳で、一語が二つ以上の英語に割れたら比喩である。

| 使わない | 代わりに | 割れ方 |
|---|---|---|
| 引く | 取得する・検索する | pull / fetch / query |
| 落とす | throw する・削除する・拒否する | throw / drop / reject |
| 倒す | 既定値にする・フォールバックする | fall / default |
| 畳む | まとめる・変換する・閉じる | fold / collapse / close |
| 流す | 適用する・デプロイする・実行する | apply / deploy / run |
| 弾く・握る・掛ける | 拒否する・握りつぶす・設定する | reject / swallow / set |
| 口・関門・印・登録簿・受け皿・素通し | エントリポイント・検証・フラグ・レジストリ・既定の行・検証なしで通す | 語ごとに定義が要る |
| 領分・綴り・「〜の側」 | 担当・名前・主体の名（「規約の側」でなく `callPersona`） | 主体が無い。「クライアント側」のような位置の用法は可 |
| 器 | リポジトリ／アプリ | ADR 0014 が言い換えると決めた語 |

物は識別子で名指しする。
「唯一の利用者の email を env から読む」でなく「`TOIITO_SINGLE_USER_EMAIL` を読む」。
言い換えると読み手は識別子との対応を自分で復元することになる。

製品の比喩語（発酵槽・仕込む・面の温度・書きの間）は UI の文言と設計文書に閉じる。
コードのコメントは「問いの一覧と投入フォーム」のように技術の語で言い、`DESIGN.md`「重心」のように文書名と節名の一行で参照する。
HARNESS の層記号（L0〜L5）も同じで、コメントでは `tsc`・lint・単体テストと道具の名で言う。

### 省略

日本語は主語と目的語を落としても文になるので、書き手が知っている前提がそのまま抜ける。
レビューで「何が」「何を」と訊かれた形がそれで、抜けた語を補うと 1 行目の what が立つ。

- ✗ `未設定なら落とす` → ○ `TOIITO_SINGLE_USER_EMAIL が未設定なら throw する`
- ✗ `書き込みの前に呼ぶ` → ○ `問いを更新・削除する repo 関数が、最初に呼ぶ`
- ✗ `所有者の問いを一件引く` → ○ `id で問いを 1 件取得する。所有者が owner でなければ undefined`
- ✗ `他人の問いも undefined になる` → ○ `owner 以外が所有する問いも undefined になる`
- ✗ `ここに値を足したら向こうにも足す` → ○ `この enum に値を足したら QUESTION_STATUSES にも足す`

失敗の形は throw か undefined か空配列かを毎回書く。
「落とす」「弾く」はどれにも読める。

### 語順

- 理由は結論の前に置く。
  日本語は述語が末尾に来るので、「B なので A」と書けば一文で閉じる。
  「A。B」と倒置すると文が一度閉じてしまい、理由を継ぎ足す場所が文の外にしか残らない
  - ✗ `N+1 に割らない。メモ一覧はメモの数だけ問いを引きに戻る形になりやすい`
  - ○ `メモ一覧はメモの数だけ問いを引きに戻る形になりやすいので、N+1 に割らない`
- 倒置してよいのは、結論を先に立てること自体が目的のときだけ。
  走査して拾わせたい禁止則の見出しがそれで、理由を読まなくても行動が決まる

倒置は英語の語順に引かれて入り込む。
英語は主節が先に来るので「Don't do X — because Y」が自然に書けるが、日本語で同じ順に並べると理由が文の外へこぼれる。

### 改行と字面

- 折り返しは**句点でのみ**。
  接続の直後（「〜のため、」「〜だが、」）や述語の切れ目では改めない。
  日本語としては意味の切れ目だが、桁で折った跡と見分けが付かない
- **1 行 1 文**。
  1 行完結の JSDoc も同じで、2 文あるならブロックへ展開する
- 言い切った文の末尾へ `——` で補足を継ぎ足さない。
  補足は次の行の独立した文にする。
  括弧の内側は文が閉じていないので、この限りでない
- 語の途中・助詞の直前・「A と B」の間で折らない。
  片方の行だけ読んで意味が壊れる位置は、そこが切れ目でない証拠
- 行長に上限は無い。
  折る位置が見つからないときは、探すのではなく**文が長すぎる**と判断して分ける
- 1 行 1 命題を目安に。
  並列を散文へ押し込んで折り返すより、箇条にした方が読める
- 箇条・例示・図示の行は句点で閉じなくてよい。
  散文ではないので、そもそも折れた文ではない
- 既存コメントの折り返し位置を、無関係な変更のついでに詰め直さない

### モジュール冒頭コメントの精度

精度が低いときの兆候:
- ファイル名の言い換え（`user_service.py` → 「ユーザーサービス」）
- 中の関数名を並べた目次（grep で足りるうえ、必ず腐る）
- 「〜を管理する」「〜を処理する」で終わり、**何を管理しないか**が無い

書く内容（該当するものだけ、簡潔に）:
1. **責務**: このモジュールが引き受ける一つのこと。
   複数書きたくなったら分割の合図
2. **境界**: 引き受けないこと・呼び出し側に委ねること。
   依存の向き
3. **why**: なぜこの切り方なのか。
   外部制約（プロトコル、既存スキーマ、API の癖）
4. **入口**: 典型的な呼び出し口が一つあるならそれ（公開 API の全列挙はしない）

長さの目安は 3〜8 行。
超えるならモジュールが複数の責務を抱えている疑い。
コメントを削るのではなく、**モジュールを割る方を先に検討する**。

判定基準: そのファイルを初めて開いた人が、中身を読む前に「自分が探しているものがここにあるか」を決められるか。
決められないなら精度不足。

### 削除テスト（残すか削るかの一問）

各行に問う: **この行を知らずにこのファイルを触った人は、具体的に何を間違えるか。**
誤りを 1 つ挙げられないなら、その行は削る。

これはレビュアーの道具である。
書き手が自分の行に当てると必ず答えが作れるので、書く側は上の「理由は 2 文まで」と語彙の読者定義で止める。

答えられる（残す）:
- **単位・表現の正**。
  「オフセットは UTF-16 code unit」を知らなければ、絵文字で位置がずれる
- **依存している不変条件**。
  「レコードは追記のみ」を知らなければ、編集機能を足して壊す
- **禁止則**。
  「ここに DOM を持ち込まない」を知らなければ、持ち込む
- **外部制約**。
  直せない相手の仕様、既存スキーマ、プロトコルの癖

答えられない（削る）:
- **設計の自己弁護**。
  「〜は偶然ではない」「〜のための性質である」「だからここへ寄せた」。
  読み手ではなく書き手自身に向いた文
- **予言**。
  「永続化が X へ移っても影響を受けない」「将来 Y にも使える」
- **中の関数の目次**。
  grep で足りるうえ、必ず腐る
- **コードが語ること**。
  import が示す依存、シグネチャが示す引数
- **正しいが行動を変えない事実**。
  「両画面から使われる」

### 時間の切り分け

ソースは**現時点のスナップショット**であって、決定の記録ではない。

| 内容 | 置き場 | 時制 |
|---|---|---|
| いま効いている制約・前提・単位・禁止則（局所） | コメント | 現在 |
| 現在の設計の正（全体像・層の切り方・データモデル） | 設計ドキュメント（docs/ARCHITECTURE.md 等） | 現在 |
| なぜそう決めたか・採らなかった案・トレードオフ | ADR（無いリポジトリでは設計ドキュメントの決定節） | 過去 |
| いつ何を変えたか | git | — |
| これから変える予定 | issue | 未来 |

**過去形を許されるのは ADR だけ**。
コメントと設計ドキュメントはどちらもスナップショットで、変わったら古い記述を置き換える。
ADR だけが追記され、覆すときも消さず新しい ADR で supersede する（だから経緯を安全に捨てられる——捨てるのではなく移すだけになる）。
逃がし先が無いリポジトリで「経緯は ADR へ」とだけ言うと、行き場を失った経緯がコメントへ逆流する。
規約を配る前に、そのリポジトリの受け皿がどれかを決めておく。

**経緯は捨てるのではなく畳む**。
必要なのは出来事ではなく、出来事が残した現在の制約:

- ✗「当初 DOM に埋めていたが検証できず切り出した」（履歴）
- ○「オフセット演算はこのファイルに閉じる。DOM 側へ出すと単体テストが書けない」（禁止則）
- ✗「MVP 最大のリスク箇所なのでテストで固めることにした」（判断の記録）
- ○「境界・区間重複・サロゲートペアはテストが正」（現在の運用）

経緯そのものを残したくなったら、それは ADR を書く合図であってコメントを伸ばす合図ではない。
本文へリンク一本を貼り、**貼った先の中身を要約し直さない**。

### 書き直しの実例

削る前（16 行。単位・不変条件・禁止則以外はすべて自己弁護と予言）:

```
// メモのアンカー（メッセージ本文中の文字オフセット）を扱う純関数群。
// 本文の分割・オフセット換算・引用生成を行い、対話画面と逆引き画面の両方が使う。
//
// DB / next / DOM のいずれにも依存しない。
// オフセット演算（サロゲートペア・区間の重複・境界）は MVP 最大のリスク箇所で、DOM に埋めると検証できない。
// だからここへ寄せてテストで固める。
// UI 側は DOM から読んだ数値をこの層に渡すだけにする。
// 永続化が Prisma + Postgres へ移っても（issue #11）この層は影響を受けない。
// DB 非依存はそのための性質であって、偶然ではない。
//
// オフセットの正は JS の string index（UTF-16 code unit）。
// コードポイント（サロゲートペアで 2 code unit を使う絵文字等）ではない。
//
// アンカーが腐らない根拠は messages が immutable（追記のみ・編集しない）であること。
// この不変条件が壊れると、保存済みのオフセットが別の位置を指し始める。
// ここの全関数の前提が同時に崩れる（docs/ARCHITECTURE.md データモデル節）。
```

削った後（10 行。踏む地雷は 1 つも減っていない）:

```
// メッセージ本文の文字オフセット（アンカー）を扱う純関数群。
//
// オフセットの単位は JS の string index（UTF-16 code unit）。
// コードポイントではない。
// 絵文字は 1 文字で 2 進む。
// アンカーの有効性は messages が immutable（追記のみ）であることに依存する。
// 編集を許すと保存済みオフセットが別の位置を指す（docs/ARCHITECTURE.md データモデル節）。
//
// DB / next / DOM を持ち込まない。
// オフセット演算をテストで固めるための切り出しで、外部依存が入った時点で検証できなくなる。
```

## 余白と密度の判断基準

空行を入れる位置（PEP 8 の趣旨を言語横断で適用）:
- トップレベル定義（関数・クラス）の間は 2 行、メソッド間は 1 行（Python）。
  他言語は 1 行で揃える
- 関数内で段落が変わるところ: 準備 → 主処理 → 後始末 / 取得 → 変換 → 返却
- ガード節の塊と本体の間
- 大きなループ・条件ブロックの前後
- 本体が数行以上あるときの `return` の前
- 変数の宣言群と、それを使い始める処理の間

空行を入れない位置:
- 関数の先頭と末尾（開き括弧の直後、閉じ括弧の直前）
- 1 つの意味をなす連続した数行の内部（分けると塊が壊れる）
- 関数内の 2 行以上の連続空行（2 行はトップレベルの区切り専用）

**リンタは助けてくれない**: ruff の E301–E306 も Prettier / Biome も、見るのは定義の周辺だけで、関数**内部**の論理ブロックの空行は誰も検出しない。
フォーマッタは既存の空行を保存するが、無い空行を足しはしない。
入れるのは書き手の責務。

### エージェント特有の密度最適化（避ける）

生成の都合で短く書く癖は、そのまま人間の読み手へ転嫁される。

| 兆候 | 代わりに |
|---|---|
| 空行ゼロの関数（全行が詰まっている） | 論理ブロックで割る |
| 三項演算子・内包表記の多重ネスト | 中間変数か if 文へ展開する |
| 中間変数を省いた長い式・メソッド連鎖 | 名前付き中間変数に意図を語らせる |
| why コメントごと削除して行数を減らす | why は残す（コメントの判断基準） |
| コメントを桁数基準で機械的に折り返す | 句点で改める（読点でも折らない） |
| 1 行へ複数の文を詰める・`——` で補足を後置きする | 1 行 1 文。補足も次の行の独立した文にする |
| 冒頭コメントがファイル名の言い換え | 責務と境界（何をしないか）を書く |
| コメントで設計を弁護する（「偶然ではない」） | 削除テストにかける。経緯なら ADR へ |
| 1 行に複数文（`;` 連結、1 行 if、複数代入） | 分ける |
| 触っていない箇所の空行・整形まで詰める | 変更は当該論理ブロックに閉じる |
| 早すぎる共通化で呼び出し側を圧縮 | YAGNI。2〜3 例目まで待つ |

原則: **短さは可読性の代理指標ではない**。
迷ったら、初見の人間が上から一度読んで理解できるかで決める。

## レビュー時の適用手順

1. 差分を読む前に目的（何を達成する変更か）を確認する
2. 上の判断基準を **命名 → 分割 → 状態 → 凝集 → エラー** の順に当てる
3. 指摘には必ず理由（どの原則にどう反するか）と改善案を添える
4. 規約に無い好みの問題は「nit:」を付けて強制しない

## 言語別の作法

| 言語 | ファイル | 読む条件 |
|---|---|---|
| TypeScript / JavaScript | `.claude/rules/languages/typescript.md` | `*.{ts,tsx,mts,cts,js,jsx,mjs,cjs}` を Read したとき |
