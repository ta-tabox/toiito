# レビューで繰り返し指摘される型

機械の検査が通った後に人間のレビューが繰り返し拾った型を、判定と直し方で持つ。
書き終えたら、変更した各コメント・名前・ファイルにこの表を一度当ててから PR にする。

| 型 | 判定 | 直し方 |
|---|---|---|
| コメントが今の実装を語る | 関数の本体を別の書き方に置き換えたら、この文も直すことになるか | 役割（何に責任を持ち、何に持たないか）だけを残し、実装の説明は消す |
| 識別子の羅列 | その文から識別子を消すと、何をするかが読めなくなるか | 一般語で何をするかを言い直し、識別子は括弧で添える |
| 目的の無い保証 | 並び順・不変条件を書いた文に、何のための保証かがあるか | 保証が効く先（どの画面・どの呼び手が何を頼るか）を添える |
| 目的の無い関数 | 関数名と 1 行目から、何のために呼ぶかが読めるか | 呼ぶ目的を一文添える |
| 抽象だけの冒頭 | 冒頭を読んで、入力から結果までの動作を思い浮かべられるか | 具体例一つで入力と結果を示す |
| 実装から数えた数 | 「N つの経路」「N 行」「N 本」の N が、コードを数えて出た値か | 数を消し、何をするかの文にする |
| 造語 | その名詞は識別子か、辞書にある一般語か | 識別子はバッククォートで、概念は一般語で書き直す |
| 婉曲 | 動作を技術用語（取得する・throw する・拒否する）で言い直せるか | 失敗の形（throw・undefined・空配列）を毎回書いて言い直す |
| 場所が語ることの再掲 | その文は、ファイルのパス・import 文・`layers.md` を見れば分かるか | 消す |
| 比喩・ライブラリの API 名・タグ名が名前に入る | 名前から、保持するもの・行うことを一般語として読み取れるか | 保持するもの・操作の一般語に改名する |
| 名前が汎用語 | `data`・`util`・`common` のように、隣のファイルにも同じ名前を付けられるか | 保持するものの名前にする |
| 名前が実装の一段階だけを言う | ファイル名が、中の関数の集合を一語で言えているか | 集合の名前にする（実装の一段階は関数名が持つ） |
| 同じ形の文字列の散在 | 同じ書式の文字列（URL・id・台詞）を二つのファイルが組み立てているか | 持ち主のモジュールを一つ作り、キー付きのオブジェクトで持つ |
| 配線ごとに繰り返す前置き | すべての配線が同じ検査を先頭に持つか | 共通の入口の一箇所に寄せる |
| 1 ファイルに複数のコンポーネント | 二つ目のコンポーネントを書いているか | 別ファイルへ切る |
| className の定数 | 同じ並びを名指すために定数にしたか | その要素を部品として切り出す |
| 位置を子が語る | 冒頭コメントか props が、親の中での位置（重ねる位置・幅）に触れているか | 親へ移す |
| 現況の文書に実装の粒度 | その行は、一つのファイルを直すだけで古くなるか | ソースコードとそのコメントへ移す |
| ADR に実装の選択 | その決定は、ADR の規約（`docs/adr/README.md`）に当たる決定か | 当たらないなら、コミットの本文とコメントへ移す |
| 表の散文 | セルに二文以上あるか | 列を足すか、行の抽象を上げて組み直す |
| 利用者への文言が長い | 状況の一文と操作の一つに収まっているか | 収める |
