# TypeScript / JavaScript への写像

核（`coding.md`）の原則を TS のイディオムへ写す。
書き方だけを持ち、toolchain（pnpm / Biome / mise）の設定は持たない。

## 不変を既定に
- `const` で宣言し、再代入が本質的なときだけ `let` にする
- プロパティは `readonly`、配列は `ReadonlyArray<T>` / `readonly T[]` を検討
- 更新はスプレッドで新オブジェクト生成を基本とし、局所的な可変は関数内に閉じる

## 不正状態の表現不能化
- 直和型 + 判別子で状態を分ける:
  `type State = { kind: "loading" } | { kind: "loaded"; data: Item[] } | { kind: "error"; error: Error }`
  「loading なのに data がある」を型レベルで排除する
- 「無い」の表し方を `undefined` か `null` のどちらかに決め、リポジトリの中で揃える
  決めた側と、外部の値（DB の NULL 列・JSON の `null`）を写す型だけに現れる例外は、同じ `paths` を持つ `typescript.project.md` に書く
- 外から来た値は `unknown` で受け、絞り込んでから使う
- 取りうる値は `as const` の並びから型を導く（`(typeof VALUES)[number]`）
  取りうる値ごとの表は `Record<その値の型, …>` で受け、値を足したときに型検査で止まる形にする
- 検証を通った値はブランド型（`string & { readonly __brand: "OwnerId" }`）で表し、その型を作るのは検証した関数だけにする

## 関数・エラー
- 異常は例外で表す
  Result 型（`{ ok: true; value } | { ok: false; error }`）を採るリポジトリは `typescript.project.md` にそう書き、混在させない

## 式と制御
- `await` は文の先頭か代入の右辺に置く
  引数の中で `await` した値は、先に変数へ受けてから渡す
- 配列から配列を作るときは `map` と `filter` を使い、添字が要るときも `map` の第二引数で受ける
  `for` を使うのは、途中で return するか、`await` を直列に待つときに限る
- 一つの意味を持つコメントとその対象は空行で区切り、どの文に付くコメントかを見て分かるようにする

## import
- **`@`（パスエイリアス）起点で書かなくてよいのは、`@` を定義する側だけ**
  エイリアスが解決される前に読まれる設定ファイルと、素の node が読むスクリプトは相対パスで書く

## 命名
- 型は PascalCase、値は camelCase、定数は用途次第（グローバル定数のみ UPPER_SNAKE）
- 型名は PascalCase の名詞にし、実装と同じ語で呼ぶ
  `I` プレフィクスで実装と区別したくなるのは設計が滲んでいる兆候

## 余白
- 論理ブロックごとに 1 行空ける
  空けるのは 1 行で、連続 2 行はトップレベルの区切りにも使わない
- Prettier / Biome は既存の空行を（1 行に丸めて）保存するだけで、足してはくれない
  整形が通ることと読めることは別
- メソッドチェーンは段ごとに改行して意図を段落化する

## コメント / JSDoc
- **1 行目は what を完全な文で書く**
  動詞・対象・キー・戻り値の形を一般語で一文にし、引数や欄の名前は括弧で添える（「`items` のうち、選択中のタグ（`selectedTags`）をすべて持つものを返す」）
  識別子を並べて組んだ文は、名前の意味を知らない読み手にはコードの読み直しになる
  シグネチャを見なくても呼べる一文が目標で、理由・制約・失敗の仕方は空行を挟んで下へ置く
  要約に条件や経緯を詰めると、補完のポップアップで最初に出る一行が読めなくなる
- 2 行目以降に書くのは**シグネチャが語らないこと**
  順序の保証、失敗の仕方、呼んではいけない場面、前提にしている不変条件
  重ねないのは `@param` / `@returns` の型注釈であって、要約から引数を省くことではない（括弧で添えて名指す）
- **要約の語彙は関数名に合わせる**
  名前と違う語で呼び始めると読み手は別のものを探し始めるので、`createQuestion` の説明を「問いの投入」で始めない
  ドメインの言葉で呼びたいなら、寄せるのは説明でなく名前の方
- `@param` と `@returns` には、型が語れない制約だけを書く
- 構文から意図が読めない一行（`.min(1)`、`path.resolve(root, \`.${relative}\`)`）には、その行の理由を `//` で添える
- 型と interface の JSDoc は、その値が何を表し、誰が作って誰へ渡すかを書く
  フィールドの目次は書かない

## 機械が見ている分

`pnpm check` が見る規則は記憶で守らず、報告が出てから直す。
error は終了コードを赤にし、warn は報告だけを出すので、warn も報告が出たら直す。
severity はリポジトリで決める（下は雛形の既定）。
「何のために」の列は、各規則が防ぐものを一句で持つ。
`scripts/lint-comments.ts` の規則は、各検査の JSDoc が理由を持つ。

| 規則 | 道具 | severity | 何のために |
|---|---|---|---|
| モジュール冒頭コメントの有無・`/** */`・直後の空行 | `scripts/lint-comments.ts` | error | 中身を読む前に、責務と境界が分かる |
| `@param {string}` のような型注釈の重複 | 同上 | error | JSDoc と TS の型が食い違わない |
| コメントの改行が句点に乗っているか（箇条・例示の行は除く） | 同上 | error | 桁で折った跡を残さない |
| コメント 1 行に 2 文以上置いていないか（括弧の内側の句点は除く） | 同上 | error | 一文直した diff が 1 行で済む |
| コメントの禁止語（表は `writing.md`「語彙と読み手」節） | 同上 | warn | 初見の読み手に辞書の無い語を使わない |
| 関数の JSDoc の有無 | 同上 | warn | 何を保証するかを書く前に言えるか確かめる |
| 宣言に接した `//` | 同上 | warn | 説明がホバーに出て呼び出し側へ届く |
| 言い切った文への `——` の後置き | 同上 | warn | 閉じた文へ読み手を戻さない |
| 関数の JSDoc の理由が 2 文以内か | 同上 | warn | 全関数に理由の段落が付くのを止める |
| バッククォートで名指した識別子・ファイルの実在 | 同上 | warn | 改名した相手を古い名前で指さない |
| import は `@` 起点 | biome `style/noRestrictedImports` | error | 相対パスの登り（`../`）は位置を語らない |
| 1 行 if・三項の多重ネスト・複数代入・多重宣言 | biome | error | 書き手には短く、読み手には遅い形を止める |
| floating promise | biome `nursery/noFloatingPromises` | error | 待たない意図を `void` で明示させる |
| 認知的複雑度 | biome `complexity/noExcessiveCognitiveComplexity` | error | 関数を分ける合図にする |
| 引数 3 つ超 | biome `complexity/useMaxParams` | warn | 呼び出し側で各値の名前が読める |

この表に無い作法（1 行目は要約だけ・要約の語彙は関数名・冒頭が責務と境界を語るか）は機械が見ないので、書く前にこのファイルを読むこと以外に守る手段が無い。
