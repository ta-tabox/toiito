# コーディング規約（核）

Clean Code / リーダブルコード / 良いコード悪いコードの交差点の蒸留。
上の `paths` に当たるファイルを Read した時点で読み込まれる。
コードに触らないセッションでは読み込まれないので、コードの外でも効く規律（文章・コミットの粒度）は `writing.md` が持つ。
判断に迷う具体例は skill `coding-standards` が持つ（**コードを書く前に開く**。実装・レビュー・リファクタ・設計判断のすべてが対象）。
言語固有の作法は `languages/<lang>.md` が持ち、該当言語のファイルを Read した時点で読み込まれる。
リポジトリのモジュールと依存の向きの表は `layers.md` が持つ。
ここには常時必要な原則だけを置く。
規則は「〜する」の形で書き、禁じる形で残すのは走査して拾わせたい禁止則だけにする。

## 命名
- 名前は意図を語る。
  読み手が中身を推測せずに済む名前にし、短さより誤解されないことを優先する
- 情報量はスコープに比例させる。
  ループ変数は `i` でよく、公開 API は冗長でよい
- 挙動が変わったら改名もセットで行う。
  名前が挙動を言い当てている状態を保つ
- 同じ対象には一つの名前を与える。
  派生に別語を当てると、読み手は概念が二つあると読む（`cuts` を並べただけのものを `points` と呼ばない）
- 動詞の接頭辞は skill `coding-standards`「命名の判断基準」の表から選び、同じ意味には同じ動詞を使う

## 関数・メソッド
- 小さく、一つのことをする関数にする。
  説明に「〜して、〜する」が要るなら分割候補
- 抽象度を揃える。
  高レベルの流れと低レベルの操作は別の関数に分ける
- 引数は少なく（3つ以上で構造化を検討）。
  フラグ引数は関数分割の合図
- 副作用があるなら名前で告知する

## 制御流
- ガード節・早期 return でネストを浅く保ち、else を減らす
- 条件式は肯定形で単純に書く。
  複雑な条件は説明変数か関数へ抽出する

## 状態・データ
- 不変を既定にする。
  可変は必要な場所へ最小スコープで置く
- 生成時に完全な状態を保証する（完全コンストラクタ）。
  不正な状態を表現不能にする
- データと、それを扱うロジックを同じ場所に置く。
  あるデータのバリデーション・計算が外部（Manager / Service 等）に散っていたら、データを持つ側へ寄せる（Data Class 臭）。
  構文の話ではない。
  `@dataclass` 等は不変な値オブジェクトの手段としてむしろ推奨で、ロジックを持たない運搬役が正しい境界の DTO は例外
- 一つしか無い状態の正は一箇所に決める（URL・store・親の props のどれか一つ）。
  同じ状態を二箇所に複製すると、同期が state の突き合わせになる

## 置き場と依存の向き
- 外部との境界（DB・ネットワーク・ファイル・DOM・環境変数）は、それぞれ一つのモジュールに閉じる。
  他のモジュールは境界を越えた後の値を受け取り、境界の道具（クライアント・パーサ・`process.env`）はそのモジュールだけが触る
- 境界を越えて入る値は、越えた場所で検証し、検証済みの型で内側へ渡す。
  内側の型は検証（スキーマ・ブランド型）から導き、同じ形を二重に定義しない
- 環境変数は、その値を使う層のエントリポイントで読む。
  env から値への写像と既定値は純関数が持ち、テストはその純関数に env を模した値を渡す
- 純粋な計算はそれだけのモジュールへ置き、テストを付けてから配線する
- 配線（UI・アクション・スクリプトの main）は、入力の受け取り・関数の呼び出し・出力の三つだけを持つ。
  判断は、テストから直に呼べる関数へ置く
- 呼び出し側は、解決済みの値（設定・依存する実装）を引数で受け取る。
  分岐は解決する側が一度だけ持つ
- 各モジュールが import してよい相手の表は `layers.md` が持ち、境界の禁止則はそこへ書く

## 失敗の形
- 「無い」は言語の既定の欠損値か空コレクションで返し、異常は例外で表す。
  正常系の欠損の表し方と異常の表し方は、リポジトリの中でそれぞれ一つに揃える
- catch した例外は、再送出するか、文脈を付けて throw し直す。
  log だけ出して続行する形は握りつぶしである
- エラーは発生源の近くで、文脈（対象の識別子と値）を付けて扱う。
  設定の欠落を告げるエラーには、直し方（変数名と、書き方が載る文書の節）まで書く
- 検証を通った値は、検証した関数だけが作れる型で表す。
  呼び忘れは規律でなく型検査に止めさせる

## 値域と網羅
- 値域は一箇所の並びから型を導く。
  既定値を書く側が名指すなら、並びでなくキー付きのオブジェクトで持つ
- 値域ごとの表は、値域の型を鍵にした網羅的な対応表で持つ。
  値を足したときに型検査で止まる形にする
- 識別子は値として渡す。
  文字列（見出し・パス・ラベル）を解析して復元する形は、文字列を変えた回に黙って壊れる
- 関連する定数は一つのオブジェクトにまとめ、区別は名前の接尾辞でなくキーで表す

## コメント
- コードで表現できることはコードで表す。
  コメントが持つのは 1 行目の what と、その下の制約・失敗の形・理由
- 理由は、呼び手が実際にやりそうな誤用を一つ止めるものだけ書く。
  1 関数につき 2 文まで。
  採らなかった案・設計上の選択・過去の実害は ADR へのリンク一行にまとめる。
  理由を本文に書いた文はその文だけで閉じる（ADR や issue の番号を出典として添える形は、読み手を ADR へ送るだけで理由を持たない）。
  ADR を指す一行は「理由は X」「経緯は X」の形にする（「X 決定 3」のように節を指すと、規則の置き場として指すことになる）
- 同じ事実は一箇所にだけ書く。
  複数ファイルが共有する契約（URL の書式・環境変数の名前）は持ち主の一箇所に書き、他所は「書式は X が正」の一行にする
- コメントで補う前に、名前と構造を直せないか先に問う。
  読みにくいコードへ説明を足して済ませるのは、負債の言い換えであって返済ではない
- 読者は、このリポジトリの md を読んでいないエンジニア。
  その読者が辞書も設計文書も引かずに一つの意味へ読める語で書く。
  判定は英語への直訳で、一語が二つ以上の英語に割れる語（落とす = throw / drop / reject）は比喩である
- 動作は技術用語で言う（取得する・返す・throw する・削除する・拒否する・適用する・デプロイする）
- 物は識別子で名指しする。
  関数・変数・環境変数・テーブル・ファイルはその名をバッククォートで書く。
  主体は名前で書く（「規約の側が決める」でなく「`RULES.md` が決める」）
- 語の一覧は `writing.md`「語彙と読み手」節が持ち、`web/scripts/lint-comments.ts` の `comments/noBannedWord` が検出する。
  語はリポジトリごとに変わるので、核はこの一覧を持たない
- 主語・目的語・失敗の形を毎回書く。
  「未設定なら落とす」でなく「`TOIITO_SINGLE_USER_EMAIL` が未設定なら throw する」。
  指示語（ここ・そちら・こちら・向こう）は名前に置き換える
- モジュール／ファイル冒頭には、そこが何に責任を持ち、何に持たないかを書く。
  判定は、初めて開いた人が中身を読む前に「探しているものがここにあるか」を決められるか（ファイル名の言い換え・中の関数の目次・「〜を管理する」だけの一行は、この判定に落ちる）
- 語順・`——`・改行・1 行 1 文の四規律は `writing.md`「文章の四規律」がコメントにもそのまま当たる
- 削除テスト（「これを知らずに触った人は何を間違えるか」）はレビュアーが使う。
  書き手はどの行にも誤りを一つ作れるので、書く側は上の上限と読者の定義で止める
- いま成立している制約・前提・単位だけを書く。
  過去（経緯・不採用案）は ADR、未来（移行予定）は issue。
  経緯が今も効くなら、出来事でなく現在の禁止則として書く。
  実測は値だけを書く（日付・回数・確かめたという事実は経緯）。
  実害からは、その実害が要求する現在の制約だけを残す（出所の issue 番号は経緯）

## 余白と密度
- 論理ブロックごとに空行を入れる（PEP 8 の vertical whitespace 規約に準拠。言語を問わず適用）。
  縦の余白は削れる無駄ではなく、思考の切れ目を示す構文の一部
- 「短く詰める」方向の最適化を既定で疑う。
  行数の節約は可読性と交換できない
- 密度を上げる書き換え（三項演算子や内包表記の多重ネスト、中間変数の省略、1 行への複数文の詰め込み）は、書き手には短く、読み手には遅い
- 指標は書き手のトークン数ではなく、初見の人間が一度で読み下せるか

## テスト
- 実装ではなく振る舞いをテストする。
  テストしにくさは設計の悪臭
- 1 テスト 1 観点。
  テストコードも本体と同じ可読性規約に従う
- テスト名は、前提と観測できる結果を一文で書く。
  実装の関数名を並べた名前は、何が保証されたかを語らない
- 検査器（リンタ・スキーマ・スモーク）のテストは、通る例と落ちる例を対で持つ。
  落ちる例が無い検査器は、壊れても緑のまま通る
- 永続化を伴う振る舞いは、返り値でなく、読み直した状態で検証する。
  返り値だけを見ると、永続化の失敗が緑のまま通る
- 人手で書くデータファイルは、スキーマに通す検査をテストに持つ。
  型検査はデータファイルを見ない
- 文書が持つ契約（プロンプトの節の有無など）もテストで固定する

## 全体
- YAGNI: 推測で汎用化しない。
  抽象は 2〜3 例目が現れてから抽出する
- DRY は「知識」の重複にのみ適用する。
  偶然似ているだけのコードは別々のまま置く
- ボーイスカウトルール: 触れたコードは触れる前より少し良くして返す

- （このプロジェクトで決めた逸脱・追加をここに追記する。理由を一行添える。文章側の逸脱は `writing.md` の同欄）
- 製品の比喩語（`docs/VISION.md`「語彙」・`docs/DESIGN.md`「語彙」）は UI の文言と md に閉じ、コードのコメントでは技術の語で言う。
  コメントの読者は `docs/` を読んでいないエンジニアで、比喩の辞書を持たない
