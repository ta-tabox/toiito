# コーディング規約（核）

Clean Code / リーダブルコード / 良いコード悪いコードの交差点の蒸留。
上の `paths` に当たるファイルを Read した時点で読み込まれる。
コードに触らないセッションでは読み込まれないので、コードの外でも効く規律（文章・コミットの粒度）は `writing.md` が持つ。
判断に迷う具体例は skill `coding-standards` が持つ（**コードを書く前に開く**。実装・レビュー・リファクタ・設計判断のすべてが対象）。
言語固有の作法は `languages/<lang>.md` が持ち、該当言語のファイルを Read した時点で読み込まれる。
ここには常時必要な原則だけを置く。

## 命名
- 名前は意図を語る。
  読み手が中身を推測せずに済む名前。
  誤解されない名前 > 短い名前
- 情報量はスコープに比例させる。
  ループ変数は `i` でよく、公開 API は冗長でよい
- 名前に嘘をつかせない。
  挙動が変わったら改名もセットで行う
- 同じ対象に二つの名前を与えない。
  派生に別語を当てると、読み手は概念が二つあると読む（`cuts` を並べただけのものを `points` と呼ばない）

## 関数・メソッド
- 小さく、一つのことを。
  説明に「〜して、〜する」が要るなら分割候補
- 抽象度を揃える。
  高レベルの流れと低レベルの操作を同一関数に混在させない
- 引数は少なく（3つ以上で構造化を検討）。
  フラグ引数は関数分割の合図
- 隠れた副作用を持たせない。
  副作用があるなら名前で告知する

## 制御流
- ガード節・早期 return でネストを浅く。
  else を減らす
- 条件式は肯定形・単純に。
  複雑な条件は説明変数か関数へ抽出

## 状態・データ
- 不変を既定にする。
  可変は必要な場所へ最小スコープで
- 生成時に完全な状態を保証する（完全コンストラクタ）。
  不正な状態を表現不能にする
- データと、それを扱うロジックを引き裂かない。
  あるデータのバリデーション・計算が外部（Manager / Service 等）に散っていたら、データを持つ側へ寄せる（Data Class 臭）。
  ※ 構文の話ではない。
  `@dataclass` 等は不変な値オブジェクトの手段としてむしろ推奨。
  ロジックを持たない運搬役が正しい境界の DTO は例外

## エラー
- 例外を握りつぶさない。
  null を返さない・渡さない（空コレクション / Optional / 例外で代替）
- エラーは発生源の近くで、文脈を付けて扱う

## コメント
- コードで表現できることはコードで。
  コメントが持つのは 1 行目の what と、その下の制約・失敗の形・理由
- 理由は、呼び手が実際にやりそうな誤用を一つ止めるものだけ書く。
  1 関数につき 2 文まで。
  採らなかった案・設計上の選択・過去の実害は ADR へのリンク一行に畳み、本文で再説明しない
- 同じ事実は一箇所にだけ書く。
  複数ファイルが共有する契約（URL の書式・環境変数の名前）は持ち主の一箇所に書き、他所は「書式は X が正」の一行にする
- コメントで補う前に、名前と構造を直せないか先に問う。
  読みにくいコードへ説明を足して済ませるのは、負債の言い換えであって返済ではない
- 読者は、このリポジトリの md を読んでいないエンジニア。
  その読者が辞書も設計文書も引かずに一つの意味へ読める語だけを使う。
  判定は英語への直訳で、一語が二つ以上の英語に割れる語（落とす = throw / drop / reject）は使わない
- 動作は技術用語で言う（取得する・返す・throw する・削除する・拒否する・適用する・デプロイする）。
  引く・落とす・倒す・畳む・流す・弾く・握る・掛ける は使わない
- 物は識別子で名指しする。
  関数・変数・環境変数・テーブル・ファイルはその名をバッククォートで書き、言い換えない。
  口・関門・印・登録簿・受け皿・素通し・領分・側・器・綴り は使わない（`docs/adr/0014-local-vocabulary-split.md`）
- 製品の比喩語（`VISION.md`「語彙」・`DESIGN.md`）は UI の文言と md に閉じる。
  コードのコメントでは技術の語で言い、参照は文書名と節名の一行に留める
- 主語・目的語・失敗の形を省かない。
  「未設定なら落とす」でなく「`TOIITO_SINGLE_USER_EMAIL` が未設定なら throw する」。
  指示語（ここ・そちら・こちら・向こう）は名前に置き換える
- モジュール／ファイル冒頭には、そこが何に責任を持ち、何に持たないかを書く。
  ファイル名の言い換え・中の関数の目次・「〜を管理する」だけの一行にしない。
  3〜8 行に収め、超えたらコメントを削るのでなくモジュールを割る
- 語順・`——`・改行・1 行 1 文の四規律と、箇条・例示の行の緩和条項は `writing.md`「文章の四規律」がコメントにもそのまま当たる
- 削除テスト（「これを知らずに触った人は何を間違えるか」）はレビュアーが使う。
  書き手はどの行にも誤りを一つ作れるので、書く側は上の上限と読者の定義で止める
- いま成立している制約・前提・単位だけを書く。
  過去（経緯・不採用案）は ADR、未来（移行予定）は issue。
  経緯が今も効くなら、出来事でなく現在の禁止則へ畳む

## 余白と密度
- 論理ブロックごとに空行を入れる（PEP 8 の vertical whitespace 規約に準拠。言語を問わず適用）。
  縦の余白は削れる無駄ではなく、思考の切れ目を示す構文の一部
- 「短く詰める」方向の最適化を既定で疑う。
  行数の節約は可読性と交換できない
- 密度を上げる書き換え——三項演算子や内包表記の多重ネスト、中間変数の省略、1 行への複数文の詰め込み——は、書き手には短く、読み手には遅い
- 指標は書き手のトークン数ではなく、初見の人間が一度で読み下せるか

## テスト
- 実装ではなく振る舞いをテストする。
  テストしにくさは設計の悪臭
- 1 テスト 1 観点。
  テストコードも本体と同じ可読性規約に従う

## 全体
- YAGNI: 推測で汎用化しない。
  抽象は 2〜3 例目が現れてから抽出する
- DRY は「知識」の重複にのみ適用。
  偶然似ているだけのコードは統合しない
- ボーイスカウトルール: 触れたコードは触れる前より少し良くして返す
