# コーディング規約（核）

上の `paths` に当たるファイルを Read した時点で読み込まれる。
文章の規律は `writing.md`、判断の例は skill `coding-standards`、言語の作法は `languages/<lang>.md`、このリポジトリのモジュールと依存の向きの表は `layers.md` が持つ。
規則は「〜する」の形で書き、禁じる形で残すのは走査して拾わせたい禁止則だけにする。
`.claude/rules/` へ規則を足すのは、レビューで二度拾われた型で、判定と直し方が書けるときにする。
規則を消すのは、機械の検査が同じ規則を見るようになったときか、半年のあいだレビューにも検査にも実例が無いときにする。
機械が見ている規則の表は `languages/<lang>.md`「機械が見ている分」が持ち、表に載せた規則は散文から消す。
散文の射程が機械より広い（別の言語・md・コミット本文にも当たる）規則は、散文に残す。

## 命名
- 名前は意図を語る
  読み手が中身を推測せずに済む名前にし、短さより誤解されないことを優先する
- 情報量はスコープに比例させる
  ループ変数は `i` でよく、公開 API は冗長でよい
- 挙動が変わったら改名もセットで行う
  名前が挙動を言い当てている状態を保つ
- 同じ対象には一つの名前を与える
  派生に別語を当てると、読み手は概念が二つあると読む（`cuts` を並べただけのものを `points` と呼ばない）
- 動詞の接頭辞は skill `coding-standards`「命名の判断基準」の表から選び、同じ意味には同じ動詞を使う
- 名前は、その物が保持するもの・行うことを、辞書にある一般語で言う
  名前の読者は設計文書を読んでいないエンジニアで、名前から保持するものを読み取れないと中身を開くことになるので、製品の比喩語・実装に使ったライブラリの API 名・DOM のタグ名は名前に入れない（比喩の `nursery` でなく保持するものの `drafts`、地図を動かす操作は `flyTo` でなく `pan`、見出しの props は `h2` でなく `heading`）

## 関数・メソッド
- 小さく、一つのことをする関数にする
  説明に「〜して、〜する」が要るなら分割候補
- 抽象度を揃える
  高レベルの流れと低レベルの操作は別の関数に分ける
- 引数は少なく（3つ以上で構造化を検討）
  フラグ引数は関数分割の合図
- 副作用があるなら名前で告知する

## 制御流
- ガード節・早期 return でネストを浅く保ち、else を減らす
- 条件式は肯定形で単純に書く
  複雑な条件は説明変数か関数へ抽出する

## 状態・データ
- 不変を既定にする
  可変は必要な場所へ最小スコープで置く
- 生成時に完全な状態を保証する（完全コンストラクタ）
  不正な状態を表現不能にする
- データと、それを扱うロジックを同じ場所に置く
  あるデータのバリデーション・計算が外部（Manager / Service 等）に散っていたら、データを持つ側へ寄せる（Data Class 臭）
  構文の話ではない
  `@dataclass` 等は不変な値オブジェクトの手段としてむしろ推奨で、ロジックを持たない運搬役が正しい境界の DTO は例外
- 一つしか無い状態の正は一箇所に決める（URL・store・親の props のどれか一つ）
  同じ状態を二箇所に複製すると、同期が state の突き合わせになる

## 置き場と依存の向き
- 外部との境界（DB・ネットワーク・ファイル・DOM・環境変数）は、それぞれ一つのモジュールに閉じる
  他のモジュールは境界を越えた後の値を受け取り、境界の道具（クライアント・パーサ・`process.env`）はそのモジュールだけが触る
- 境界を越えて入る値は、越えた場所で検証し、検証済みの型で内側へ渡す
  内側の型は検証（スキーマ・ブランド型）から導き、同じ形を二重に定義しない
- 環境変数は、その値を使う層のエントリポイントで読む
  env から値への写像と既定値は純関数が持ち、テストはその純関数に env を模した値を渡す
- 純粋な計算はそれだけのモジュールへ置き、テストを付けてから配線する
- 配線（UI・アクション・スクリプトの main）は、入力の受け取り・関数の呼び出し・出力の三つだけを持つ
  判断は、テストから直に呼べる関数へ置く
- 呼び出し側は、解決済みの値（設定・依存する実装）を引数で受け取る
  分岐は解決する側が一度だけ持つ
- 各モジュールが import してよい相手の表は `layers.md` が持ち、境界の禁止則はそこへ書く
- 配線ごとに書いた前置きは、配線を足した回に抜けても検査で止まらないので、すべての配線が同じ前置き（認証・所有者の検査・入力の検証）を持つなら共通の入口（ラッパー・ミドルウェア）の一箇所に寄せる

## 失敗の形
- 「無い」は言語の既定の欠損値か空コレクションで返し、異常は例外で表す
  正常系の欠損の表し方と異常の表し方は、リポジトリの中でそれぞれ一つに揃える
- catch した例外は、再送出するか、文脈を付けて throw し直す
  log だけ出して続行する形は握りつぶしである
- エラーは発生源の近くで、文脈（対象の識別子と値）を付けて扱う
  設定の欠落を告げるエラーには、直し方（変数名と、書き方が載る文書の節）まで書く
- 検証を通った値は、検証した関数だけが作れる型で表す
  呼び忘れは規律でなく型検査に止めさせる

## 取りうる値と網羅
- 取りうる値は一箇所の並びから型を導く
  既定値を書く側が名指すなら、並びでなくキー付きのオブジェクトで持つ
- 取りうる値ごとの表は、その値の型を鍵にした網羅的な対応表で持つ
  値を足したときに型検査で止まる形にする
- 識別子は値として渡す
  文字列（見出し・パス・ラベル）を解析して復元する形は、文字列を変えた回に黙って壊れる
- 関連する定数は一つのオブジェクトにまとめ、区別は名前の接尾辞でなくキーで表す
- 同じ形の値（URL・パス・DOM の id・テストの台詞・設定の項目）は、二つ目が現れた時点で持ち主のモジュールを一つ作り、キー付きのオブジェクトで持つ
  文字列リテラルの散在と、`FIRST`・`SECOND` のような接尾辞で並べた定数の列は、その合図
  YAGNI が待たせるのは関数の汎用化であって、同じ形の値の置き場ではない

## コメント
- コードで表現できることはコードで表す
  コメントが持つのは 1 行目の what と、その下の制約・失敗の形・理由
- 理由は、呼び手が実際にやりそうな誤用を一つ止めるものだけ、1 関数につき 2 文まで書く
  採らなかった案・設計上の選択・過去の実害はコミットの本文に書き、ADR の規約（`docs/adr/README.md`）に当たる決定なら ADR に書いて、コメントには「理由は X」「経緯は X」の一行だけを置く
  現況を述べた文の末尾へ ADR や issue の番号を出典として添える形は、読み手を送るだけで理由を持たない
- 同じ事実は一箇所にだけ書く
  複数ファイルが共有する契約（URL の書式・環境変数の名前）は持ち主の一箇所に書き、他所は「書式は X が正」の一行にする
- コメントで補う前に、名前と構造を直せないか先に問う
  読みにくいコードへ説明を足して済ませるのは、負債の言い換えであって返済ではない
- モジュール／ファイル冒頭には、そこが何に責任を持ち、何に持たないかを書く
  判定は、初めて開いた人が中身を読む前に「探しているものがここにあるか」を決められるか（ファイル名の言い換え・中の関数の目次・「〜を管理する」だけの一行は、この判定に落ちる）
  そのモジュールの内側に閉じた設計の選択（式の形・状態の置き場・値の根拠）は、冒頭に 5 文まで書く
  責務を抽象の語だけで書くと動作が思い浮かばないときは、具体例一つで入力から結果までを示す
- 文は一般語で何をするかを先に言い、識別子は括弧で添える
  識別子だけで組んだ文は、名前の意味を知らない読み手にはコードの読み直しになる
- 並び順・不変条件などの保証を書くときは、何のための保証かを同じ文か次の文に添える
  保証が効く先が書かれていないと、読み手はその保証を残すか消すかを判じられない
- 関数名と 1 行目から何のために呼ぶかが読めない関数には、呼ぶ目的を一文添える
  目的は呼び出し元の一覧と別物で、「ファイルの場所・import 文・`layers.md` が既に語ること」の項に当たらない
- 関数の本体を別の書き方に置き換えたとき直すことになる文は、役割でなく実装を書いているので、コメントは中の実装を書き換えても役割が変わらない限り書き換えずに済む抽象度で書く
  実装から数えた数（分岐・失敗の経路・書き込む行の数）と手順の列挙は、書き換えのたびに古くなるので書かない
- 読者は、このリポジトリの md を読んでいないエンジニアなので、物を指す名詞はコード中の識別子（バッククォート）か辞書にある一般語、動作は技術用語（取得する・返す・throw する・削除する・拒否する）で書く
  主語・目的語・失敗の形（throw・undefined・空配列）を毎回書き、書き手がその場で付けた呼び名と指示語（ここ・そちら・向こう）は識別子に置き換える（「未設定なら失敗する」でなく「`APP_ADMIN_EMAIL` が未設定なら throw する」）
  比喩の判定と禁止語の表は `writing.md`「語彙と読み手」が持つ
- ファイルの場所・import 文・`layers.md` が既に語ること（呼び出し元の一覧・import しない相手・親要素の中での位置・置いていないファイルの断り）は、読み手が同じ画面で見ているので書かない
- いま成立している制約・前提・単位だけを書く
  過去（経緯・不採用案）はコミットの本文か ADR、未来（移行予定）は issue、実測は値だけ（日付・回数・確かめた事実は経緯）
- 削除テスト（「これを知らずに触った人は何を間違えるか」）はレビュアーが使う
  書き手はどの行にも誤りを一つ作れるので、書く側は上の上限と読者の定義で止める

## 余白と密度
- 論理ブロックごとに空行を入れる（PEP 8 の vertical whitespace 規約に準拠。言語を問わず適用）
  縦の余白は削れる無駄ではなく、思考の切れ目を示す構文の一部
- 「短く詰める」方向の最適化を既定で疑う
  行数の節約は可読性と交換できない
- 密度を上げる書き換え（三項演算子や内包表記の多重ネスト、中間変数の省略、1 行への複数文の詰め込み）は、書き手には短く、読み手には遅い
- 指標は書き手のトークン数ではなく、初見の人間が一度で読み下せるか

## テスト
- 実装ではなく振る舞いをテストする
  テストしにくさは設計の悪臭
- 1 テスト 1 観点
  テストコードも本体と同じ可読性規約に従う
- テスト名は、前提と観測できる結果を一文で書く
  実装の関数名を並べた名前は、何が保証されたかを語らない
- 検査器（リンタ・スキーマ・スモーク）のテストは、通る例と落ちる例を対で持つ
  落ちる例が無い検査器は、壊れても緑のまま通る
- 永続化を伴う振る舞いは、返り値でなく、読み直した状態で検証する
  返り値だけを見ると、永続化の失敗が緑のまま通る
- 人手で書くデータファイルは、スキーマに通す検査をテストに持つ
  型検査はデータファイルを見ない
- 文書が持つ契約（プロンプトの節の有無など）もテストで固定する

## 全体
- YAGNI: 推測で汎用化しない
  抽象は 2〜3 例目が現れてから抽出する
- DRY は「知識」の重複にのみ適用する
  偶然似ているだけのコードは別々のまま置く
- ボーイスカウトルール: 触れたコードは触れる前より少し良くして返す
