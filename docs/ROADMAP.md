# ROADMAP — 作る順序と横断規約

上位文書: VISION.md（なぜ）> ARCHITECTURE.md（どう）> DESIGN.md（どう見えるか）> HARNESS.md（検証）> 本文書（順序）。
矛盾したら上位が勝つ。

## この文書の分担

| 層 | 置き場 | 持つもの |
|---|---|---|
| 地図 | **本文書** | 横断規約・依存グラフ・順序の理由 |
| 見た目（規範） | `.claude/rules/design.md` | 原則・語彙・彩度の規律・残す摩擦の線引き・やらないこと |
| 見た目（値） | `DESIGN.md` | 色のトークン・書体と字組み・余白・状態の見せ方・部品の型 |
| 実行単位 | **GitHub Issues** | 目的 / 作るもの / 触らないもの / 完了条件 / 参照文書 |
| 経緯 | `adr/` | なぜそう決めたか。1決定1レコード・追記のみ・覆すときは supersede |

**状態（着手中・完了）の正は issue 側**。
本文書はステップの ✅ を持たない—— 複数マシンから同じ markdown の状態を触ると、意味のない衝突を量産するため。
本文書が変わるのは順序か規約が変わったときだけ。
閉じた issue は依存グラフと表から消し、その順序に効いていた理由も消す（経緯は git の履歴が持つ）。

## 進め方の横断規約（全 issue 共通）

- 心拍: 変更 → `web/` で `pnpm check` → 緑ならコミット。**赤のままコミットしない**
- 作る順: **lib 関数 + テスト → UI 配線**（`.claude/rules/coding.md`「置き場と依存の向き」）
- AI を伴う動作確認は `TOIITO_FAKE_AI=1`。実 API は自動テストで叩かない
- 1 issue = 1 セッション = 1 PR。PR 本文に `closes #N`。CI 緑 + マージで閉じる
- コミット規約・署名は `CLAUDE.md` の git 節が正（prefix は変更の型、author は人間名義）

## 完了条件の判定を二本に分ける

各 issue は二つの節を持つ:

- **完了条件（機械判定）** — `pnpm check` 緑・特定のテストが通る、など。
  これを満たせば issue は閉じてよい
- **人間の判定（別トラック）** — 実機の手触り、L5 の官能。
  **close を妨げない**。
  滞留したら独立の issue を立てる

一つのチケットに両方の判定を載せると、誰も閉じられない単位ができる。

ここに書くのは、依存と「同じファイルを取り合う」という横断の事実だけである。

## 順序の理由

**#8（発話周期）は観測手段が先**。
「掘りすぎ」の適切さは L5 でしか測れないので、メモに溜まった違和感を逆引きできるようになってから調律する（ARCHITECTURE「破られたら人間が観察できることが検知機構を兼ねる」の実体化）。

**#64（ペルソナ）と #8 は隣接するが順序を持たない**。
#8 が決めるのは誰がいつ喋るかで、#64 が決めるのは設定をどこに持つかである。

**#219（プロンプトの区切り）は #64 の前**。
#64 が `web/src/personas/*.md` を既定のペルソナの初期レコードへ移すので、その文面を直す #219 が先なら移す作業が一回で済む。

**#75（ペルソナの記憶）は #64 の後**。
記憶はペルソナ ID に紐づくので、ID を選べる形が先に要る。

**#197（対話まわりを dialogue/ へ）は #64 の後**。
`personas.ts` は #64 が書き換えるファイルなので、先に移すと #64 の差分が移動と書き換えの混ざったものになる。

**#210（オフセット換算を lib へ）は #197 と同じ回か後**。
#210 が lib へ移す関数の置き場は、#197 が決めるディレクトリの形に合わせる。

**#69 / #70 / #133 は互いに独立**。
どれもユーザーが居ないと意味を持たず、ログインが済んだので着手できる。
#133 だけは着手を要求が出てからにする。
`magic link` と `email OTP` はメール送信基盤を新たな依存として増やし、`anonymous` は招待制と構造的に両立しないので、どれを採るかは要求が出た回に方式から決める（経緯は `adr/0018-invite-only-multi-user.md`）。

**#150（外周の守り）は独立**。
ヘッダ・レート制限・依存の監視・秘密の回転は、他の issue の実装の形を変えない。

**培地（#63）と派生問い（#62）は要求が出てから**。
どちらも出所は `extensions/` の構想で、材料が溜まる前に置き場だけ作っても、効いたかどうかを測れない。

**`message-body.tsx` を触る issue は一列に並べる**。
メモの選択・下線・入力欄はこの一枚に集まるので、同じ一枚を触る issue を並行させると同じ行で衝突する。
