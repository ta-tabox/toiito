# ROADMAP — 作る順序と横断規約

上位文書: VISION.md（なぜ）> ARCHITECTURE.md（どう）> DESIGN.md（どう見えるか）> HARNESS.md（検証）> 本文書（順序）。
矛盾したら上位が勝つ。

## この文書の分担

| 層 | 置き場 | 持つもの |
|---|---|---|
| 地図 | **本文書** | 横断規約・依存グラフ・順序の理由 |
| 見た目（規範） | `.claude/rules/design.md` | 原則・語彙・彩度の規律・残す摩擦の線引き・やらないこと |
| 見た目（値） | `DESIGN.md` | 色のトークン・書体と字組み・余白・状態の見せ方・部品の型 |
| 実行単位 | **GitHub Issues** | 目的 / 作るもの / 触らないもの / 完了条件 / 参照文書 |
| 経緯 | `adr/` | なぜそう決めたか。1決定1レコード・追記のみ・覆すときは supersede |

**状態（着手中・完了）の正は issue 側**。
本文書はステップの ✅ を持たない—— 複数マシンから同じ markdown の状態を触ると、意味のない衝突を量産するため。
本文書が変わるのは順序か規約が変わったときだけ。
閉じた issue は依存グラフと表から消し、その順序に効いていた理由も消す（経緯は git の履歴が持つ）。

## 進め方の横断規約（全 issue 共通）

- 心拍: 変更 → `web/` で `pnpm check` → 緑ならコミット。**赤のままコミットしない**
- 作る順: **lib 関数 + テスト → UI 配線**（`.claude/rules/coding.md`「置き場と依存の向き」）
- AI を伴う動作確認は `TOIITO_FAKE_AI=1`。実 API は自動テストで叩かない
- 1 セッション = 1 スタック
  前の issue に依存する一連の issue を一つの PR にまとめるとレビューの単位がすべての issue の差分になるので、一連の issue は 1 issue 1 PR で積み、各 PR のベースを一つ下の段のブランチにして GitHub のスタックへ入れる
  他の issue に依存しない複数の issue は 1 PR にまとめてよく、PR 本文に issue ごとの `closes #N` を並べる
  スタックへ PR を足すのは `gh stack` で、`gh stack` を使えないセッションでは PR を作った後に人間が PR のヘッダの「Add to stack」で足す
  下の段へコミットを足したら上の段を `gh stack` で積み直し、`gh stack` を使えないセッションでは rebase して `--force-with-lease` で push する
  上の段でマージを押すと下の未マージの段がまとめて main へ入り、段ごとの本番デプロイと migration が分かれなくなるので、マージを押すのはスタックの最下段にある未マージの PR だけにし、一つずつ人間が判断する
  マージの後の残りの段の rebase とベースの付け替えは GitHub が行うので、手元のブランチは作業を続ける前にリモートから取得し直す
  CI 緑 + main へのマージで閉じる（`closes #N` は main へマージされたときにだけ効く）
- コミット規約・署名は `CLAUDE.md` の git 節が正（prefix は変更の型、author は人間名義）

## 完了条件の判定を二本に分ける

各 issue は二つの節を持つ:

- **完了条件（機械判定）** — `pnpm check` 緑・特定のテストが通る、など
  これを満たせば issue は閉じてよい
- **人間の判定（別トラック）** — 実機の手触り、L5 の官能
  **close を妨げない**
  滞留したら独立の issue を立てる

一つのチケットに両方の判定を載せると、誰も閉じられない単位ができる。

## 順序の理由

**段 1（PR が開いている issue）は `post-mvp` でも最初に置く**。
開いたままの PR は main が進むたびに rebase が要り、`web/src/lib/db.ts` と migration を書き換える PR が残るあいだは、同じファイルを触る段 4 に着手できない。

**段 1 の中では、migration を足す PR を 1 本ずつマージする**。
main へのマージは本番の migration を起こすので、二本を続けて入れると、失敗した migration がどちらの PR のものかを切り分けられない。
スタックの中の順は、各 PR のベースが決める。

**#240（言い直しの履歴）は、段 1 の migration の後に実装する**。
#240 は PR を持たないので、migration のファイルを段 1 のマージの後に作れば、段 1 の PR の migration を作り直さずに済む。

**段 2（読み手に見せる・Claude だけで閉じる）は段 1 と並行させる**。
#356 は `README.md` と画像だけを、#360・#362・#363 は段 1 の PR が触らない関数と CI の設定だけを触る。

**段 3（#205・#358）は段 2 の後**。
#205 の判定結果と #358 の決定は読み手に見せる材料になるので、見せる入口（#356）が先に要る。

**#359（消去と書き出し）は #244 と #240 の後**。
三件とも migration を足し、#359 はメモと言い直しの履歴の表を消去の対象に含める。
#240 を段 4 に置くのは #359 の前提だからで、#240 の画面の配線（#241・#242）は提出の後に置く。

**#366（db.ts の分割）は段 1 の PR がすべて入った後**。
段 1 の PR はどれも `web/src/lib/db.ts` を書き換えるので、先に分割すると、開いている PR の差分がすべて衝突する。

**#197（dialogue/ へ）と #366 は並行させない**。
どちらも呼び出し側の同じ import の行を書き換える。

**#365（アクセシビリティ）は #363（E2E を CI で実行）の後**。
足す spec を PR ごとに実行する場所が先に要る。

**#133（捨てアカウント枠）は、読み手に継続して使わせる要求が出てから**。
サインインしない読み手には #357 がゲストのサインインを選んだので、#133 は Google を持たない相手を招待する要求が出た回に方式から決める（理由は `adr/20261112-invite-only-multi-user.md`）。

**#368（ゲストのデータ層）と #359（消去と書き出し）は並行させない**。
どちらも `web/src/lib/db.ts` に、利用者の持ち物を子の表から順に消す repo 関数を足す。

**#8（発話周期）は観測手段が先**。
「掘りすぎ」の適切さは L5 でしか測れないので、メモに溜まった違和感を逆引きできるようになってから調律する（ARCHITECTURE「破られたら人間が観察できることが検知機構を兼ねる」の実体化）。

**#64（ペルソナ）と #8 は隣接するが順序を持たない**。
#8 が決めるのは誰がいつ喋るかで、#64 が決めるのは設定をどこに持つかである。

**#75（ペルソナの記憶）は #64 の後**。
記憶はペルソナ ID に紐づくので、ID を選べる形が先に要る。

**#150（外周の守り）のうち、レート制限の他は独立**。
ヘッダ・依存の監視・秘密の回転は、他の issue の実装の形を変えない。

**派生問い（#62）は要求が出てから**。
出所は `extensions/` の構想で、材料が溜まる前に置き場だけ作っても、効いたかどうかを測れない。

**`message-body.tsx` を触る issue は一列に並べる**。
メモの選択・下線・入力欄はこの一枚に集まるので、同じ一枚を触る issue を並行させると同じ行で衝突する。
