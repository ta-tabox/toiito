# 0032. ペルソナをテーブルにし、当時の設定を発話が指す

- **状態**: 採用
- **決定日**: 2026-09-09
- **関係する ADR**: 0017, 0021, 0025, 0029, 0030, 0031

**0030 は supersede しない。**
`messages` に `user_id` を足さないので、0030 決定 2 は動かない（理由は「理由」節の「発話者」）。

## 文脈

`docs/ARCHITECTURE.md` は、ペルソナの可変化を次の二箇所で先送りしている。

| 節 | 記述 |
|---|---|
| 技術スタック（確定事項） | 固定ペルソナ二体。MVP は可変化しない（発酵後に再検討） |
| 二体 AI のオーケストレーション | 具体派（`ai_a`）と抽象派（`ai_b`）の固定二体 |

#64（二体のペルソナをセッション単位で設定できるようにする）が、発酵後の再検討にあたる。
固定二体では、問いの種類によらず同じ観点からしか問いを扱えない。
合成関数にパラメータを渡す案（`composePersona(id, params, custom?)`）は、ペルソナの数が二体に固定されたままになるので、2026-08-30 に採らないと決めた。

ペルソナをレコードにすると、決めることが四つ出る。
四つのうち二つは既存の ADR と重なる。

| 論点 | 重なる ADR | 重なり方 |
|---|---|---|
| 既定のペルソナを全員で共有するか、利用者ごとに複製するか | 0030 決定 1 | `persona` を二つ目の所有のルートと見込んでいるが、既定のペルソナの持ち主は決めていない |
| 編集できるペルソナで、過去の発話から当時の定義をどう復元するか | なし | |
| `Speaker` enum の `ai_a` / `ai_b` が消えた後、発話者をどう表すか | 0030 決定 2 | 発話者を「種別 + 参照先」に分けると `messages.user_id` を足す案が出るが、0030 は `sessions` / `messages` / `memos` に `user_id` を持たせないと決めている |
| 「思考: 具体 ↔ 抽象」のようなパラメータを、レコードの列にするか | なし | |

## 決定

### テーブルの形

1. **ペルソナを、同一性を持つ `persona` と設定の版を持つ `persona_config` の二段のテーブルにする。**
2. **`persona_config` は `(persona_id, version)` を一意にし、主キーは単一の `id` にする。**
3. **`persona_config` に `parent` を持たせない。**
   版は `persona_id` ごとの連番で、分岐を許さない。

| テーブル | 列（抜粋） | 持つもの |
|---|---|---|
| `persona` | `id`, `user_id` | 同一性。#75（ペルソナに、セッションを跨いだ記憶を持たせる）の記憶を紐づける先 |
| `persona_config` | `id`, `persona_id`, `version`, パラメータ, システムプロンプト | 設定の版。`@@unique([persona_id, version])` |
| `messages` | `speaker`, `persona_config_id` | 発話の時点の設定を指す |

### 既定のペルソナと利用者のペルソナ

4. **既定のペルソナは、システム所有のユーザー行が持つ。**
   ユーザー行の email は到達不能なアドレス（`system@toiito.invalid` の形）にし、`persona.user_id` は NOT NULL のままにする。
5. **利用者が既定のペルソナを編集した時点で、利用者所有の新しい `persona` を作り、編集後の設定をその版 1 にする。**

| ペルソナ | `persona.user_id` | 見える利用者 | 編集したとき |
|---|---|---|---|
| 既定 | システムのユーザー | 全員 | 利用者所有の新しい `persona` を作る |
| 利用者所有 | その利用者 | 本人だけ | 同じ `persona` に次の版の `persona_config` を足す |

repo 層は、`user_id` が現在のユーザーかシステムのユーザーである `persona` を返す。

### 発話者

6. **発話者は `speaker`（種別）と `persona_config_id`（参照先）で表し、`messages` に `user_id` を足さない。**
7. **`Speaker` enum は `human` / `ai` の 2 値にする。**

| `speaker` | `persona_config_id` | 発話者の辿り方 |
|---|---|---|
| `human` | NULL | `messages` → `sessions` → `questions.user_id` |
| `ai` | NOT NULL | `messages` → `persona_config` → `persona` |

`speaker` と `persona_config_id` の対応は Prisma スキーマで表明できないので、check 制約として migration の SQL に置く。

### パラメータとシステムプロンプト

8. **`persona_config` は、enum のパラメータと自由記述のシステムプロンプトの両方を持つ。**
9. **`web/src/personas/*.md` は、既定のペルソナの初期レコードの中身にする。**
   実行時にファイルを読む `loadPersona` は削除する。

| 欄 | 持ち方 | 前例 |
|---|---|---|
| パラメータ | `schema.prisma` の enum・TS の値域配列・絞り込み関数の三つ | `QuestionStatus`（`web/src/lib/question.ts` の `QUESTION_STATUSES` と `isQuestionStatus`） |
| システムプロンプト | 自由記述の文字列 | `web/src/personas/*.md` の現在の文面 |

## 理由

### テーブルの形

- **二段に分ける**: `messages` は immutable なので、編集できる定義を `persona_id` だけで指すと、過去の対話を読み返したときに当時の設定を復元できない。
- **同一性を別のテーブルに残す**: #75（ペルソナに、セッションを跨いだ記憶を持たせる）の記憶は、版をまたいで続く持ち主を要する。
- **問いの原型と同じ形にする**: `docs/ARCHITECTURE.md`「原型と現在の形」は原型を書き換えずに現在の形を別の列へ持つ形を採り、#57（再訪で過去セッションが読めなくなる。メモが指すセッションごと設計し直す）も過去を当時の姿で読めることを要求した。
- **主キーを単一の `id` にする**: `messages` からの外部キーが 1 列で済む。
- **`parent` を持たない**: 分岐を許さなければ版の前後は `version` の大小で分かり、`parent` を辿る再帰クエリも要らない。

採らなかった案。

- **`persona` に `version` 列を足し、1 枚のテーブルで `(persona_id, version)` を一意にする**: `messages` からの外部キーが 2 列になり、ADR 0030 が全テーブルへ `user_id` を持たせる案を退けた条件と同じ費用を負う。
- **`messages` に設定のスナップショットを持たせる**: 同じ設定が発話の数だけ複製され、ある設定で話した発話を設定から検索できなくなる。

### 既定のペルソナと利用者のペルソナ

- **システム所有のユーザー行を作る**: ADR 0030 決定 4（持ち主のいない行を作らない）が、二つ目の所有のルートである `persona` にも当たる。
- **email を到達不能なアドレスにする**: ログインは Google OAuth だけ（ADR 0029 決定 3）なので、実在しないアドレスのユーザーとしてログインする経路が無い。
- **ユーザー行を一行作る形には前例がある**: ADR 0031 決定 6 は、migration で既定のユーザーを一行作り、既存の問いをそのユーザーへ寄せた。
- **編集で新しい `persona` を作る**: 既定の `persona` の下に利用者の `persona_config` を足すと、`persona` に紐づく #75 の記憶が全利用者で一つに混ざる。
- **既定の改善が複製へ届かないことを受け入れる**: 届く形（全員が既定の 1 レコードを参照し続ける形）では利用者がペルソナを編集できず、#64 の「自分のものを作る」を満たせない。

採らなかった案。

- **`persona.user_id` を nullable にし、NULL をシステム所有と読む**: NULL が「持ち主がいない」と「入れ忘れ」を同じ値で表し、DB が入れ忘れを拒否できない。
- **`is_default` のような真偽値を別の列に置く**: 二つの列が同じ事実を表し、`is_default` が真なのに利用者の `user_id` を持つ行を作れる。
- **既定のペルソナをソースコード上の定義として持ち、利用者ごとに最初から複製する**（#64 の本文にあった案）: 編集していない利用者の分まで、同じ設定の行が利用者の数だけ増える。

### 発話者

- **`messages` に `user_id` を足さない**: 一つのセッションで話す人間は一人なので、人間の発話者は `sessions` → `questions.user_id` で一意に決まり、列を足しても新しい事実が入らない。
- **ADR 0030 決定 2 の条件が同じく当たる**: 発話者としての `user_id` も値の出所が親の行なので、0030 が退けた「親の `user_id` を書き込み経路の各所でコピーし、コピーし忘れがずれになる」形になる。
- **所有権の列と区別する手段が無い**: スキーマ上は所有権の `user_id` と同じ 1 列になり、「この列は所有権ではない」という約束を repo 層の規律だけで守ることになるので、機械が検査できない。
- **check 制約を migration の SQL に置く**: Prisma スキーマは列の間の対応を表明できず、`memos_anchor_range_check` も同じ置き場にある。

採らなかった案。

- **種別 + `persona_config_id` + `user_id`**（#64 の本文にあった案）: 所有権の列と同じ 1 列が `messages` に入り、ADR 0030 決定 2 を supersede することになる。

### パラメータとシステムプロンプト

- **パラメータを enum にする**: 当初案の「-2..2」の数値と違い、enum は値ごとに一つの文言の節を対応させられる（`web/src/personas/params/*.md` に節を置く案と一致する）。
- **`QuestionStatus` と同じ三つで持つ**: DB の enum と TS の値域がずれると `tsc` が失敗する。
- **値へ比喩を持ち込まない**: 比喩は選び直すことがあるが、enum の値の変更は本番の DB に migration を要する（ADR 0017）。
- **システムプロンプトを併せて持つ**: `docs/ARCHITECTURE.md`「二体 AI のオーケストレーション」が要求する材料の供給規律と手筋のカタログは、パラメータの値では表せない文章である。
- **`web/src/personas/*.md` を初期レコードの中身にする**: 既定のペルソナの設定の正はレコードに移るので、実行時にファイルを読む経路を残すと正が二つになる。

採らなかった案。

- **自由記述のシステムプロンプトだけを持つ**: 利用者が毎回ゼロから書くことになる。
- **パラメータを生成の材料に留め、生成した文面だけをレコードに残す**: 後からパラメータだけを変更できなくなる。

## 帰結

| 対象 | 変わること |
|---|---|
| `docs/ARCHITECTURE.md`「技術スタック（確定事項）」 | 「固定ペルソナ二体」の項を削除する |
| `docs/ARCHITECTURE.md`「二体 AI のオーケストレーション」 | 「固定二体」の記述が変わる |
| `docs/ARCHITECTURE.md`「データモデル」 | `persona` と `persona_config` が加わり、`messages.speaker` の値が変わる |
| ADR 0030 | 決定 1 が見込んだ二つ目の所有のルートが `persona` として実装される。決定 2〜5 は変わらない |
| ADR 0025 | 一往復の三行を同時に入れる不変条件は変わらない。入る行の列が増える |
| `web/src/lib/types.ts` | `Speaker` の値が変わる |
| `web/src/lib/personas.ts` | `PersonaId`・`PERSONA_LABEL`・`loadPersona` が変わる |
| `messages` の check 制約 | 一つ増える。実体は migration の SQL にだけある |
| `pnpm seed` | システムのユーザーと既定のペルソナの行を作る |
| `persona_config.version` の採番 | 同時に二つ作ると同じ番号を取りうる。unique 制約が重複を拒否するので、リトライが要る。単一利用者のうちは起きない |

## 覆る条件

| 起きたこと | 覆る決定 | 要るようになるもの |
|---|---|---|
| 一つのセッションに複数の人間が入る設計になる | 決定 6 | 人間の発話者を指す `messages.user_id` |
| ペルソナから別系統を派生させたくなる | 決定 3 | `persona_config.parent` |
| 既定のペルソナの改善を、既存の複製へ届けたくなる | 決定 5 | 既定の新しい版を複製へ適用する仕組み |
| パラメータの軸が増え、enum の組み合わせごとに文言を用意できなくなる | 決定 8 | パラメータから文面を生成する形 |
| 削除機能を入れる | 決定 1 | `persona` を削除したときに、`messages` が指す `persona_config` をどう扱うか（ADR 0030 の覆る条件と同じ問い） |

## この ADR が決めないこと

未決の論点は ADR にしない（規約 5）ので、次の五つは issue に残す。

| 論点 | 残す先 | 決めない理由 |
|---|---|---|
| `effort` を `persona_config` の列にするか | #64 | ADR 0021 が深さを Anthropic 固有の設定（`AnthropicSettings.effort`）と決めており、列にするとプロバイダ固有の値がレコードに入る。現在の値は `TOIITO_ANTHROPIC_EFFORT_CONCRETE` / `TOIITO_ANTHROPIC_EFFORT_ABSTRACT` にある |
| 既存の `messages` を削除するか、既定のペルソナの版へ寄せるか | #64 | #64 本文の「本番のレコードは作り直してよい」（2026-08-30）は本番が止まる前提の判断で、ADR 0030 の理由節と ADR 0031 決定 5 で本番が動き続けることになった |
| パラメータの軸と各軸の値域 | #64 | この ADR が決めたのは持ち方だけである |
| システムのユーザーと既定のペルソナの行を、migration と `pnpm seed` のどちらが作るか | #64 | 本番にも行が要るので、開発用の seed だけでは足りない |
| 一つのセッションに立てるペルソナの数と発話順 | #8（発話周期の可変化（具体／抽象のバランス）） | 発話周期は #8 の対象である |
