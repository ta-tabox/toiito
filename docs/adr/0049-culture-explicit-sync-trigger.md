# 0049. 培地の付与は利用者の明示の操作で始め、その場で待つ

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 0002, 0025, 0026, 0038, 0043, 0050

## 文脈

この ADR で培地は、問いに付随する材料（AI が対話の前に集める、外部の調査の結果など）を指す。
構想は `extensions/fermentation-and-outlets.md`「D. 培地（culture）」節が持ち、実装は #63（培地を整える）とその子 issue が持つ。

構想は付与を非同期に置き、利用者が見ていない間に材料が付く形を想定した。
一方で、誰が付与を始めるか（時間・再訪・明示の操作）は未決のまま残した。

0038 は、`new` の問いに培地が付いたときに機械が `status` を `stocked` へ上げると決めた。
付与を始める契機は、そのまま `stocked` へ上がる契機になる。

付与の形を縛る条件は次のとおりである。

| 条件 | 出典 |
|---|---|
| 本番の関数の実行時間には、変更できない上限がある | 0002 |
| アプリの定期実行（Cron Jobs）をアプリへ入れない | 0002 決定 2 |
| AI の呼び出しは、一回ごとに上限時間で打ち切る | 0025 |
| AI の応答をストリーミングで見せない | 0026 |
| 一回の付与は、AI が web 検索を行う呼び出しになる | 0050 |

決めるのは、付与を何で始めるかと、利用者が付与の完了を待つかどうかの二つである。

## 決定

1. **培地の付与は、利用者が対話画面で行う明示の操作だけで始める。**
   問いの投入・再訪・時間の経過では始めない。
2. **付与は、操作を受けたリクエストの中で完了させ、利用者はその完了を待つ。**
   応答を返した後に処理を続ける形も、付与中や失敗の状態を DB に持つ形も採らない。
3. **付与の待ちは、実行環境の上限時間より手前で打ち切る。**
   一回の付与で行う AI の呼び出しの上限時間と、検索の回数の上限と、出力の上限を、関数の実行時間の上限に収まる値として定数で持つ。
4. **付与が失敗したら培地の行を作らず、失敗をその操作の応答で利用者に伝える。**
   失敗を DB に残さない。
   再試行は、利用者が同じ操作をもう一度行うことである。

決定時点の例として、一回の呼び出しの上限時間は 120 秒で、Vercel Hobby の関数の上限は 300 秒である。
現況は `web/src/lib/ai/anthropic.ts` と `docs/DEPLOY.md` が持つ。

| 契機 | 採否 |
|---|---|
| 対話画面の明示の操作 | 採る |
| 問いの投入 | 採らない |
| 再訪 | 採らない |
| 時間の経過（定期実行） | 採らない |

## 理由

- **明示の操作で始める**: 付与のたびに web 検索の料金が加わる（0050）ので、利用者が材料を求めた問いにだけ費用をかける。
- **その場で待つ**: 一回の呼び出しが上限時間で打ち切られるので、付与は関数の上限の内側で終わり、実行環境に強制終了されない。
- **状態を DB に持たない**: 付与がリクエストの中で始まって終わるので、付与中の行が失敗のあとに残り続ける状態が生まれない。
- **待ちを残す**: `docs/DESIGN.md`「残す摩擦」は応答の待ちを残す側に置き、何が起きたか分からない沈黙だけを直す側に置く。
  付与中であることを操作した部品に出せば、待ちは残り沈黙は生まれない。
- **失敗を応答で伝える**: 行を作らないので `status` も動かず（0038）、同じ操作をもう一度行えば元の状態から付与をやり直せる。

採らなかった案と、それを採らなかった条件。

- **応答を返した後に処理を続ける（Next.js の `after`）**: 操作はすぐ戻る。
  `after` の処理もルートの実行時間の上限の内側で動くので、待てる長さは同期と変わらない。
  付与中と失敗を画面に出すには状態を持つ表と画面の読み直しが要るので採らなかった。
- **問いの投入で自動に始める**: 利用者の操作が要らない。
  捨てる問いにも検索の料金が生じ、投入を付与の完了まで待たせないために応答後の処理が前提になるので採らなかった。
- **再訪で自動に始める**: 戻った問いに新しい材料が付く。
  再訪のたびに料金が生じ、再訪の操作が付与の完了まで待つことになるので採らなかった。
- **定期実行で始める**: 利用者が見ていない間に材料が付き、構想の想定に一致する。
  アプリの定期実行は 0002 決定 2 の禁止則に当たり、外部のスケジューラから呼ぶ場合は利用者の操作を経ずに付与を始めるエンドポイントとその認証が新たに要るので採らなかった。
- **ストリーミングで付与の進みを見せる**: 検索の途中経過が見える。
  0026 がストリーミングを見送っており、この決定だけのために覆る条件を満たす根拠が無いので採らなかった。

## 帰結

| 対象 | 変わること |
|---|---|
| 対話画面 | 付与を始める操作と、付与中の表示と、失敗の知らせが加わる |
| 0038 | `stocked` へ上がるのは、利用者が付与を操作して行が入った問いだけになる。操作しない問いは、人間が 5 値を選ぶまで `new` のまま残る |
| 構想の想定 | 利用者が見ていない間に材料が付く形は、この決定の範囲では実現しない |
| 一回の付与の所要時間 | 計測していない。検索の回数と出力の上限を下げれば待ちは縮むが、材料が減る |
| 0025 | 一往復の手順とは別のリクエストで動くので、一往復の上限時間の見積もりは変わらない |

## 覆る条件

| 起きたこと | 覆る決定 | 要るようになるもの |
|---|---|---|
| 一回の付与の実測が、関数の実行時間の上限に近づく | 決定 2・3 | 応答後の処理と付与の状態の表、または実行環境の決め直し（0002 の覆る条件） |
| 利用者が見ていない間に材料が付かないことが、問いへ戻る動機を損ねていると常用で判定される | 決定 1 | 自動の契機か定期実行と、それに見合う費用の上限 |
| 利用者が付与の待ちを苦痛と言う | 決定 2 | `docs/DESIGN.md`「残す摩擦」の見直しが先に要る |
| 付与の失敗が常用で繰り返され、同じ操作のやり直しでは材料が付かない | 決定 4 | 失敗の理由を利用者へ区別して伝える形 |
