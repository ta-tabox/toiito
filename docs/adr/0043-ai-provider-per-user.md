# 0043. AI を呼び出すコードをプロバイダ単位で切り、モデルとキーを利用者ごとに解決する（0021 の改訂）

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 0021, 0025, 0035, 0042, 0044, 0045

**0021 を supersede する**。
動いたのは二点で、プロバイダを解決する単位と、送信の契約の範囲である。
残りは 0021 の本文を複写している（ADR 規約 4）。
複写した決定は、規約 7 に合わせてファイル名・型名・環境変数名を決定時点の例へ移し、比喩の語を直叙の語へ置き換えたが、意味は変えていない。
何がどう動いたかは下の「0021 から動いたところ」。

**0042 は supersede しない。**
0042 決定 13（深さをペルソナに持たせず、アプリ全体で一つにする）は動かず、この改訂はその読みを決定の本文に書くだけである。

## 文脈

### 0021 の文脈（複写）

AI を呼び出すコードが三つのモジュールへ散っている。
`effort.ts` が思考の深さの値域を、`config.ts` が env から作る既定値を、`claude.ts` が API 呼び出しを持つ。

`effort` は Claude API の `output_config.effort` そのもので、モデル名と同じくプロバイダ固有の概念である。
それがモデル名と別のモジュールに住み、既定値だけがさらに別の `config.ts` に集まっている。
分布の理由は env を読む都合であって、扱う概念のまとまりではない。

将来ほかのプロバイダを足す想定があるので、切り方の軸は「AI 全般」ではなくプロバイダになる。

### 0021 の後に出た要求

| 要求 | 出所 | 食い違う 0021 の決定 |
|---|---|---|
| 既定は安いモデルにし、高いモデルを使いたい利用者は自分の API キーで使う | #70（ユーザーごとのモデル選択と API キー（BYOK）） | プロバイダはアプリ全体で一つとする |
| 問いに対する材料を AI の web 検索で集め、出典の URL を添える | #63（培地を整える） | プロバイダが引き受けるのは、組み立て済みの本文を送って応答を返すところだけとする |
| 思考の深さをペルソナに持たせず、アプリ全体で一つにする | ADR 0042 決定 13 | 深さは系統ごとに違うので、プロバイダも系統ごとに解決する |

三つ目について、0042 は 0021 を supersede せず、系統ごとの解決をペルソナが固定二体だった時点の実装の例と読んだ。

## 決定

### モジュールの切り方（0021 から複写）

1. **AI を呼び出すコードをプロバイダ単位で切る。**
   プロバイダに依らない呼び出しの規約（フェイクモードへの分岐・呼び出しの記録・欠けた本文を返さないこと）と、プロバイダ固有の一切（深さの値域・設定の型・env からの読み・HTTP の作法）を別のモジュールに置く。
2. **依存を一方向にそろえる。**
   プロバイダの契約は何も import しない葉にし、規約の側からプロバイダの実装を参照しない。
3. **値域を絞り込む手順は概念に依らないので、独立したモジュールへ切り出し、値域を持つモジュールが使う。**

決定時点の例は次の六枚で、`effort.ts` と `claude.ts` は無くなった。
現況は `web/src/lib/ai/` が持つ。

| ファイル | 持つもの |
|---|---|
| `ai/index.ts` | 呼び出しの規約と、一回の呼び出しの手順 |
| `ai/provider.ts` | プロバイダ一つ分の契約 |
| `ai/prompt.ts` | モデルへ渡す本文の組み立てと、その材料の型 |
| `ai/fake.ts` | フェイクモードの応答 |
| `ai/providers.ts` | `process.env` を渡して解決済みのプロバイダを作る一枚 |
| `ai/anthropic.ts` | Anthropic 固有の一切 |

### プロバイダの契約

4. **プロバイダが引き受けるのは、組み立て済みの本文とサーバー側のツールの要求を送り、応答を規約の形で返すところまでとする。**
   打ち切りの表し方はプロバイダごとに違うので判定済みの真偽値で受け、それをどう扱うか（途中までの本文を返さない）は規約の側が決める。
5. **応答の規約の形は、本文・打ち切りの判定・使用トークン数に、出典の URL の一覧と web 検索の回数を加えたものとする。**
   ツールを要求しない呼び出しでは、出典の一覧は空で、検索の回数は 0 である。
   フェイクモードも同じ形を返す。
6. **どのプロバイダの設定も持つ欄を、共通の欄として型で括る。**
   規約の側がプロバイダを選ぶ前に読む欄が、そこに挙がっているものだけだと表明するためである。
7. **プロバイダは契約を継承したクラスで持つ。**
   設定は構築時に渡して保持させ、二つ目のプロバイダは契約を継承した別のクラスとして足す。
   規約の側にプロバイダごとの分岐は置かない。
8. **プロバイダ固有の型は名前でスコープを切る。**
   無印の名前は、他社の同種の指定を同じ型で表せるかのように読めてしまう。

決定時点の例として、契約は `AiProvider`、応答の形は `ProviderResponse`、共通の欄は `CommonSettings`、深さの値域は `AnthropicEffort`（`Effort` ではない）である。
サーバー側のツールの例は、Claude API の web 検索のツールである。
現況は `web/src/lib/ai/provider.ts` と `web/src/lib/ai/anthropic.ts` が持つ。

### 深さ

9. **深さはプロバイダの設定の一つとして持ち、呼び出しの指定に出さない。**
10. **深さはアプリ全体で一つにし、系統ごと・ペルソナごと・利用者ごとに変えない。**

決定時点の例として、0021 の時点では系統ごとの二つの環境変数から系統ごとのプロバイダを解決していた。
現況は `web/README.md` が持つ。

### プロバイダ・モデル・キーの解決

11. **対応するプロバイダは Anthropic だけとする。**
12. **モデルと API キーは、AI を呼ぶ時点で利用者ごとに解決する。**
    系統ごと・ペルソナごと・セッションごとには選ばない。
    利用者のキーの置き場は 0044、キーを登録していない利用者の扱いは 0045 が決める。

### 環境変数（0021 から複写）

13. **env はプロバイダを名乗る形にする。**
    SDK の慣習で決まっている API キーの名前と、プロバイダを叩かないというハーネス側の指定（フェイクモード）は名乗らせない。
    フェイクモードの指定を読むのは規約の側で、プロバイダへは解決済みの真偽値を渡す。
14. **`process.env` を渡すのは、その値を使う層の入口とする。**
    プロバイダ固有のモジュールは env を模した object を受ける純関数だけを持ち、env の読み方を純関数として検査できるようにする。

決定時点の例は次の改名で、現況は `web/README.md` が持つ。

| 旧 | 新 |
|---|---|
| `TOIITO_MODEL` | `TOIITO_ANTHROPIC_MODEL` |
| `TOIITO_MAX_TOKENS` | `TOIITO_ANTHROPIC_MAX_TOKENS` |
| `TOIITO_EFFORT_CONCRETE` | `TOIITO_ANTHROPIC_EFFORT_CONCRETE` |
| `TOIITO_EFFORT_ABSTRACT` | `TOIITO_ANTHROPIC_EFFORT_ABSTRACT` |

## 理由

### 0021 から複写した決定

- **深さをプロバイダ固有の設定にまとめる**: プロバイダ間で名前も値域も違う概念が、呼び出し側の視界から消える。
- **呼び出しの指定に固有の値を残さない**: 共通の欄とプロバイダ固有の値の集まりを並べる形では、集まりの中身を読む側が結局どのプロバイダかを判じることになり、抽象が一段無駄になる。
- **共通の欄を型で括ることは、上で退けた形とは別である**: 退けた集まりが持つのはプロバイダごとに中身の変わる値で、括るのは全プロバイダが同じ意味で持つ値なので、後者は判じずに読める。
- **クラスにする**: 設定を保持したインスタンスを呼び出し側が持てるので、規約の側にプロバイダごとの分岐が一つも要らなくなる。
- **依存が一方向にそろう**: 分岐が無い分、Anthropic の実装が契約を継承し、規約の側は Anthropic を知らない。
- **解決済みのプロバイダを AI のモジュールに置く**: プロバイダを探す読み手は AI のモジュールを見る。
  設定の定義を置くモジュールから AI の実体を取り出す形は辿れない。
- **env の改名を 0021 の時点で行った**: 二つ目が来てから直すより安く、据え置くとモデルの変数が「どちらのモデルか」を答えられないまま残る。

採らなかった案（0021 から複写）。

- **プロバイダを判別ユニオンの設定と関数の分岐で表す**: 規約の側にプロバイダごとの分岐が残る。
- **深さを toiito 独自の値域（`Depth` など）へ正規化する**: `xhigh` と `max` は他社の値域に無く、写像は情報を失う。
  深さを UI から触らせる要求が出れば正規化に値するが、いまは env にしか出ていない。

### 利用者ごとに解決する

- **利用者ごとにする**: API キーは利用者が持つもので、#70 の要求（高いモデルを使いたい利用者が自分のキーで使う）はキーとモデルの組を利用者に一つ持たせれば満たせる。
- **Anthropic だけにする**: 二つ目のプロバイダが実在しない段階で選択の手段を作っても、正しさを確かめる相手がいない（0021 が系統ごとにプロバイダを選ぶ手段を作らなかった理由と同じ）。
- **契約の形は保つ**: 二つ目を足すときに要るのが、契約を継承したクラスと、利用者の設定にプロバイダを持たせることだけになる。
- **深さをアプリ全体で一つと書く**: 0042 決定 13 と同じく、深さを選ばせる要求が出ていない。

採らなかった案。

- **ペルソナごとにモデルを選ぶ**: モデル名はプロバイダ固有の値で、0042 が深さをペルソナの版に持たせなかった条件（プロバイダ固有の値がレコードに入る）が同じく当たる。
- **セッションごとにモデルを選ぶ**: 投入と再訪のたびに選ぶ手順が増える。
- **Anthropic と他社を同時に対応する**: 契約に収まるかの確認と、ペルソナの文面が別のモデルで効くかの人間の判定が、プロバイダの数だけ要る。

### 送信の契約にサーバー側のツールを含める

- **契約に含める**: #63 は材料の出所を AI の web 検索にすると決めており、検索はプロバイダのサーバーで実行されるので、呼び出し側から見れば送信の要求の一部になる。
- **出典の URL を応答の形に持たせる**: ADR 0035 は外部の材料に出典を添えることを求めており、応答の形に出典があれば、出典の有無を機械が検査できる。
- **判定済みの一覧で受ける**: 打ち切りと同じく、出典の表し方もプロバイダごとに違う。
- **検索の回数を応答の形に持たせる**: 検索の回数はトークン数と別の量で、利用量の記録（#69（管理機能））がトークン数と並べて残すために要る。

採らなかった案。

- **検索をアプリで実行し、結果を本文に組み立てて送る**: 検索の API という依存が一つ増え、手仕舞いで閉じる相手が増える。
- **出典を本文の中に書かせ、応答の形を変えない**: 本文の文字列から URL を読み取ることになり、ADR 0035 の「出典を添える」を機械が確かめられない。

## 帰結

| 対象 | 変わること |
|---|---|
| `docs/ARCHITECTURE.md`「技術スタック（確定事項）」 | AI の行が、Anthropic だけを対応し、利用者ごとにモデルとキーを解決する形になる |
| env | env が決めるのはアプリの既定（既定モデル・深さ・上限・運営のキー）で、利用者ごとのモデルとキーは DB から解決して既定を上書きする |
| 系統ごとの深さの環境変数 | 一つになる（0042 決定 13 の帰結と同じ） |
| 一往復の失敗経路（ADR 0025） | モデルとキーの解決が DB の読み取りと復号を伴うので、解決の失敗も一往復の失敗に入る。解決は人間の発話を保留へ書き込んだ後に行い、失敗しても発話を保留に残す |
| 応答の規約の形 | 出典の URL の一覧と検索の回数が加わる。いまの対話の呼び出しはツールを要求しないので、空と 0 になる |
| フェイクモード | 出典を含む決定的な応答を返す形が要る |
| 利用量の記録（#69） | トークン数と並べて検索の回数を残せる。使ったキーの出所は 0045 が決める |
| 発話を生んだモデル | 記録しない。0042 がモデル名も深さもペルソナの版に残さないのと同じ扱いになる |
| ADR 0042 | 変わらない。決定 13 の読みを、この ADR の決定 10 が本文に持つ |

## 覆る条件

- **二つ目のプロバイダを足したとき、契約に押し込めなかったとき**（0021 から複写）。
  契約が実質 Anthropic の形をしていたということなので、切り直す。
- **二つ目のプロバイダの応答が規約の形に収まらなかったとき**（0021 から複写。出典の一覧と検索の回数を含む）。
  打ち切りと本文と使用トークン数と出典で足りるという見立てが外れたということなので、規約の形を決め直す。
- **深さを UI から触らせるとき**（0021 から複写）。
  独自の値域への正規化を再検討する。
- **利用者が Anthropic 以外のプロバイダのキーを使いたいと求めたとき**。
  決定 11 を見直し、利用者の設定にプロバイダを持たせる。
- **ペルソナごと・セッションごとにモデルを変えたい要求が出たとき**。
  決定 12 の単位を決め直す（ペルソナごとなら、0042 がプロバイダ固有の値を版に持たせなかった条件も同時に見直す）。
- **発話を生んだモデルを後から知りたい要求が出たとき**。
  記録の置き場を決める。

## 0021 から動いたところ

- **「プロバイダはアプリ全体で一つとする」が動いた**。
  0043 は、プロバイダを Anthropic だけに保ったまま、モデルと API キーを利用者ごとに解決する（決定 11・12）。
- **送信の契約の範囲が動いた**。
  0021 はプロバイダが引き受けるのを本文の送信と応答の返却だけとしていた。
  0043 はサーバー側のツールの要求を送信に含め、応答の形に出典の URL の一覧と検索の回数を加えた（決定 4・5）。
- **深さをアプリ全体で一つと書いた**（決定 10）。
  0021 は深さを系統ごとに解決していたが、0042 はそれを固定二体の時点の実装の例と読んでおり、深さをプロバイダの設定に持つという決定の意味は動いていない。
- **覆る条件のうち「ペルソナごと・系統ごとにプロバイダを変えたい要求が出たとき」を置き換えた**。
  深さはアプリ全体で一つになり、モデルとキーは利用者ごとに解決するので、残る問いはペルソナごと・セッションごとの要求と、Anthropic 以外のキーの要求になる。
- 決定の本体からファイル名・型名・環境変数名を外し、決定時点の例へ移した（規約 7）。
- 0021 の本文にあった比喩の語を、直叙の語へ置き換えた（規約 4 の、意味を変えない語彙の置き換え）。
