# AI の呼び出しごとの利用量を DB の表に記録し、本文を残さない

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 20260828-production-runtime, 20260830-invite-only-multi-user, 20260831-ai-provider-scope, 20260906-ownership-granularity, 20260915-ai-provider-per-user, 20260915-operator-key-for-keyless-users, 20260915-admin-flag-on-user-row, 20260915-suspend-on-user-row

## 文脈

#69（管理機能）は、誰がどれだけ AI を呼んでいるかを、管理者が見られることを求めている。
AI の費用はアプリ側に乗っている（20260830-invite-only-multi-user）。

いま AI の呼び出しの量が残るのは、実行ログの 1 行だけである。
その行は利用者を持たず、アプリから読む手段も無い。
実行ログは Vercel の保持期間を過ぎると残らない（Hobby での保持期間は、Vercel のドキュメントの検索では確かめられなかった）。

利用量を数える必要は #69 の外にもある。

- #70（BYOK）は、使用量の上限を利用量の記録が入ってからとしている。
  20260915-operator-key-for-keyless-users（キーを登録していない利用者は運営のキーを使う）の決定 4 は、利用量の記録に使ったキーの出所（運営のキーか利用者のキーか）を持たせると決めた
- #63（培地）で AI に web 検索をさせると、呼び出しごとに検索の回数が費用に加わる。
  20260915-ai-provider-per-user（モデルとキーを利用者ごとに解決する）の決定 5 は、プロバイダの応答の形に web 検索の回数を加えた

決めるのは次の四つである。

- 利用量をどこに持つか
- 何を記録し、何を記録しないか
- どこで計測するか
- 誰に見せるか

候補の置き場は三つあった。

| 候補 | 持ち方 |
|---|---|
| DB の表 | 呼び出し 1 回につき 1 行 |
| 実行ログ | 既存の呼び出しの記録に利用者を足す |
| 利用者ごとの累計の列 | 利用者 1 人につき合計の値を更新する |

## 決定

### 置き場

1. **AI の呼び出し 1 回ごとに、利用量の行を DB の表へ 1 行書く。**
   実行ログは利用量の置き場にしない。
2. **#63（培地）と #70（BYOK）の量も同じ表に書く。**
   領域ごとに表を分けない。

### 記録する値

3. **行が持つのは、下の表の値だけにする。**

| 値 | 意味 |
|---|---|
| 利用者 | 誰の操作で呼んだか |
| プロバイダとモデル | どこへ送ったか |
| 種別 | 何のための呼び出しか（ペルソナの発話・培地の作成など） |
| 入力と出力のトークン数 | プロバイダが返した値 |
| web 検索の回数 | 呼び出しの中で行った検索の回数 |
| キーの出所 | 運営のキーか利用者のキーか（20260915-operator-key-for-keyless-users 決定 4） |
| 時刻 | 記録した時刻 |

4. **プロンプト・応答・問いの本文は記録しない。**
   問い・セッション・発話を指す参照も持たない。

### 計測の場所

5. **計測は、AI の呼び出しの規約を持つ層の一か所で、プロバイダの応答を受け取った直後に行う。**
   呼び出し側が失敗として扱う応答（打ち切り・空の本文）も記録する。
   応答を受け取れなかった呼び出し（上限時間の超過・通信の失敗）は、トークン数が返らないので記録しない。
6. **呼び出しの規約を持つ層は DB を知らない。**
   記録する手段は、AI と DB の両方を知る呼び出し側が渡す。
7. **フェイクモードの呼び出しは記録しない。**

### 見せる相手

8. **利用量は、管理者（20260915-admin-flag-on-user-row）だけが見る運用の記録にする。**
   利用者には見せない。

決定時点の例として、表は `usage_logs`、呼び出しの規約を持つ関数は `callPersona`、記録する手段を渡す呼び出し側は `lib/turn.ts` である。
現況は `web/prisma/schema.prisma`・`web/src/lib/ai/index.ts`・`.claude/rules/layers.md` が持つ。

## 理由

- 管理の画面は、利用者ごと・期間ごとの量をアプリの中から読める必要があり、DB の表ならほかのデータと同じ repo 関数で読める
- 実行ログをアプリから読むには実行環境の API へ依存することになり、実行環境に依らない道具だけを入れるという禁止則（`.claude/rules/layers.md`。理由は 20260828-production-runtime）に反する
- #70 の上限は利用者ごと・期間ごとに数えることになるので、1 回ずつ残した記録から数えられる形が要る
- 費用に関わる量が一つの表に揃えば、管理の画面は表をまたがずに合算できる
- 問いは機微な出自を含みうるので、管理者が問いの本文を読める設計を作らない。
  既存の実行ログの 1 行も、同じ理由で本文を出していない
- 問い・セッション・発話を指す参照があると、管理者は DB の参照を辿って本文へ行き着けるので、参照も持たない
- 呼び出し側ごとに計測を置くと、呼び出す場所が増えたときに記録を書き忘れるので、計測は規約の層の一か所に置く
- 打ち切りや空の本文でも、プロバイダは応答を返しておりトークンは消費されているので、記録する
- 層の表は、AI と DB の両方を import してよいのを一往復の手順の層に限っているので、規約の層は記録する手段を受け取る
- フェイクモードはプロバイダを呼ばず費用が発生しないので、記録するとテストと Preview の行が費用の数に混ざる
- `docs/ARCHITECTURE.md`「意図的にやらないこと」の「KPI・利用統計」は、問いの熟成を速度で測らないという不作為であり、利用者に見せない運用の記録はそれに当たらない

採らなかった案と、それを採らなかった条件。

- **実行ログ**。
  スキーマが変わらず、書き込みの往復も増えない。
  保持期間を過ぎると残らず、アプリから読むには実行環境の API への依存が要るので採らなかった
- **利用者ごとの累計の列**。
  書き込みが 1 行の更新で済み、読むときに集計が要らない。
  モデル・期間・キーの出所ごとの内訳が残らず、#70 の上限を期間で数えるなら作り直すことになるので採らなかった
- **領域ごとに表を分ける**。
  #63 と #70 がそれぞれの表を持ち、互いの列に触れない。
  管理の画面で費用の量を合算するのに表をまたぐ集計が要るので採らなかった
- **本文も記録する**。
  管理者が問いの中身から停止を判断できる。
  管理者が他人の問いを読める設計になり、他人の問いを読ませないという所有権の絞り込み（20260906-ownership-granularity）と食い違うので採らなかった
- **規約の層が DB へ直接書く**。
  呼び出し側から記録する手段を渡さずに済む。
  規約の層が DB に依存し、層の表に反するので採らなかった
- **フェイクモードの呼び出しも記録する**。
  E2E で記録の書き込みを確かめられる。
  費用の発生しない行が費用の数に混ざり、書き込みは単体テストで確かめられるので採らなかった

## 帰結

- DB に利用量の表が 1 つ加わり、migration が 1 本入る（列の現況は `web/prisma/schema.prisma`）
- 利用量の表は利用者を指す列を持つが、利用者が読むリソースではないので、所有のルート（20260906-ownership-granularity 決定 1）ではない。
  利用者の画面の repo 関数からは読まず、読むのは管理の画面だけである
- AI の呼び出しの規約に、記録する手段を受け取る欄が加わる（現況は `web/src/lib/ai/index.ts`）
- #63（培地）の web 検索と #70（BYOK）のキーの選択は、それぞれの実装で同じ表へ値を書く（20260915-ai-provider-per-user 決定 5・20260915-operator-key-for-keyless-users 決定 4）。
  それまでの行は、web 検索の回数を 0、キーの出所を運営のキーとして書く
- 行を消す処理を持たないので、行は本番の DB の容量を使い続ける
- `docs/ARCHITECTURE.md`「意図的にやらないこと」の「KPI・利用統計」の行に、管理者だけが見る運用の記録である旨の但し書きが入る。
  現況の文書なので、#69（管理機能）の子 issue が直す
- 記録と表示の実装は、#69（管理機能）の子 issue が作る

## 覆る条件

- 利用量の行が、本番の DB の容量に対して無視できない大きさになったとき。
  古い行を消すか、期間ごとの集計へ置き換えるかを決める
- #70 の上限の判定で、呼び出しのたびの集計が実測で遅いと分かったとき。
  累計の列を併用するかを決め直す
- 停止の判断に、本文を読まなければ分からない事情が繰り返し出たとき。
  決定 4 を決め直す
- プロバイダが、応答を返さなかった呼び出しにも課金すると分かったとき。
  決定 5 の記録しない条件を決め直す
- 本番が、長く保持されアプリから読めるログの基盤を持つ実行環境へ移ったとき。
  決定 1 を決め直す
