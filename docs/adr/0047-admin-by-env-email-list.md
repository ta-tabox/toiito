# 0047. 管理者を環境変数のメール一覧で見分ける

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 0018, 0022, 0033, 0036, 0037, 0048, 0049

## 文脈

#69（管理機能）は、利用者の一覧と利用量を見ることと、利用者を停止することを、管理者だけに許すよう求めている。
いまのアプリが利用者を区別するのは、サインインしているかどうかの二値だけで、管理者という区別を持たない。

0022（セッションの守り）の覆る条件は「二値でない認可が入ったら、認可の設計そのものを議題にする」と書いている。
管理者と一般の利用者を分けることはこの条件に当たるので、見分け方をここで決める。

候補は三つあった。

| 候補 | 見分ける材料 |
|---|---|
| 環境変数のメール一覧 | サインインした利用者の email が一覧に載っているか |
| 利用者の行の役割の列 | `user` 表に足した役割の値 |
| Better Auth の admin プラグインの利用者 id の一覧 | プラグインの設定に並べた `user.id` |

## 決定

1. **管理者は、サインインした利用者の email が環境変数の管理者の一覧に載っているかで見分ける。**
   DB に役割を持たせない。
2. **管理者の一覧は、許可リストと同じ置き方と比べ方にする。**
   環境変数にカンマ区切りで置き、前後の空白を除いて小文字へ揃えてから比べる。
3. **サインインできるかどうかは、許可リストだけが決める。**
   管理者の一覧に載っていても、許可リストに載っていなければサインインできない。
4. **管理者の判定は、現在の利用者を返す入口を通った後の一か所で行う。**
   管理の画面も、管理の操作を行う Server Action も、同じ判定を通る。
5. **管理者でないリクエストには、管理の画面が存在しないときと同じ応答（404）を返す。**
6. **管理者の一覧が未設定か空なら、管理者はいないものとして扱う。**
   設定の読み取りは throw しない。

決定時点の例として、環境変数は `TOIITO_ADMIN_EMAILS`、判定の関数は `requireAdmin`、管理の画面は `/admin` である。
現況は `web/README.md`「環境変数」・`docs/DEPLOY.md`「秘密の置き場」・`web/src/lib/auth/` が持つ。

## 理由

- 管理者は運営する一人で、替える回数が少ないので、替えるたびに再デプロイが要ることは対価として小さい
- 0018 決定 3 が許可リストを環境変数に置いているので、サインインに関わる一覧の置き場が一つに揃う
- 比べ方を許可リストと揃えると、同じ email を二つの一覧に書いたときに片方だけ一致しない事故が起きない
- 管理者の一覧でサインインの可否まで決めると、許可リストから外した人が管理者の一覧に残っていたときに入れてしまうので、サインインの可否は許可リストだけに持たせる
- 0022 決定 9 が現在の利用者を読む経路を一本に絞っており、その後ろに判定を一か所置けば、画面と Server Action のどちらかで判定を書き忘れる経路ができない
- 管理の画面があること自体が一般の利用者に要らない情報なので、403 でなく 404 を返す
- 管理者がいない環境（Preview・手元）は運用上ありうるので、未設定を throw にはしない。
  未設定の結果は「誰も管理の画面を開けない」になり、「誰でも開ける」にはならない

採らなかった案と、それを採らなかった条件。

- **利用者の行の役割の列**。
  再デプロイなしで管理者を替えられる。
  migration と、最初の管理者を SQL で立てる手順が要り、`db.ts` が Better Auth の表から読む列が増える（0037 の覆る条件）。
  管理者が一人のうちは払う理由が無いので採らなかった
- **Better Auth の admin プラグインの利用者 id の一覧**。
  プラグインが持つ一覧・停止のエンドポイントがそのまま使える。
  `user.id` は初回サインインで Better Auth が振るので、サインインの後に環境変数を書き換えて再デプロイする二段の手順になる。
  加えて、一覧に載った利用者は Better Auth 1.7.2 の `dist/plugins/admin/has-permission.mjs` で全権限を持ち、なりすまし・パスワードの設定・利用者の作成まで行える。
  パスワードを実装しない決定（0036 決定 2）と招待制（0018）の外にある操作が開くので採らなかった
- **許可リストの先頭の email を管理者にする**。
  環境変数が増えない。
  一覧の並びに意味を持たせると、人を足す編集で管理者が入れ替わりうるので採らなかった

## 帰結

- 環境変数が 1 本増える。
  名前と意味の現況は `web/README.md`「環境変数」、本番での置き場は `docs/DEPLOY.md`「秘密の置き場」が持つ
- 管理者の一覧を読むのは、認証の環境変数を閉じるモジュールである（`.claude/rules/layers.md`「境界を閉じるモジュール」の表）
- 0022 の覆る条件「二値でない認可が入ったら」に当たる。
  判定を現在の利用者を返す入口の後ろ一か所に置くので、0022 決定 9 の「読む経路を一本に絞る」は保たれる
- 利用量を見る画面（0048）と停止の操作（0049）は、この判定を通った管理者だけが使える
- 管理の画面と判定の実装は、#69（管理機能）の子 issue が作る

## 覆る条件

- 管理者が複数になり、替える頻度が再デプロイの手間を上回ったとき。
  役割を DB へ移すかを決め直す
- 許可リストを廃止してアカウント登録制へ移るとき（0022 帰結「移行の順序」）。
  サインインに関わる一覧を DB へ移すなら、管理者の一覧も同時に移す
- 管理者と一般の利用者の間に第三の権限が要るようになったとき。
  二値の一覧では表せないので、役割の設計を決め直す
