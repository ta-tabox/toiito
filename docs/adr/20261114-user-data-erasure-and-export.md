# 利用者は問い一件と全データを物理削除でき、全データを JSON と Markdown で書き出せる

- **状態**: 採用
- **決定日**: 2026-11-14
- **関係する ADR**: 20260906-ownership-granularity, 20260909-ownership-before-auth, 20260914-memo-edit-and-soft-delete, 20260914-question-form-history, 20260915-suspend-on-user-row, 20260915-usage-log-in-db, 20260828-production-runtime, 20261112-guest-sign-in-with-quota, 20261112-invite-only-multi-user

## 文脈

問いと発話は利用者の出自を含みうる。
招待制で他人へ開いた（20261112-invite-only-multi-user）ので、利用者が自分のデータを消す経路と持ち出す経路が要る。

決定時点のデータ層は、問い・セッション・発話を削除する repo 関数を持たない。
`questions` から下の外部キーは削除の挙動を持たず、`user` の行の削除に連鎖するのは認証の表だけなので、利用者の行を消しても問いと発話が残る。
ゲストのサインイン（20261112-guest-sign-in-with-quota）も、期限切れのゲストの行と持ち物を消す処理を必要としている。

## 決定

### 消去の単位

1. **利用者は、問い一件と、自分の全データの二つの単位で消去できる。**
   問い一件の消去は、その問いと、問いを根とする行（セッション・発話・未完了の発話・メモ・メモ間の辺・材料・言い直しの履歴）をすべて消す。
   全データの消去は、利用者を所有者として持つ行のすべてを消す。
2. **消去の対象は、所有のルート（20260906-ownership-granularity）から外部キーで辿れる行のすべてと定義する。**
   この決定より後に足された表も、所有のルートから外部キーで辿れる限り同じ消去の対象に入る。

### 消去の方式

3. **消去は物理削除にする。**
   行を DB から消し、削除した時刻を書いて残す形を取らない。
   消した行を戻す操作は作らず、消す前に確認の一手を挟む。
4. **子の行は、外部キーの削除の連鎖（`ON DELETE CASCADE`）で消す。**
   所有のルートから下へ辿る外部キーと、所有のルートから `user` を指す外部キーは、すべて削除を連鎖させる。
   問い一件の消去は問いの行を、全データの消去とゲストの消去は `user` の行を消すだけにし、アプリが子の表を順に消す手順を持たない。
   新しい表を所有のルートの下に足すときは、その外部キーに削除の連鎖を持たせる。
5. **所有の連鎖の外から行を指す外部キー（例: セッションがペルソナを指す）は、文の途中で拒否しない挙動にする。**
   同じ `user` の削除の中で指す側と指される側が一緒に消えるので、検査を文の終わりで行う挙動（`NO ACTION`）にし、文の途中で拒否する挙動（`RESTRICT`）にしない。

### 退会

6. **全データの消去は退会を兼ね、`user` の行ごと消す。**
   ログインのセッションも連鎖で消え、利用者はその場でサインアウトした状態になる。
   許可リストに残っている利用者が再びサインインすると、空の新しい行ができる。
7. **退会では、その利用者の利用量の行（20260915-usage-log-in-db）も連鎖で消す。**

### 書き出し

8. **利用者は、自分の全データを JSON と Markdown の二つの形式で書き出せる。**
   どちらも全データを形式ごとに 1 ファイルで渡し、問い一件ごとの書き出しは作らない。
   JSON は所有のルートから辿れる行を、メモの範囲と並び順を含めて欠けなく持つ。
   Markdown は問いごとの見出しで区切り、人間が読む形で対話とメモを持つ。
9. **書き出しに含めないものは、利用量の行・暗号化した API キー・認証の表・論理削除したメモである。**

### 保持期間

10. **招待した利用者のデータに保持期間を設けない。**
    利用者が消すまで残す。
    ゲストの期限付きの消去（20261112-guest-sign-in-with-quota 決定 3）は変わらない。

### ゲスト

11. **ゲストにも、招待した利用者と同じ消去と書き出しの操作を出す。**
    画面の経路をゲストのために分岐させない（20261112-guest-sign-in-with-quota 決定 2）。

決定時点の例として、消去の repo 関数は `deleteQuestion(owner, id)` と `deleteUser(owner)`、書き出しの変換は `web/src/lib/export.ts`、退会と書き出しの操作の置き場は `/settings` の画面である。
現況は `web/prisma/schema.prisma`・`web/src/lib/db.ts`・`web/src/app/` が持つ。

## 理由

- 特定の問いだけを消したい利用者に退会を強いると、残したい問いまで失うので、問い一件の単位を持つ
- 全データの消去を問い一件の消去と別に持つのは、所有のルートが問い以外（ペルソナ・モデルの設定）にもあり、問いをすべて消しても利用者の行と設定が残るため
- 発話は書き換えない設計（`messages` の不変条件）なので、論理削除では本文が DB に残り、出自を消すという目的を満たさない
- 消去は利用者自身の明示の操作で、メモの論理削除（20260914-memo-edit-and-soft-delete）が守った「誤った下線を消す」とは目的が違うので、メモの論理削除と方式を揃えない
- 子から順に消す手順をアプリが持つと、表が増えるたびに問い一件・全データ・ゲストの 3 経路の順序を直すことになり、直し忘れると外部キーの拒否で消去が失敗するので、削除の連鎖を DB に持たせる
- 削除の連鎖を外部キーの宣言に置けば、後から足す表（ペルソナ逸脱検査の判定結果を保存する表など）も、宣言を書いた時点で消去の対象に入る
- `RESTRICT` は文の途中で検査するので、`user` の削除が問いとペルソナを同じ文で消すとき、連鎖の順によって拒否される
- 停止（20260915-suspend-on-user-row）は利用者のデータを残して利用を止める操作で、退会とは目的が逆なので、停止の列で退会を表さない
- 利用量の行は本文を持たないが `user` を指しており、`user` の行を消すには外部キーを外すか行を消すかを選ぶことになり、ゲストの消去も利用量の行を一緒に消しているので、扱いを揃える
- JSON は構造（メモの範囲・並び順・状態）を欠けなく持ち、他の道具へ機械で変換できる
- Markdown はそのまま読め、ノートの道具へ置ける
- 全データを形式ごとに 1 ファイルにすれば、zip を作る依存が要らない
- 利用量の行は管理者だけが見る運用の記録（20260915-usage-log-in-db 決定 8）なので、利用者の書き出しに含めない
- 暗号化した API キーは利用者が復号できず、持ち出しても使えないので含めない
- 論理削除したメモは、利用者がすべての表示から除くと決めた行なので、書き出しにも出さない
- このアプリは問いを長く寝かせる用途を持ち、状態に `permanent` があるので、使われない期間で消すと利用者の意図に反する
- 本番の Vercel Hobby には定期実行の設定が無い（20260828-production-runtime）
- ゲストの画面を分岐させると、20261112-guest-sign-in-with-quota 決定 2 が避けた分岐が増え、読み手が消去と書き出しを機能として確かめられなくなる

採らなかった案と、それを採らなかった条件。

- **全データの消去だけ**。
  操作が一つで済む。
  特定の問いを消すのに退会が要るので採らなかった
- **問い一件の消去だけ**。
  `user` の行を消す経路が要らない。
  ペルソナ・モデルの設定・利用者の行が残り、退会の経路が無いので採らなかった
- **論理削除**。
  誤って消した行を戻せる。
  発話の本文が DB に残り、全読み取りに条件が増えるので採らなかった
- **論理削除と、期限後の物理削除**。
  一定期間は戻せる。
  期限後に消す定期実行が本番に無いので採らなかった
- **アプリが子の表から順に消す**。
  migration が要らず、外部キーが消し忘れを拒否する。
  表が増えるたびに 3 経路の順序を直すことになるので採らなかった
- **退会を停止と同じに扱う**。
  行が残り、管理者が解除できる。
  名前とメールアドレスが DB に残り、停止の目的（データを残して止める）と逆なので採らなかった
- **全データの消去と退会を分ける**。
  設定を残したまま中身だけを空にできる。
  画面の操作が二つになり、空にした利用者は問いを一件ずつ消すのと結果が変わらないので採らなかった
- **退会しても利用量の行の `user_id` を空にして残す**。
  運営の費用の合計が退会の後も残る。
  `user_id` を空にできる migration が要り、ゲストの上限の数え方に `user_id` の無い行が混ざるので採らなかった
- **JSON だけ**。
  変換が一つで済む。
  人間がそのまま読める形が無いので採らなかった
- **Markdown だけ**。
  そのまま読める。
  メモの範囲と並び順が落ち、機械で戻せないので採らなかった
- **問い一件ごとの書き出し**。
  対話画面の状態 `exported` と操作が対応する。
  操作が一つ増え、全データの書き出しから同じ問いを取り出せるので採らなかった
- **Markdown を問いごとのファイルにして zip で渡す**。
  ノートの道具へ問いごとに置ける。
  zip を作る依存が増えるので採らなかった
- **最後の利用から一定期間で消す**。
  使われなくなった本文が残らない。
  最後の利用の時刻の列・消去の経路・事前の通知が要り、問いを長く寝かせる用途と食い違うので採らなかった
- **ゲストには退会を出さない**。
  ゲストの利用量の行が上限の期間の内で消えない。
  画面にゲストの分岐が入り、利用量の行を消して全ゲスト合計の上限を回避する効果は新しいゲストでサインインし直すのと変わらないので採らなかった

## 帰結

- 所有の連鎖の外部キーに削除の連鎖が付き、所有の連鎖の外から指す外部キーの `RESTRICT` が `NO ACTION` に変わる（migration が一本入る。現況は `web/prisma/schema.prisma`）
- ゲストのデータ層（#368（ゲストの行・上限の判定・消去を、データ層と純関数で持つ））の消去は、子から順に消す手順を持たず、期限を過ぎたゲストの `user` の行を消すだけになる
  #368 は削除の連鎖の migration の後に着手する
- 言い直しの履歴（20260914-question-form-history）の表を含め、所有のルートの下に表を足す issue は、外部キーに削除の連鎖を宣言する
- `usage_logs` の行は、退会とゲストの消去で消える
  20260915-usage-log-in-db 帰結「行を消す処理を持たない」は、利用者が残る限りで成り立つ
- 管理の画面の期間ごとの合計から、退会した利用者の分が消える
- 退会は `user` の行を消すので、管理の画面の利用者の一覧から消える
- 書き出しの JSON の形は、表を足すたびに書き出しの変換が追随する
  Markdown も同じ
- 対話画面に問い一件の消去が、`/settings` の画面に退会と書き出しが加わる

## 覆る条件

- 誤って消したという申し出が出たら
  論理削除と期限後の物理削除へ戻る（定期実行の手段が要る）
- 管理者が退会した利用者の費用を後から確かめる要求が出たら
  利用量の行の `user_id` を空にして残す案へ戻る
- 退会でゲストの全ゲスト合計の上限が回避される量が観測されたら
  ゲストの退会を閉じるか、利用量の行をゲストの消去の期限まで残す
- 利用者の数が増え、使われない本文が Neon Free の容量を圧迫したら
  保持期間を持つ
- 他の道具への取り込みに、問いごとのファイルが要ると分かったら
  zip の書き出しを足す
