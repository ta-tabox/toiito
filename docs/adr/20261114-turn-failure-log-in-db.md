# 一往復の失敗を DB の表に記録し、管理者のホームに未確認の件数を出す

- **状態**: 採用
- **決定日**: 2026-11-14
- **関係する ADR**: 20260902-turn-atomicity-and-pending-utterance, 20260915-usage-log-in-db, 20260915-admin-flag-on-user-row, 20261112-guest-sign-in-with-quota, 20260828-production-runtime

## 文脈

一往復が `messages` へ書き込まれずに終わったときの記録は、標準エラーへ出す `turn_failed` の 1 行の JSON と、Next が出す例外のログだけである。
作者が Vercel のログ画面を開かない限り、失敗が起きたことを知る経路が無く、ログを遡れる期間も Vercel のプランが決める。

ゲストのサインイン（20261112-guest-sign-in-with-quota）で招待していない匿名の読み手が AI を呼ぶので、失敗の件数は招待した利用者だけの時期より増えうる。
ゲストの行と持ち物は作られてから 26 時間で消えるので、失敗の記録をゲストの持ち物として持つと記録も消える。

通知の手段の候補は四つあった。

| 案 | 作者が知る時点 | 増える依存と秘密 |
|---|---|---|
| DB の表 + 管理者のホームに未確認の件数 | 作者がアプリを開いたとき | 無し |
| DB の表 + `/admin` だけ | 作者が `/admin` を開いたとき | 無し |
| エラー監視のサービス（Sentry など） | 失敗の直後（メール） | SDK と DSN が一つずつ |
| メール送信のサービス（Resend など） | 失敗の直後か日次 | SDK と API キーが一つずつ、日次なら定期実行 |

Vercel のログの転送（Log Drains）は Hobby では使えないので、候補に入らない。

## 決定

1. **一往復の失敗は、DB の失敗の表に 1 行ずつ記録する。**
   書くのは、一往復が `messages` へ書き込まれずに終わったことが確定した時点で、標準エラーの `turn_failed` の 1 行は残す。
   再試行の内で成功した呼び出しは失敗に数えず、一往復として最後に失敗したときだけ 1 行書く。
2. **作者へは、外部のサービスを使わずアプリの画面で知らせる。**
   管理者（利用者の行のフラグが真の利用者）のホームに、未確認の失敗の件数を出す。
   `/admin` に失敗の一覧（時刻・種類・理由・ゲストだったか）を出す。
3. **未確認は、管理者が失敗の一覧を最後に開いた時刻より後の失敗とする。**
   最後に開いた時刻は管理者の利用者の行に持ち、`/admin` の失敗の一覧を描いたときに更新する。
4. **失敗の行は、失敗の種類・時刻・例外の message・利用者・セッション・ゲストだったかを持つ。**
   発話の本文は持たない。
   例外の message は `turn_failed` の `reason` と同じ文字列で、Claude API の応答本文の先頭（エラーの詳細）を含みうるが、利用者の発話は含まない。
5. **失敗の種類は、コードの一箇所の並びが持つ値の集合にし、値ごとに「ホームの件数に数えるか」を持つ。**
   種類を足すときは並びに値を一つ足し、DB の列の型は変えない。
   設計どおりに拒否した一往復（ゲストの上限など）は、種類を分けて記録し、ホームの件数に数えず、`/admin` の一覧にだけ出す。
6. **ゲストの行を消すときは、そのゲストの失敗の行を消さず、利用者とセッションへの参照だけを外す。**
   ゲストだったかは行のフラグに持つので、参照を外した後も一覧で見分けられる。

決定時点の例として、失敗の種類は次のとおりにする。
値の現況は、失敗の種類の並びを持つコードの定数が持つ。

| 種類 | 起きる場面 | ホームの件数 |
|---|---|---|
| `ai_call_failed` | ペルソナの決定か AI の呼び出しが throw した | 数える |
| `commit_conflict` | 応答を待つあいだに同じセッションへ別の一往復が書き込まれた | 数える |
| `guest_quota_exceeded` | ゲストの上限に達して AI を呼ばずに拒否した | 数えない |

## 理由

- **エラー監視のサービスを採らなかった条件**: 依存と秘密が一つずつ増え、例外の message（Claude API の応答本文の先頭を含む）を外部へ送る範囲を別に決めて守る必要が出る
  作者は自分でアプリを日常的に使うので、ホームに件数を出せば外部へ送らずに数日以内に気付ける
- **メール送信のサービスを採らなかった条件**: 依存と秘密が増えるうえ、日次の送信には本番の Vercel Hobby に無い定期実行が要る（20260828-production-runtime）
- **`/admin` だけに出す案を採らなかった条件**: 作者が `/admin` を開く動機は失敗の有無を知ること以外に無く、失敗を知らないうちは開かない
- **ログだけに残す案を採らなかった条件**: ログを数えて件数を出す経路が Hobby に無く、遡れる期間もプランが決める
- **例外の message を残す理由**: 種類だけでは理由を追うのに Vercel のログ画面を開く必要が残り、ログの保持期間を過ぎると理由が失われる
- **発話の本文を持たない理由**: 投入される問いは機微な出自を含みうるので、`ai_call` と `turn_failed` のログと同じく本文を残さない（20260915-usage-log-in-db と同じ扱い）
- **直近 24 時間の件数を出す案を採らなかった条件**: 確認した後も件数が残り、24 時間以上アプリを開かなかった間の失敗を見落とす
- **ゲストの上限による拒否を記録しない案を採らなかった条件**: ゲストの濫用は 20261112-guest-sign-in-with-quota の覆る条件で、拒否の頻度が見えないとその条件に気付けない
- **ゲストの上限による拒否をホームの件数に数える案を採らなかった条件**: 上限は設計どおりの挙動で、ゲストが上限を使い切るたびに件数が増えると障害の件数が埋もれる
- **ゲストの失敗の行を一緒に消す案を採らなかった条件**: 作者が 26 時間以内にアプリを開かなければ、ゲストの失敗は記録ごと消えて知る経路が無くなる
- **種類を Prisma の enum にしない理由**: 一往復でモデルへ渡す発話の量の上限（#361）など、失敗の形が後から増える見込みがあり、種類を足すたびに migration が要るのを避ける

## 帰結

- 失敗の表が増え、利用者の行に失敗の一覧を最後に開いた時刻の列が増える（migration が一本増える）
- 一往復の手順（`web/src/lib/turn.ts`）が、失敗が確定したときに失敗の表へ書く
  失敗の表への書き込み自体が throw したときの扱いは、実装の issue が決める
- `db.ts` のゲストの行を消す repo 関数が、失敗の行を消さず参照を外す
- ホーム（`web/src/app/page.tsx`）が、管理者にだけ未確認の失敗の件数を出す
- `/admin` に失敗の一覧が増える
- 失敗の行は消さないので、行数は失敗の件数だけ増え続ける
- 失敗の種類を足す決定（#361（一往復でモデルへ渡す発話の量の上限）など）は、種類の並びに値を一つ足し、ホームの件数に数えるかを選ぶ

## 覆る条件

- 作者がアプリを数日開かない運用になり、失敗に気付くのが遅れて実害が出たら
  外部へ知らせる経路（メールかエラー監視のサービス）を足す
- 失敗の行が Neon Free の容量を圧迫したら
  期間で古い行を消す手順を足す
- 例外の message に利用者の発話が混ざる経路が見つかったら
  message を残すのをやめて種類だけにするか、混ざる経路を断つ
- 本番の実行環境が定期実行かログの転送を持つプランへ移ったら
  ログの転送と通知の機能を比べ直す
