# 0046. 管理者を利用者の行のフラグで見分ける

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 0018, 0022, 0033, 0036, 0037, 0047, 0048

## 文脈

#69（管理機能）は、利用者の一覧と利用量を見ることと、利用者を停止することを、管理者だけに許すよう求めている。
いまのアプリが利用者を区別するのは、サインインしているかどうかの二値だけで、管理者という区別を持たない。

0022（セッションの守り）の覆る条件は「二値でない認可が入ったら、認可の設計そのものを議題にする」と書いている。
管理者と一般の利用者を分けることはこの条件に当たるので、見分け方をここで決める。

サインインできる人を決める許可リストは、0022 決定 8 が暫定措置と位置づけており、0022 帰結「移行の順序」の 4 段目で廃止する予定である。

候補は四つあった。

| 候補 | 見分ける材料 |
|---|---|
| 利用者の行の管理者のフラグ | `user` 表に足した二値の列 |
| 利用者の行の役割の列 | `user` 表に足した役割の値 |
| 環境変数のメール一覧 | サインインした利用者の email が一覧に載っているか |
| Better Auth の admin プラグインの利用者 id の一覧 | プラグインの設定に並べた `user.id` |

## 決定

### 持ち方

1. **管理者は、利用者の行が持つ管理者のフラグで見分ける。**
   環境変数に管理者の一覧を持たない。
2. **フラグは管理者かどうかの二値にし、役割の値域を持たせない。**
3. **フラグの列は Better Auth が生成する列ではないので、アプリの規約（snake_case）で名付ける。**
4. **フラグを立てる手段は DB への直接の更新だけにし、アプリの画面と操作に置かない。**
   最初の管理者は、本番の DB でフラグを直接立てる。

### 判定

5. **サインインできるかどうかは、フラグで変えない。**
   フラグが立っていても、サインインの可否は許可リスト（廃止した後はその後継）が決める。
6. **管理者の判定は、現在の利用者を返す入口を通った後の一か所で行う。**
   管理の画面も、管理の操作を行う Server Action も、同じ判定を通る。
7. **管理者でないリクエストには、管理の画面が存在しないときと同じ応答（404）を返す。**
8. **フラグの立った利用者がいなければ、管理者はいないものとして扱う。**

決定時点の例として、列は `user.is_admin`（既定は偽）、判定の関数は `requireAdmin`、管理の画面は `/admin` である。
現況は `web/prisma/schema.prisma`・`web/src/lib/auth/current-user.ts` が持ち、フラグを立てる手順は `docs/DEPLOY.md` が持つ。

## 理由

- 許可リストは暫定措置でいずれ廃止するので、管理者の見分け方を許可リストの置き方に揃える理由にならない
- 利用者の行に持てば、許可リストを廃止しても管理者の判定は動かない
- 利用者の行に持てば、管理者を替えるのに再デプロイが要らない
- 管理者と一般の利用者の二つを分ければ足りる。
  役割の値域を持たせると、各値の権限を決める設計が先に要る（0022 の覆る条件）ので、二値に留める
- 0037 が Better Auth の表の列名を生成されたまま置いたのは、版が上がるたびに手で直さないためで、アプリが足す列にはその理由が当たらない（0048 決定 2 と同じ）
- 管理者は運営する一人で、立てる回数が少ない。
  フラグを立てる操作をアプリに置くと、その操作を管理者だけに許す判定と、最初の一人を立てる手順が別に要る
- フラグでサインインの可否まで決めると、許可リストから外した人のフラグが残っていたときに入れてしまうので、サインインの可否に使わない
- 0022 決定 9 が現在の利用者を読む経路を一本に絞っており、その後ろに判定を一か所置けば、画面と Server Action のどちらかで判定を書き忘れる経路ができない
- 管理の画面があること自体が一般の利用者に要らない情報なので、403 でなく 404 を返す
- 管理者がいない環境（Preview・手元）は運用上ありうる。
  フラグの立った利用者がいない結果は「誰も管理の画面を開けない」になり、「誰でも開ける」にはならない

採らなかった案と、それを採らなかった条件。

- **環境変数のメール一覧**。
  migration が要らない。
  許可リストを廃止するときに管理者の一覧も移し直すことになり、管理者を替えるたびに再デプロイも要るので採らなかった
- **利用者の行の役割の列**。
  管理者以外の役割を後から足せる。
  第三の権限を必要とする要求がまだ無く、役割の値域と各値の権限を決める材料が無いので採らなかった
- **Better Auth の admin プラグインの利用者 id の一覧**。
  プラグインが持つ一覧・停止のエンドポイントがそのまま使える。
  `user.id` は初回サインインで Better Auth が振るので、サインインの後に設定を書き換えて再デプロイする二段の手順になる。
  加えて、一覧に載った利用者は Better Auth 1.7.2 の `dist/plugins/admin/has-permission.mjs` で全権限を持ち、なりすまし・パスワードの設定・利用者の作成まで行える。
  パスワードを実装しない決定（0036 決定 2）と招待制（0018）の外にある操作が開くので採らなかった
- **管理の画面からフラグを立てる**。
  DB へ直接触らずに管理者を増やせる。
  最初の管理者は結局 DB で立てることになり、昇格の操作を管理者だけに許す判定が一つ増えるので採らなかった

## 帰結

- `user` 表にフラグの列が 1 本加わり、migration が 1 本入る（現況は `web/prisma/schema.prisma`）
- `db.ts` が `user` 表から読む列が一つ増える。
  0037 の覆る条件の一つ目（`db.ts` が四表の他の列を読む）に当たるが、決定 3 で詰め替えを発生させないので、0037 決定 4 は動かない（0048 の停止の列と同じ）
- 最初の管理者を立てる手順（DB でフラグを立てる更新）が `docs/DEPLOY.md` に加わる。
  シードは一人目の利用者にフラグを立て、E2E はそのシードを使う
- 環境変数は増えない
- 0022 の覆る条件「二値でない認可が入ったら」に当たる。
  判定を現在の利用者を返す入口の後ろ一か所に置くので、0022 決定 9 の「読む経路を一本に絞る」は保たれる
- 許可リストを廃止する移行（0022 帰結「移行の順序」の 4 段目）で、管理者の判定を移す作業は要らない
- 利用量を見る画面（0047）と停止の操作（0048）は、この判定を通った管理者だけが使える
- 管理の画面と判定の実装は、#69（管理機能）の子 issue が作る

## 覆る条件

- 管理者と一般の利用者の間に第三の権限が要るようになったとき。
  二値のフラグでは表せないので、役割の設計を決め直す
- 管理者が複数になり、DB への直接の更新でフラグを立てる手間が運用に合わなくなったとき。
  決定 4 を決め直し、昇格の操作と、その操作を管理者だけに許す判定を設計する
- Better Auth が版を上げて、`user` 表に管理者を表す列を生成するようになったとき。
  決定 3 の前提（アプリだけが足す列である）が崩れる
