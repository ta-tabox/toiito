# 0009. Postgres のメジャーを、本番を立てる前に 18 で揃える

- **状態**: 採用
- **決定日**: 2026-08-29
- **関係する ADR**: 0004

## 文脈

本番の Postgres は Neon に置く（#90（本番環境へデプロイする））。
Neon はプロジェクトの作成時にメジャーを選ばせ、**メジャーの in-place upgrade を持たない**。
上げるには新しいプロジェクトを作ってデータを移す。

いまはまだ本番にデータが無いので、プロジェクトごと捨てて作り直すのが最も安い。
本番が動き出すとその窓は閉じる。

ローカル（`compose.yaml`）と CI（`check.yml` / `claude.yml`）は 17 だった。
本番だけ 18 を選ぶと、方言差が出たときに手元で再現できない。

## 決定

ローカル・CI・本番の三者を 18 で揃える。
揃えるのは本番を立てる前で、手元と CI が 18 で緑になったことを Neon のメジャーを選ぶ条件にする。

ローカルの volume は `/var/lib/postgresql` へ当てる。

## 理由

**窓が閉じる前に踏むのが安い。**
版の非互換で詰まったとき、本番 DB を持っていなければ切り分けは「アプリの問題か・版の問題か」の二択で済む。
本番を持ってから踏むと、ここに「本番環境の問題か」が足されて三択になる。

**17 に留める案を採らなかった条件**: Prisma 7.10.0 が 18 で動くことが未確認だった。
手元で migration が積め、`pnpm check` と `pnpm e2e` が緑になったので、この条件は消えた。
逆に赤ければ 17 へ戻し、Prisma 側の対応を待つ側へ倒れていた。

**本番だけ 18 にする案を採らなかった条件**: ローカルと CI が 17 のままだと、18 でしか出ない挙動を手元で再現できない。
Neon が in-place upgrade を持てば、本番を後から追随させられるのでこの条件は消える。

## 帰結

- ローカルの volume は作り直しになる。
  18 からイメージがデータをメジャーごとの部分ディレクトリへ置くので、17 までの `/var/lib/postgresql/data` を当てたままだと起動時に弾かれる。
  マウント先を `/var/lib/postgresql` へ移し、`docker compose down -v` で作り直す
- CI は volume を持たないので、`image:` の行だけで足りる
- リモート（Claude Code on the web）の Postgres は 16 のままで、非対称が 17 との差から 18 との差になる。
  `apt.postgresql.org` へ出られないので上げる手段が無い（`HARNESS.md`「リモート」）
- Neon のプロジェクトは 18 で作る。
  この判断は #90 の人間のコンソール作業に従属している

## 覆る条件

- Prisma が 18 で壊れる不具合を出したら。
  17 へ戻し、本番も作り直す（本番にデータが乗る前に限る）
- Neon がメジャーの in-place upgrade を持ったら。
  三者を同時に動かす必要が無くなるので、ローカルと CI が先に進んでよくなる
- 19 が出て、同じ理由で揃え直す必要が出たら
