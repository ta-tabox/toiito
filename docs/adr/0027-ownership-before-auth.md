# 0027. 所有者を認証より先にデータ層へ入れ、Better Auth の四表はモデル名も列名も生成されたまま同居させる

- **状態**: 採用
- **決定日**: 2026-09-02
- **関係する ADR**: 0013, 0018, 0019, 0020, 0022, 0024

## 文脈

0019・0020・0022 は認証と所有権の方式を決めたが、どれも実装される前の決定である。
#166（所有権の土台を敷く）は、そのうち**データ層の分だけ**を先に入れる回として #68（ログイン（Google OAuth）とリソースの所有権）から切り出された。
先に切り出す理由は #64（二体のペルソナをセッション単位で設定できるようにする）が待っているのが認証の配線ではなく `user_id` が指せる先だからで、そのルートを切るのに OAuth は要らない。

**入れてみると、決定されていなかったことが四つ出た。**

- **`Session` という名前が二つある。**
  Better Auth はログインのセッションを `session` と呼び、この器は問いへの再訪を `sessions` と呼ぶ。
  Prisma のモデル名は一意でなければならないので、四表をそのまま同居させると `model Session` が衝突する。
  同じ衝突が TS 側にもあり、`db.ts` は既に `getSession(id)` を対話の意味で export している——0022 の決定 9 が要求する認証のラッパも、上流の API 名をなぞれば同じ関数名になる
- **`db.ts` が `user` 表に触れることになった。**
  0019 の帰結は「この四表は `db.ts` から読まない」を前提に列名の据え置きを正当化しており、同じ ADR の覆る条件の一つが「四表を `db.ts` から読む必要が出たら」だった
- **固定の利用者を、どの環境変数で名指しするか決まっていない。**
  0019 の決定 7 は「環境変数で固定の利用者としてログイン済みにする」とだけ書いており、変数名が決まっていない
- **本番の利用者を誰にするかが決まっていない。**
  `questions.user_id` は NOT NULL（0020 決定 4）で backfill を書かない（同 決定 5）ので、この回の migration は既存の問いを消す。
  そして本物の認証はまだ無いので、0019 の決定 7 を字義どおり読むと、この回から #68 が入るまで本番は現在の利用者を決められない

## 決定

1. **Better Auth の四表は、1.7.2 が要求するモデル名と列名のまま `schema.prisma` へ置く。**
   取り込みの正は `@better-auth/cli` ではなく、`better-auth` 本体が export する `getAuthTables` が返す定義にする。
2. **`Session` の衝突は、対話側の Prisma モデル名を `DialogueSession` へ改めて解く。**
   表名（`sessions`）・列名・ドメイン型（`types.ts` の `Session`）はどれも動かさない。
3. **認証側の「現在の利用者」の口は `getCurrentUser` と名乗る。**
   `getSession` は対話側が持ち続ける。
4. **`db.ts` は `user` 表に触れる。**
   用途は二つだけ——現在の利用者を email で引く・開発用シードが二人作る——で、それでも列名は snake_case へ揃えない。
5. **ログインが入るまで、利用者は `TOIITO_SINGLE_USER_EMAIL` が名指しする一人に固定する。本番も同じにする。**
   未設定なら落とす。
   本番でこれを許す間、**外周を守るのは `proxy.ts` の Basic 認証だけ**になる。
   Basic 認証を外すのは #68（ログイン（Google OAuth）とリソースの所有権）でログインを入れて本番で確かめた後にし、**その順序は運用の規律で持つ。機械では止めない**。

## 理由

### 決定 1 — 四表の正を `getAuthTables` に置く

**`@better-auth/cli` は 2026-09-02 時点で deprecated で、`latest` が 1.4.21 のまま止まっている**（npm の deprecation メッセージは "Package no longer supported"）。
実際に 1.4.21 の CLI へ 1.7.2 の設定を読ませて生成すると、**`account.issuer` が落ちる**（1.7.2 は必須で持ち、1.4.21 は知らない）。
生成物をそのまま貼っていたら、#68 で Google のアカウントを作った瞬間に NOT NULL 違反で落ちていた。
`getAuthTables` は Better Auth 自身がアダプタと migration 生成の両方で呼んでいる定義なので、版と必ず一致する。

**CLI の出力を採らなかった条件**: 版が追随していないこと。
CLI が本体と同じ版で配布され直したら、そちらの方が索引や既定値まで含めて正しいので戻る。

**手書きの `User(provider, provider_subject, …)` を採らなかった条件**: 0019 の決定 1 が Better Auth の自前ホストを選んでおり、プロバイダの識別子は `user` でなく `account` が持つ。
この判断は #166 で選び直したものではなく、0019 の帰結をそのまま実装しただけである。

### 決定 2 — 譲るのは対話側の Prisma モデル名

**同居させる以上どちらかが名前を譲るが、譲る費用が非対称だった。**

Better Auth 側を `AuthSession` へ改めると、`session: { modelName: "authSession" }` を設定に書くことになる。
そして Prisma アダプタは `db[model]` で delegate を引く（`@better-auth/prisma-adapter` 1.7.2 の `create` / `findOne`）ので、渡すモデル名は Prisma のクライアントに合わせた camelCase でなければならない——**モデル名という一つの欄が、Prisma のモデル名と Prisma クライアントの property 名の二つを同時に満たす必要がある**。
同じアダプタは join のキー名を `getModelName(model).toLowerCase() + "s"` で組み立てる箇所も持っており、改名がそこへどう響くかは #68 で実際に繋ぐまで分からない。

対話側の Prisma モデル名を改めると、動くのは `schema.prisma` の一語と `db.ts` の中の `db().dialogueSession` だけである。
**表も列もドメイン型も動かないので、migration は一行も出ない**（`prisma migrate diff` で確認した）。
Prisma のモデル名はこの器では外へ出ない——`db.ts` の外へ Prisma を出さないという禁止則が既に効いているので、読み手の目に触れるのは `types.ts` の `Session` の方である。

**「セッション」という語をどちらが持つか**という問いにも、この向きの方が答えが揃う。
0022 は既に「Better Auth の `session` は対話の `sessions` と別物である」と書いており、この器の語彙では「セッション」は問いへの再訪を指す。
名前を譲るのは、内側にしか出ない機械の handle の側でよい。

**対話の表ごと `dialogue_sessions` へ改名する案を採らなかった条件**: 表名を変えると migration が出るうえ、`ARCHITECTURE.md`・`db.ts`・E2E が持つ表名の記述が全部動く。
衝突しているのは Prisma のモデル名だけで、表名は `sessions` と `session` で既に割れている。

### 決定 3 — 認証側は `getCurrentUser`

0022 の決定 9 は「`getSession` ラッパ」と書いているが、それは上流の `auth.api.getSession` をなぞった呼び名であって、**この器で何を返すかを言った名前ではない**。
返すのは利用者であり、呼び出し側（RSC と Server Action）が欲しいのも利用者である。
`getCurrentUser` なら要約の語彙が名前と揃い（`CODING.md`）、対話側の `getSession` と関数名も意味も衝突しない。

0022 の決定 9 が要求している中身——`React.cache()` で包む・戻り値に branded type を付ける・データ層の関数はその型しか受け取らない・ラッパ以外からの `auth` の import を `no-restricted-imports` で禁じる——は名前を替えても全部そのまま残っており、実装で満たしている。

**対話側の `getSession` を改名する案を採らなかった条件**: 呼ばれている場所が多いだけでなく、`Session` というドメイン型と対になっている名前である。
片方だけ改名すると、型と関数で別の語を使うことになる。

### 決定 4 — `user` 表を読むが、列名は据え置く

0019 が列名の据え置きを正当化した根拠は「`db.ts` から読まないので詰め替えの利益が発生しない」だった。
読むことになった以上、根拠は差し替わる——**読むのが `id` / `email` / `name` の三つだけで、どれも Better Auth 側で既に camelCase を持たない語だから、詰め替えが一件も発生しない**。
`emailVerified` や `accessTokenExpiresAt` のような列名は、この器のコードのどこにも現れない。

対して揃える費用は据え置きのままである。
四表は Better Auth の版に従属するので、揃えると版が上がるたびに手で直すことになる。

**読まずに済ませる案を採らなかった条件**: 現在の利用者を env の email から解くのに `user` を引くしかなく、開発用シードが二人を作るのにも書くしかない。
`TOIITO_FAKE_USER_ID` で id を直に指す案なら読まずに済むが、id はシードが振る UUID なので、シードを流すたびに env を書き換えることになる。

### 決定 5 — 本番も一人に固定し、順序は運用で持つ

**未設定を素通しへ倒さない条件は 0022 が書いている。**
この器は「掛けたつもりで掛かっていなかった」形を二度踏んでおり（0013 の Edge ランタイムと #152 の ruleset）、どちらも素通し側へ倒れる分岐が生き残ったことが原因だった。
いま素通しの倒し先を作ると、#68 で本物の述語を入れるときに外し忘れる分岐がそこに残る。

**本番でも許す条件は、0019 の決定 7 が何を守っていたかを読み直すと出る。**
決定 7 が本番を禁じた理由は、フェイク認証が「認証を丸ごと外す口」だからだった。
だが**その口が危険なのは外周が開くからで、外周そのものは 0013 の Basic 認証が持っている**。
Basic 認証を継続する限り外周は開かない。
そして 0018（招待制で他人へ開く）が実際に複数人を入れるまで、本番へ届くのは Basic のパスワードを知っている一人だけである。
利用者が構造上ひとりなら、その一人を env が名指しするのはフェイクの持ち込みでなく**単一利用者の運用**に当たる。

**本番を止めたまま #68 を待つ案を採らなかった条件**: 止めて得られる守りが無い。
外周は既に Basic 認証が持っているので、本番でフェイクを禁じることが足すのは二重の守りではなく「本番が動かないこと」だけである。
失うものの方は具体的で、#68 が入るまで自分の問いを本番へ投げられない。

**Basic 認証の有無と機械で結ぶ案を、いまは採らなかった条件**: `readBasicAuthCredentials` が資格情報を返すときだけ単一利用者を許す形にすれば、#68 で Basic 認証を外した瞬間に単一利用者の口も閉じ、順序の間違いが構造的に起きなくなる。
採らなかったのは、開発者が一人で URL をどこにも公開していない現状で、実装を一つ増やすより運用の規律で足りると判断したためである（2026-09-06）。
**採る条件**: 開発者が増えるか、URL を公開するか、Basic 認証を外す回が #68 と別の回になったとき。

**順序を逆にしたときに何が起きるかは、書いておく**。
ログインが動かないまま Basic 認証だけを外すと、`TOIITO_SINGLE_USER_EMAIL` が名指しする一人として誰でも全部読める状態になる。
これは 0013 が踏んだ「掛けたつもりで掛かっていなかった」と同じ形なので、規律で持つと決めた以上、手順の側（`DEPLOY.md`「アクセス制限」）に順序を明示する。

**変数名を `TOIITO_FAKE_USER_EMAIL` から替えた条件**: 本番で走るものを「フェイク」と呼ぶと、いま何が起きているかを取り違える。
実態は認証の偽装ではなく、利用者がまだ一人だという運用である。

**`NODE_ENV` と `VERCEL_ENV` で環境を見分ける必要も消えた**。
本番を含むどの環境でも同じ一本の経路になったので、見分ける材料が要らない。
手元の `next build` が `NODE_ENV=production` で走ることも問題にならず、置き場は `.env.local` のままでよい（`.env.development.local` へ逃がす必要が無い）。

**#68 を待って一つの PR で入れる案を採らなかった条件**: #166 を切り出した理由（#64 が待っているのは `user_id` が指せる先で、OAuth ではない）がそこで消える。

## 帰結

- **0019 の覆る条件の一つ目が発火した**（「Better Auth の四表を `db.ts` から読む必要が出たら」）。
  帰結の「snake_case の対象外」は成り立ったままだが、根拠が「読まないから」から「読む三列に詰め替えが発生しないから」へ差し替わる。
  **0019 は supersede しない**——決定は一つも動いていない
- **0022 の決定 9 が挙げた関数名が変わる**。
  ラッパの名前は `getSession` でなく `getCurrentUser`（`src/lib/current-user.ts`）。
  要求している性質は変わらない
- **#68 は `session.modelName` を設定に書かなくてよい**。
  四表が生成されたモデル名のままなので、Prisma アダプタは既定の解決で届く
- `ARCHITECTURE.md`「所有権」に、`db.ts` が `user` を読むことと `DialogueSession` の由来が入る
- **0019 の決定 7 のうち「production で設定されていたら投げる」を、この決定が置き換える**。
  0019 のヘッダには `supersede 済み` を足さない——残る 7 つの決定と、決定 7 の前半（Preview と E2E はフェイク認証を使う）は一つも動いていないので、ファイル全体を supersede 済みにすると読み手を誤らせる。
  覆したのが決定 7 の後半だけであることは、ここに書いておく
- `web/README.md` の環境変数表に `TOIITO_SINGLE_USER_EMAIL` が加わり、`DEPLOY.md` は Production と Preview の両方の表が 1 本ずつ増える
- **本番の `user` 表に、名指しした email の行を一つ入れる手順が要る**（`DEPLOY.md`「唯一の利用者」）。
  `pnpm seed` は開発用の問いまで入れるうえ `NODE_ENV=production` で止まるので、本番には使わない
- **その email は、ログインに使う Google アカウントのものにしておく**。
  0019 の決定 6 が自動リンクを既定で有効にしないと決めているので、email が違うと #68 の後に自分の問いが見えなくなる
- **`DEPLOY.md`「アクセス制限」に Basic 認証を外す順序が入る**。
  ログインを入れる → 本番で確かめる → Basic 認証を外す、の三段で、途中は二重認証になる
- **Preview は migration を流した後にもう一度 `pnpm seed` が要る**。
  この回の migration が既存の問いを消し、シードは二人分の利用者ごと入れ直す形になった
- 開発用シードが二人になる。
  一人目が「現在の利用者」で、二人目の問いはどの画面にも出てはいけない側として在る
- #64（二体のペルソナをセッション単位で設定できるようにする）が `persona` を二つ目の所有のルートにするとき、`user_id` の指す先が既に在る
- **#175（一往復は成立してから書き、成立前の発話は預かる）より先に main へ入れる**。
  あちらが作る `pending_messages` は `sessions` を `ON DELETE RESTRICT` で参照するので、後から流すとこの回の `DELETE FROM "sessions"` が外部キーに止められる（2026-09-02 に実測）。
  逆順で入れるなら、この回の migration へ `pending_messages` の DELETE を足してから流す。
  落ちるのは migration であってデータではないので、取り違えても壊れるのは deploy だけである
- **#175 は `db.ts` の rebase が要る**。
  追加している `commitTurn` / `savePendingBody` / `getPendingBody` の三本は所有者を受け取らないので、そのままだと預かり中の発話が絞り込みの外に出る。
  `PendingMessage` が参照する `Session` も、こちらが `DialogueSession` へ改めた側である

## 覆る条件

- **`db.ts` が四表の他の列を読む必要が出たら。**
  決定 4 の根拠（詰め替えが一件も発生しない）がそこで崩れるので、揃えるかどうかを決め直す
- **Better Auth が 1.8 系へ上がったら。**
  四表の定義を `getAuthTables` から取り直す。
  0022 が同じ条件で `dist/` の読み直しを求めているので、そちらと同時に見る
- **`@better-auth/cli` が本体と同じ版で配布され直したら。**
  決定 1 の理由（版が追随していない）が消えるので、生成に戻す
- **Better Auth のログインセッションを `db.ts` から読む必要が出たら。**
  決定 2 と決定 3 の名前の分担を、両方まとめて見直す
- **Prisma のモデル名が `db.ts` の外へ出るようになったら。**
  決定 2 が「内側にしか出ない handle の側が譲る」に寄り掛かっている
- **#68（ログイン（Google OAuth）とリソースの所有権）が入ったら。**
  本番の利用者は Better Auth のセッションが決めるようになるので、決定 5 の単一利用者は本番から外れる。
  `TOIITO_SINGLE_USER_EMAIL` は Preview と E2E に残る
- **開発者が増えるか、URL を公開するか、招待制で他人を入れるとき**（0018）。
  「本番へ届くのは Basic のパスワードを知っている一人だけ」が成り立たなくなるので、単一利用者の運用ごと畳んで #68 を先に入れる
- **Basic 認証を外す回が #68 と別の回になったら。**
  順序を運用の規律で持つという判断がそこで崩れるので、`readBasicAuthCredentials` と結んで機械が止める形へ移す（採らなかった案として上に書いてある形）
- **Basic 認証そのものを先に外したくなったら。**
  決定 5 が寄り掛かっているのは外周が別の層で掛かっていることなので、0013（本番へのアクセス制限をアプリ側の Basic 認証で持つ）を動かす判断はこの決定を同時に動かす
