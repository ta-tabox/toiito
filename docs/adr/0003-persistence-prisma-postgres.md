# 0003. 永続化を `node:sqlite` から Prisma + Postgres へ移す

- **状態**: 採用
- **決定日**: 2026-08-15
- **関係する ADR**: 0004, 0005, 0006

## 文脈

旧方針は「`node:sqlite` でネイティブ依存ゼロ・ローカル完結」と「`db.ts` の repo 関数のシグネチャを保ったまま Postgres へ差し替える契約」の二本立てだった。
この形は方言の二重管理（`db.ts` の `SCHEMA` と `supabase/migrations/0001_init.sql`）と型の手書きキャスト（`.all() as Memo[]`）をメンテナンスコストとして残していた。

契約の漏れも実際に出た。
`latestSession` / `listMessages` が Postgres に無い `rowid` を使っており、シグネチャを保っただけでは差し替えが通らない状態になっていた。

## 決定

1. **Prisma を入れて開発も本番も Postgres 一本にする**。
2. **repo 関数のシグネチャ契約はここで意図的に破る**。
   同期から `async` へ変わる。
3. **維持するのは境界の方だけ**。
   `@prisma/client` と生成型は repo 層の内側に閉じ、UI と Server Actions が受け取るのは `types.ts` のドメイン型に限る。

## 理由

ネイティブ依存ゼロという旧方針の価値基準そのものが、メンテナンスコストと釣り合わなくなったためである。
守ろうとしていたのは「どこでも `node` だけで動く」ことだったが、その対価が方言の二重管理と手書きキャストで、しかも守れていなかった（`rowid` の漏れ）。

**旧方針を維持する案を採らなかった条件**: シグネチャ契約が机上のもので、実際には守られていなかったこと。
契約が漏れる形で残るなら、それは移行容易性ではなく移行容易性の見かけである。

**旧方針のもう一つの根拠が失効していた**。
`node:sqlite` を選んだ理由には Cowork サンドボックスの制約（FUSE・コマンド 45 秒制限・GitHub 到達不可）があったが、実装を Claude Code のローカル環境で行うことになった時点でこれは効かなくなっている（0006）。

置き場と ORM の選定（Neon + Prisma 7）は hatchery の kb `postgres-hosting-selection-2026.md` が正典で、この器で決めたのはローカルの立て方だけである（0004）。

## 帰結

- `ARCHITECTURE.md` の技術スタックが Postgres + Prisma になり、「永続化について今も効く禁止則」の節が置かれた（方言を二重に持たない・repo 関数はすべて `async`・Prisma を repo 層の外へ出さない・起動に外部プロセスが要ることは引き受けた前提）
- **ローカル完結性を捨てた**。
  起動に外部プロセスが要るので、手元での立て方を別に決める必要が出た（0004）
- `tests/migrate.test.ts` を削除した。
  旧スキーマからの移送を `db.ts` の `migrate()` が担っていたのを検証するテストであり、その役割は Prisma Migrate の migration 履歴へ移ったためである（テスト用 DB は毎回 `migrate deploy` で migration を積み直すので、履歴の健全性はそこで機械的に確かめられる）
- 既存データを移送するかという論点が残り、PR #14 のレビューで取りやめた（0005）

## 覆る条件

- **禁止則「方言を二重に持たない」「Prisma を repo 層の外へ出さない」を破る必要が出たら**。
  境界が保てないなら、ORM の選択そのものがこの器の要求に合っていない合図になる
- **起動に外部プロセスが要ることが着手の頻度を落としていると分かったら**。
  ローカル完結性を捨てた判断は「手元で Postgres を立てる手数は安い」を前提にしているので、そこが崩れれば前提ごと見直す
- **Prisma 7 の driver adapter が本番の実行環境（0002 で Vercel）で動かなくなったら**。
  永続化の形が実行環境に従属することになるので、両方をまとめて決め直す
