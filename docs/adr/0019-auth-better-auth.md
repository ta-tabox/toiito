# 0019. 認証基盤を Better Auth の自前ホストにし、Google OAuth 一本で始める

- **状態**: 採用
- **決定日**: 2026-08-30
- **関係する ADR**: 0012, 0013, 0018

## 文脈

0018 で招待制へ開くと決まり、複数の人間を区別する認証が要ることになった。

#65（認証と所有権の方式を決める）が並べた候補は Firebase Auth / Auth.js (NextAuth) + Google OAuth / Clerk / Supabase Auth の四つだった。
**このリストが書かれた後に前提が動いている。**
Auth.js は 2025-09 に保守が Better Auth チームへ移管され、2026 年初頭から maintenance mode に入った。
リポジトリの README は「Auth js is now part of Better Auth」と述べ、新規プロジェクトには Better Auth を勧めている（2026-08-30 に確認）。
`npm` の `next-auth@latest` は今も 4.24.15 で、App Router 向けの v5 は `next-auth@beta` を明示で入れないと来ない。

#68（ログインと所有権）は「認証情報（パスワード・トークン）は toiito の DB に持たない。持つのは外部 IdP の識別子だけ」を要求している。

## 決定

1. **Better Auth（2026-08-30 時点で 1.7.2・MIT）を自前でホストする。**
   Neon の Managed Better Auth は使わない。
2. **パスワードは実装しない。**
3. **初期スコープは Google OAuth 一本。**
4. **セッションは DB に持つ**（JWT にしない）。
5. **`proxy.ts` は cookie の有無だけを見る楽観的な判定に留める。**
   実際の認可は repo 層が `user_id` で行う。
6. **アカウントの自動リンクを既定で有効にしない。**
   プロバイダが二つ目になる回（#133（捨てアカウント枠））に、束ねるかどうかを決める。
7. **Preview と E2E はフェイク認証を使う。**
   環境変数で固定の利用者としてログイン済みにする。
   `TOIITO_FAKE_AI` と同じ発想だが、**production で設定されていたら投げる**。
8. **#68（ログインと所有権）の要求文を精密化する。**
   OAuth のトークンは保存しない。

## 理由

**決め手は、手仕舞いで閉じる相手を増やさないことだった。**
このプロジェクトは有期で終わる（`CLAUDE.md` の完了条件）。
Better Auth は自分のプロセスで動き、同一性のテーブルは自分の Postgres にある。
閉じる相手は Google の OAuth クライアント一つで、それは Google 一本を選ぶ限りどの候補でも要る。
0012 が Vercel Marketplace の Neon を落とした理由（剥がすときが片側で済む）と同型である。

**Clerk を採らなかった条件**: 利用者の実体が他社側に残るので、Neon へ写すための同期層（webhook）が一枚生える。
無料枠は 50k MRU で費用は問題にならないが、閉じる相手が一つ増える。

**Firebase Auth を採らなかった条件**: この器は GCP に居ない。
`firebase-admin` が Edge ランタイムで動かず、入口での検証に負債を負うことになる。
GCP へ寄る理由が他に無い以上、払う理由が無い。

**Supabase Auth を採らなかった条件**: DB は Neon で決着している（0012）ので、認証のためだけに Supabase のプロジェクトを持つことになる。
Supabase Auth の強みである RLS も、DB が別なら効かない。

**Auth.js を採らなかった条件**: 上流自身が新規プロジェクトへ Better Auth を勧めている。
JWT セッションなら DB に一行も持たずに #68 の要求をそのまま満たせるという利点はあるが、maintenance mode の基盤に載せて得るのがそれだけなら釣り合わない。

**Neon の Managed Better Auth を採らなかった条件**: 同じ Better Auth を自分のプロセスで動かせば、テーブルは Postgres である限りどこへでも運べる。
管理された側を採ると、0012 が避けた「剥がすときに二つ動かす」形へ戻る。

**JWT セッションを採らなかった条件**: #69（管理機能）が「停止したユーザーの AI 呼び出しを断つ」を要求している。
JWT は発行済みのものを取り消せないので、停止が次の期限切れまで効かない。
DB セッションなら行を消した瞬間に効く。
DB を毎回叩く対価はあるが、それは速度の話で、`ARCHITECTURE.md`「快適さの最適化をしない」に照らすと最適化を優先する理由にならない。

**`proxy.ts` で毎リクエスト DB 検証する案を採らなかった条件**: Next の proxy は常に Node.js ランタイムで走る（0013 で実測済み）ので、技術的には書ける。
採らないのは、0013 が「matcher を書かず全リクエストを通す」と決めているためである。
全リクエストに DB の往復を足すと、Neon の Scale to Zero からの復帰が入口に乗る。
cookie の有無だけなら往復が無く、**取りこぼしても repo 層の `user_id` が最後に守る**。
入口は導線であって関門ではない、という役割分担にする。

**自動リンクを既定で有効にしない条件**: いまプロバイダは Google 一つで、束ねる相手がそもそも存在しない。
決めずに済むうちは非可逆でない側へ倒す——有効にすると同じメールアドレスの別プロバイダが同一の利用者へ吸われ、後から別扱いへ改めても**既に束ねた行は割れない**。
無効から有効へは後でいつでも動かせるので、片方向にしか動けない側を既定に置かない。
加えて自動リンクは、メールの所有証明が弱いプロバイダを信頼した瞬間に乗っ取りの経路になる。
Google は検証済みのメールを返すので信頼できるが、二つ目が何を保証するかは二つ目を選んでから分かる。
**Better Auth の既定がどちら側かは確かめていない**ので、実装時に設定を明示する（#68（ログインと所有権））。

**Preview で本物の OAuth を通す案を採らなかった条件**: Google の redirect URI は事前登録が要り、ワイルドカードを受け付けない。
Vercel の Preview URL は PR ごとに変わるので、登録が追いつかない。
ブランチ固定の URL を登録する案は、ブランチが増えるたびに手作業が増える。
フェイク認証は、この問題と #68 の E2E 要求（二人分の利用者を用意して他人のリソースが見えないことを見る）を同じ一つの仕掛けで解く——実 OAuth では二人分のログインを自動化できない。

**フェイク認証を「設定が無ければ素通し」に倒さなかった条件**: 0013 が踏んだ失敗が「掛けたつもりの制限が掛かっていなかった」ことだった。
同じ形をもう一度作らない。
`TOIITO_FAKE_AI` を本番へ入れないのは `DEPLOY.md` の運用上の注意だが、こちらは認証を丸ごと外す口なので、注意ではなくモジュールの評価時の例外にする。

**トークンを保存する既定のままにしなかった条件**: Better Auth は OAuth の `accessToken` / `refreshToken` を `account` テーブルへ平文で保存する（暗号化は `encryptOAuthTokens` を明示的に有効にする形で、既定では掛からない）。
このアプリは Google の API を叩かないので、要るのは同一性だけである。
使わない資産を持つと、DB が漏れた日の影響範囲だけが広がる。
#70（BYOK）が「平文で持たない」を要求しているのと同じ判断である。

## 帰結

- `ARCHITECTURE.md`「技術スタック」に Better Auth の行が入る
- **#68（ログインと所有権）の「作るもの」が変わる。**
  自前の `User`（`provider` / `provider_subject` を持つ）は作らない。
  Better Auth が `user` / `session` / `account` / `verification` の四表を作り、プロバイダと IdP 側の識別子は `account` が持つ
- Better Auth のテーブルは、CLI が生成した綴りのまま `prisma/schema.prisma` へ同居させる。
  **snake_case で揃えるという約束の対象外にする**——列名を揃える理由は repo 層の詰め替えを消すことだが、この四表は `db.ts` から読まないのでその利益が発生しない。
  揃えると再生成のたびに手で直すことになる
- migration の経路は動かない。
  Prisma Migrate が運び、main への push で GitHub Actions が流す（0008）
- 本番と Preview の環境変数が増える（Better Auth の秘密・Google のクライアント ID と秘密・許可リスト。Preview はフェイク認証の 1 本）。
  実際の綴りと本数は #68 が確定させる
- #133（捨てアカウント枠）を足す回に、決定 6（自動リンク）へ戻ることになる

## 覆る条件

- **Better Auth が保守されなくなったら。**
  Auth.js が辿った経路をもう一度辿ることになる
- 停止（#69（管理機能））が JWT の短い有効期限で足りると判断できたら。
  決定 4 の理由が消える
- Google を持たない相手を入れる必要が出たら。
  決定 3 と決定 6 が同時に動く（#133（捨てアカウント枠））
- Better Auth の四表を `db.ts` から読む必要が出たら。
  帰結の「snake_case の対象外」が成り立たなくなる
- 入口の楽観的な判定で実害が出たら——未ログインが保護されたページの中身を一瞬でも受け取る、など。
  そのとき proxy を DB 検証へ上げる
