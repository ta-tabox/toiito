# 0005. 既存データの移送を取りやめる

- **状態**: 採用
- **決定日**: 2026-08-16
- **関係する ADR**: 0003

## 文脈

issue #11（永続化の Postgres 移行）は「既存のローカルデータは移送する（S0 の実キー対話ログを消さない）」を決定事項として置いていた。
PR #14 のレビューでこれを覆した。

## 決定

移送しない。
移送スクリプトと、そのために足した migration を落とす。

## 理由

移送を通すために持ち込んだ複雑さが、守ろうとした価値を上回っていたためである。

具体的には二つある。
移送スクリプト（`scripts/import-sqlite-data.ts`）が、`node:sqlite` を撤去したはずのリポジトリに唯一の依存として残り、そのために `@` 起点の import 規約にも例外を作っていた。
`seq` を後から足した migration も、既存行を時刻順に振り直す `row_number()` と `setval` を抱えていた——これは移送してきた行のためだけの処理で、空の DB では何もしない。

**「移送する」を採らなかった条件は「まだ作り直せる段階か」である**。
開発初期で本番も無く、旧データは SQLite ファイルとして手元に残る。
消えて困るものが無い以上、恒久的にリポジトリへ残る複雑さの方が高くつく。

## 帰結

- migration は init 一本になった（後付けの `add_insertion_sequence` は、`seq` を最初から schema に持てば存在しない migration だった）
- `node:sqlite` への依存がリポジトリから完全に消え、`@` 起点の import 規約の例外も消えた
- S0（2026-07-17）の実キー対話ログは Postgres 側に無い。
  SQLite ファイルとして手元にあるだけである

## 覆る条件

- **「まだ作り直せる段階か」が反転したら**。
  本番にデータが乗って消えて困るものができた時点で、以後の破壊的なスキーマ変更は同じ基準では判断できない。
  そこからは移送の複雑さを引き受ける側が既定になる
