# 停止を利用者の行に持ち、現在の利用者を返す入口で判定して、停止中の操作をすべて断つ

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 20260830-invite-only-multi-user, 20260901-session-security, 20260909-login-and-fake-sign-in, 20260909-auth-better-auth, 20260909-ownership-before-auth, 20260915-admin-flag-on-user-row, 20260915-usage-log-in-db

## 文脈

#69（管理機能）は、AI の費用がアプリ側に乗る以上、利用者を止める手段を求めている。
いま利用者を止めるには、許可リストから外して再デプロイするしかない。
許可リストの照合はサインインのときだけなので（20260901-session-security 決定 8）、外しても既存のセッションは最大 1 日有効なまま残る。

20260901-session-security（セッションの守り）は、停止の即時性を前提に置いている。
決定 6 は、取り消しの遅れを作らないために `cookieCache` を禁じた。
帰結「移行の順序」は、利用者の行に停止フラグを足し、現在の利用者を返すラッパの判定でそのフラグを見る形を予定している。

決めるのは次の五つである。

- 停止をどの仕組みで持つか
- どこで判定するか
- 停止中に何を断つか
- 許可リストとの関係
- 利用者の表は Better Auth が生成する表なので、アプリが足す列をどの規約で名付けるか（20260909-ownership-before-auth 決定 4 は、この表の列名を snake_case へ揃えないと決めている）

候補の仕組みは三つあった。

| 候補 | 停止の持ち方 | 判定の場所 |
|---|---|---|
| 自前の停止の列 | 利用者の行に停止した時刻 | 現在の利用者を返す入口 |
| Better Auth の admin プラグイン | プラグインが足す停止の列 | プラグインのフック（セッションの作成）と、停止時のセッションの削除 |
| 許可リストからの削除 | 環境変数 | サインインのとき |

## 決定

### 持ち方

1. **停止は、利用者の行に停止した時刻を持つ列で表す。**
   停止を解くと、列を空に戻す。
2. **停止の列は Better Auth が生成する列ではないので、アプリの規約（snake_case）で名付ける。**

### 判定

3. **停止の判定は、現在の利用者を返す入口が毎リクエスト行う。**
   停止中の利用者は、未サインインと同じに扱う。
4. **サインインのときも、停止中の利用者にはセッションを作らない。**
   判定は許可リストの照合と同じ位置に置く。
5. **停止しても、既存のセッションの行は消さない。**

### 範囲

6. **停止中は、読み・書き・AI の呼び出しのすべてを断つ。**
7. **停止と解除は管理者（20260915-admin-flag-on-user-row）だけが行える。**
   管理者は自分自身を停止できない。

### 許可リストとの関係

8. **許可リストと停止を併存させる。**
   許可リストはサインインできる人を決め、停止はサインインできる人のうち使わせない人を決める。

決定時点の例として、停止の列は `user.suspended_at`、現在の利用者を返す入口は `getCurrentUser`、サインインのときの判定の位置は `databaseHooks.session.create.before` である。
現況は `web/prisma/schema.prisma`・`web/src/lib/auth/current-user.ts`・`web/src/lib/auth/index.ts` が持つ。

## 理由

- 20260901-session-security 決定 6 で `cookieCache` を禁じたので、入口は毎リクエスト利用者の行を DB から読んでいる。
  停止の列を同じ読み取りに足せば、往復を増やさずに次のリクエストから効く
- 20260901-session-security 帰結「移行の順序」が、停止フラグをラッパの判定で見る形を既に予定している
- 20260909-ownership-before-auth が Better Auth の表の列名を生成されたまま置いたのは、版が上がるたびに手で直さないためで、アプリが足す列にはその理由が当たらない
- 停止の列を snake_case にすれば、ドメイン型へ詰め替えずに読めるので、20260909-ownership-before-auth 決定 4 の根拠（`db.ts` が読む列に詰め替えが発生しない）が保たれる
- 列名の規約が違うことで、その列が Better Auth の生成物でないことが列名から読める
- 判定を入口の一か所に置けば、画面・Server Action・AI を呼ぶ手順のどれかで判定を書き忘れる経路ができないので、停止中はすべてを断つ
- サインインのときに断たないと、停止中の利用者がサインインするたびにセッションの行ができ、説明の無いままログインの画面へ戻される
- 入口の判定で次のリクエストから断てるので、セッションの行を消す処理は判定と重複する。
  消す処理を持たなければ、`db.ts` が Better Auth のセッションの表へ書く用途も増えない
- 20260830-invite-only-multi-user の覆る条件は、公開登録を選択肢へ戻すのを #69（管理機能）と #70（BYOK）の両方が入った後としている。
  許可リストを外す移行（20260901-session-security 帰結「移行の順序」の 4 段目）は、誰が登録できるかの決め直しを伴うので、停止を入れる回には含めない
- 停止は利用者の利用を止める権限なので、20260915-admin-flag-on-user-row の管理者の判定を通す。
  管理者が自分を停止すると、解除できる人がいなくなるので禁じる

採らなかった案と、それを採らなかった条件。

- **Better Auth の admin プラグイン**。
  停止時のセッションの削除と、停止中のサインインの拒否をプラグインが持つ（1.7.2 の `dist/plugins/admin/routes.mjs` の `banUser` と `admin.mjs` のフック）。
  migration で 5 列が増え、なりすまし・パスワードの設定・利用者の作成のエンドポイントが `/api/auth/admin/*` に加わる。
  パスワードを実装しない決定（20260909-auth-better-auth 決定 2）と招待制（20260830-invite-only-multi-user）の外にある操作を、役割の定義で閉じる作業が要る。
  停止の効き目がフックとセッションの削除の二か所に分かれ、入口の判定一か所にならないので採らなかった
- **許可リストからの削除だけ**。
  コードが要らない。
  再デプロイが要り、既存のセッションが最大 1 日残り（20260901-session-security 決定 8）、停止したことが DB に残らないので採らなかった
- **AI の呼び出しだけを断つ**。
  停止中も自分の問いとメモを読み書きできる。
  判定が AI を呼ぶ手順ごとに要り、#63（培地）のように AI を呼ぶ操作が増えるたびに足すことになるので採らなかった
- **停止のときにセッションの行を消す**。
  入口の判定を持たなくても、次のリクエストでセッションが無くなる。
  `db.ts` が Better Auth のセッションの表へ書くことになり、入口の判定と重複するので採らなかった
- **停止の列を Better Auth の表の規約（camelCase）で名付ける**。
  一つの表の中で列名の規約が揃う。
  `db.ts` がドメイン型へ詰め替えることになり、20260909-ownership-before-auth 決定 4 の根拠が崩れて改訂版が要るので採らなかった

## 帰結

- `user` 表に停止の列が 1 本加わり、migration が 1 本入る（現況は `web/prisma/schema.prisma`）
- `db.ts` が `user` 表から読む列が一つ増える。
  20260909-ownership-before-auth の覆る条件の一つ目（`db.ts` が四表の他の列を読む）に当たるが、決定 2 で詰め替えを発生させないので、20260909-ownership-before-auth 決定 4 は動かない
- 停止中の利用者のリクエストは、入口が未サインインとして返すので、ログインの画面へ redirect される。
  サインインを試しても決定 4 でセッションが作られず、#203（サインインの拒否の文言）が決めた、理由を伏せた文言が出る
- 停止しても、その利用者の問い・セッション・メモは消えない。
  停止を解くと、元どおり読める
- 20260901-session-security 決定 8（許可リストの照合をサインインのときだけにする暫定措置）は動かない。
  20260901-session-security 帰結「移行の順序」のうち、停止のフラグを足す・ラッパの判定で見る・動作を確かめる、の 3 段がこの決定で済み、許可リストを外す 4 段目だけが残る
- 20260901-session-security の理由節は、再認証の閾値（`freshAge`）を「#69（管理機能）が機微な操作を作る回に戻る」としている。
  停止は機微な操作だが、セッションの寿命が 1 日（20260901-session-security 決定 3）なので、セッションは常に閾値の内側にあり、再認証の判定は発火しない
- サインインのときの判定の位置が、許可リストの照合と停止の判定の二つを持つ
- 停止と解除の実装は、#69（管理機能）の子 issue が作る

## 覆る条件

- 停止中の利用者に、自分の問いを書き出させる必要が出たとき（手仕舞いや退会）。
  決定 6 の「すべてを断つ」を決め直す
- 許可リストを廃止してアカウント登録制へ移るとき。
  20260901-session-security 帰結「移行の順序」の 4 段目に進み、停止が利用者を拒否する唯一の手段になる
- Better Auth の本体が、なりすましやパスワードの操作を伴わない停止の機能を持ったとき。
  本体の機能へ移すかを決め直す
- Better Auth が版を上げて、`user` 表に同じ意味の列を生成するようになったとき。
  決定 2 の前提（アプリだけが足す列である）が崩れる
- 停止の後に、既存のセッションで実害が出たとき（入口の判定を経ない経路が見つかった、など）。
  決定 5 を決め直し、停止のときにセッションの行を消す
