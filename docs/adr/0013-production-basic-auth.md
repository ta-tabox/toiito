# 0013. 本番へのアクセス制限を、ホスティングでなくアプリ側の Basic 認証で持つ

- **状態**: 採用
- **決定日**: 2026-08-29
- **関係する ADR**: 0002

## 文脈

ADR 0002（本番の実行環境を Vercel にする）は四軸——App Router と Server Actions・Prisma 7 の driver adapter・AI 呼び出しの実行時間上限・費用——では差が付かず、**決め手はアクセスの制限だった**。

> Vercel Authentication は全プランで使えて Production も保護できるが、Render の IP 制限は Scale プラン、Fly.io と Railway には既製の門が無く、VPS は自分で nginx か Caddy に掛けることになる。

2026-08-29 に本番を立てて実測したところ、**この前提が誤りだった**。

Hobby で選べるのは Standard Protection だけで、その API 上の名前は `prod_deployment_urls_and_all_previews` である。
名前のとおり守るのは production の**デプロイ URL**（`<project>-<hash>-<team>.vercel.app`）と Preview であって、production の **domain**（`<project>.vercel.app`）は素通しになる。
シークレットウィンドウでも Safari でも、ログインを求められずアプリへ到達することを確認した。
本番まで囲える `all`（All Deployments）は Pro の Advanced Deployment Protection（月 150 ドル）が要る。

アクセス制限が無いまま migration を流せば、URL を知っている誰でも問いを投げられ、`ANTHROPIC_API_KEY` で課金が走る。
このアプリに削除 UI は無いので、投げ込まれた行はそのまま残る。

## 決定

**アクセス制限をホスティングからアプリへ移す。**
`web/src/proxy.ts` が Basic 認証を掛け、判定は `web/src/lib/basic-auth.ts` の純関数が持つ。

- 資格情報は `TOIITO_BASIC_AUTH_USER` と `TOIITO_BASIC_AUTH_PASSWORD` の二本
- **両方無ければ認証を掛けない。ただし `NODE_ENV` が production なら投げる**
- 片方だけでも投げる
- **matcher を書かず、全リクエストを通す**
- 旧 `middleware` 規約でなく `proxy` 規約で書く
- Vercel Authentication は無効化しない。
  デプロイ URL と Preview はあちらが守り続ける

`#68`（ログイン（Google OAuth）とリソースの所有権）が入ったら、この Basic 認証ごと外す。

## 理由

`ARCHITECTURE.md`「意図的にやらないこと」は「マルチユーザー対応の作り込み（自分専用。**Auth は門としてのみ**）」と書いており、アクセスを制限すること自体は許している。
Basic 認証は所有権の概念を持たず、通すか通さないかしか決めないので、この線の内側に収まる。

`proxy.ts` は Next.js の標準機能で `next start` の自己ホストでも動く。
ADR 0002 の禁止則が挙げる `@vercel/*` の import・ISR のオンデマンド再検証・Edge Config・Cron Jobs のどれでもない。
**副産物として、アクセス制限が Vercel 依存でなくなる**。

**設定が無いときに素通しへ倒さなかった条件**: 今回の失敗が「掛けたつもりの制限が掛かっていなかった」ことだったので、同じ形をもう一度作らない。
production で資格情報が欠けていればモジュールの評価時に投げ、リクエストを捌く前に落ちる。
development では素通しするので、`pnpm dev` と E2E は認証を知らずに済む。

**旧 `middleware` 規約を採らなかった条件**: Next 16 が非推奨にしており、既定が Edge ランタイムになる。
Edge の `process.env` は Next が注入した数個しか持たず、`TOIITO_BASIC_AUTH_*` も `NODE_ENV` も実行時に undefined になる（2026-08-29 に生成物で確認。ビルド時置換も掛からず `process.env.X` の綴りが残る）。
**素通しへ倒す分岐だけが生き残る**ので、守りたい場面でだけ効かない形になっていた。
`proxy` は常に Node.js ランタイムで走ると規約が決めているので、この危険が構造から消える。

**`VERCEL_ENV` でなく `NODE_ENV` を見る条件**: 前者はホストに固有で、他所へ移した日に未定義となり、判定が黙って素通し側へ落ちる。

**matcher を書かなかった条件**: 除外の綴りを誤ったとき、その経路だけ制限の外に出たことが誰にも見えない。
全部通す方が遅いが、失敗が見える。

**cookie 形の認証を採らなかった条件**: 入口の摩擦は小さくなるが、入力画面と署名の鍵が増え、`#68` で捨てるコードがその分多くなる。
Basic 認証はブラウザがダイアログを持つので画面を作らずに済む。
実際に毎回聞かれて煩わしければ、そのとき差し替える。

**Pro + Advanced Deployment Protection（月 170 ドル）を採らなかった条件**: この器の規模に釣り合わない。

**`#68` を前倒しする案を採らなかった条件**: 本命ではあるが、前提の `#65`（認証と所有権の方式を決める）が未決なので、本番を開けたまま待つ時間が長くなる。

## 検証の層

判定の単体テスト（`web/tests/basic-auth.test.ts`）と `proxy` の戻り値のテスト（`web/tests/proxy.test.ts`）は、関数が正しい値を返すことしか言えない。
**今回の二つの失敗は、どちらもそこから見えない場所にあった**——設定上は掛かっている制限が、実際のリクエストでは通っていた。

だから層を二つ足す。

- `web/e2e/basic-auth.spec.ts`（L4）。
  資格情報を持つサーバーを別に立てて、実際に 401 が返るかを見る。
  退行を捕まえるための層で、**Vercel のランタイム差は再現しない**
- `DEPLOY.md`「アクセス制限」の curl。
  本番の URL を直接叩いて 401 を確かめる。
  今回の二つを実際に捕まえられるのはここだけなので、デプロイの手順に組み込む

## 帰結

- `web/src/**` に認証が入る。
  #90（本番環境へデプロイする）と #96（本番の migration 経路を通す）がどちらも触らないと決めていた場所で、この ADR がその例外を作る
- 本番の環境変数が 3 本から **5 本**になる（`DEPLOY.md`「秘密の置き場」）
- **ADR 0002 は supersede しない**。
  決定（Vercel を使う）は動いておらず、崩れたのはそれを支えていた事実の一つである
- ただし **ADR 0002 の決め手は失われた**。
  四軸では差が付かなかったので、次に実行環境を問い直すとき——たとえば Cloudflare Workers の CPU 予算を実測したとき——**アクセス制限は比較の材料にならない**。
  この制限がアプリ側にある以上、どの候補へ移しても一緒に付いていく
- Preview のデプロイは環境変数を持たないのでビルドが落ちる。
  制限の有無以前に到達できない状態は変わらない

## 覆る条件

- **`#68` が入ったら外す**。
  所有権を持つ認証が入れば、通すか通さないかだけの制限は要らなくなる
- 入口の摩擦が常用を妨げたら。
  Basic 認証のダイアログが毎回出るなら cookie 形へ差し替える（判断は L5 の官能で、実測してから）
- 他人へ開く段になったら。
  共有の秘密一つで全員を通す形は、そこで破綻する
- Vercel が Hobby でも production domain を守れるようにしたら。
  ホスティング側へ戻す選択肢が復活するが、**戻す理由は薄い**——アプリ側の制限は移植性の面でむしろ勝っている
