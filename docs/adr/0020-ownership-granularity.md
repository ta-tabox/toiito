# 0020. 所有権を、所有のルートにだけ持たせる

- **状態**: 採用
- **決定日**: 2026-08-30
- **関係する ADR**: 0005, 0018, 0019

## 文脈

0018 で招待制へ開くと決まり、リソースに持ち主が要ることになった。

粒度の候補は二つあった。
`questions` にだけ `user_id` を持たせて下位は親から辿るか、全テーブルに持たせるかである。
前者は join が増え、後者は不整合の余地が増える。

`questions` だけの話には閉じない。
#64（ペルソナをテーブルへ）が `questions` の子ではない独立のルートを足すためである。

## 決定

1. **所有のルートにだけ `user_id` を持たせる。**
   いまは `questions` 一つで、#64（ペルソナをテーブルへ）が入れば `persona` が二つ目のルートになる。
2. **`sessions` / `messages` / `memos` は持たない。**
   所有者は親から辿る。
3. **絞り込みは `db.ts` の repo 関数が行う。**
   UI 側でやらない。
4. **`user_id` は NOT NULL。**
   持ち主のいない行を作らない。
5. **既存データは移送しない。**
   本番のレコードは作り直す。
   backfill を書かない。

## 理由

**逆引きが最悪ケースに見えて、実際には最も安いところに当たる。**
`listMemosWithContext` は `memos → messages → sessions → questions` を一本の join で引くと決まっている（`ARCHITECTURE.md`「データモデル」。N+1 に割らないため）。
所有者の条件はその join の先に `where` が一つ増えるだけで、**追加の join がゼロ**である。
`db.ts` の読み取り 8 本のうち、辿る段数が 3 になるのは `listMemosForSession` と `listMemosWithContext` の二本だけで、後者は既にその経路を持っている。

**全テーブルに持たせる案を採らなかった条件は、join でなく書き込み側にある。**
`addMessage` / `addMemo` / `createSession` が `user_id` を受け取ることになり、その値の出所は結局のところ親の行である。
つまり全テーブル案は「親の `user_id` をコピーする」処理を書き込み経路の各所へ置く設計で、コピーの置き忘れと取り違えがそのままずれになる。
ずれた状態は、**セッションの一覧には出ないのに URL を直に叩けば読める発話**として現れる——#68（ログインと所有権）が「存在の有無も漏らさない」と書いた要求の、ちょうど裏をかく形である。
ずれを DB で弾くこともできるが、`sessions(id, user_id)` に unique を張って `messages(session_id, user_id)` から複合外部キーを引く形になり、**全テーブルの外部キーが 2 列になる**。
#64（ペルソナをテーブルへ）がペルソナの版を「ID + 版」の複合キーで持つ案を落とした条件（外部キー参照が全部 2 列になるので避けたい）を、今度は全テーブル分引き受けることになる。

**`memos` にだけ冗長に持たせる案を採らなかった条件**: 逆引きの入口で join を省ける案だが、上のとおりその join は既に存在する。
得るものが無い。

**移送しない条件は 0005 と同じ「まだ作り直せる段階か」である。**
0005 の覆る条件は「本番にデータが乗って消えて困るものができた時点」だった。
本番は 2026-08-29 に立ったが、載っている行は作り直してよいと人間が判断している（2026-08-30）。
条件は反転していない。
backfill を書けば、一度しか走らない処理が migration へ恒久的に残る——0005 が落としたのはまさにその形だった。

## 帰結

- `ARCHITECTURE.md`「データモデル」に所有権の節が入り、`questions` の列に `user_id` が加わる
- **`user_id` の型は Better Auth の `user.id` に合わせる。**
  既存の主キーは `@db.Uuid` だが、Better Auth の ID 生成を曲げると再生成のたびに差分が出るので、合わせる側はこちらになる（実際の型は #68（ログインと所有権）が生成して確かめる）
- `pnpm seed` は所有者つきになる（#68（ログインと所有権））
- ADR 0005 は覆らない
- 削除機能を入れる回に、親を消したときの子の扱いを決めることになる。
  いまこの器に削除 UI は無く、`messages` は immutable なので、まだ踏む地面ではない

## 覆る条件

- **削除機能を入れるとき。**
  親を消せる形になると、子が孤児になる経路ができる。
  所有権が親の存在に依存するという性質が、そこで初めて代償になる
- 所有のルートが増えて、辿る段数がいまより深いテーブルが出てきたら。
  現状の最深は 3 段で、そこには既に join がある
- 実測で逆引きが遅いと分かったら。
  **段数から遅いと決めない**——まだ測っていない
- 本番に消えて困るデータが載ったら。
  0005 の覆る条件がそのまま効き、以後の破壊的なスキーマ変更は同じ基準では判断できない
