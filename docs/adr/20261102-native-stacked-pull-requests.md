# スタック型 PR を GitHub のスタック機能で積み、マージの後の積み直しを GitHub に任せ、マージは最下段の PR でだけ押す

- **状態**: 採用
- **決定日**: 2026-11-02
- **関係する ADR**: 20261102-stacked-pull-requests

## 文脈

#64（二体のペルソナをセッション単位で設定できるようにする）と #70（利用者ごとのモデルと API キー）の子 issue は、前の段の表と repo 関数を前提にする列になっている。
「1 セッション = 1 PR」では、後ろの段を前の段のマージ前に書けない。

20261102-stacked-pull-requests は、列をスタック型 PR で積み、積み直しを rebase と main 以外への `--force-with-lease` で手で行うと決めた。
その覆る条件に「GitHub のスタック機能が有効になり、積み直しを GitHub が行うようになったら」を置いていた。
#64 の 1 段目と 2 段目の PR は、GitHub のスタック機能でスタックにした。

GitHub のスタック機能は、次の三つの点で手の積み直しと振る舞いが違う。

| 操作 | GitHub のスタック機能の振る舞い |
|---|---|
| ある段の PR のマージ | その段より下にある未マージの PR もまとめて main へ入る |
| マージの後の残りの段 | GitHub が base へ rebase し直す |
| スタックへ PR を足す | PR のヘッダの「Add to stack」か、CLI の `gh stack`（add / submit / sync / modify） |

Claude のクラウドのセッションは、gh を検索にしか使えず、決定時点の gh（2.89.0）は `stack` コマンドを持たない。

## 決定

1. 列は 1 issue 1 PR で積み、各 PR のベースを一つ下の段のブランチにして、GitHub のスタックへ入れる
2. CI の `check` は、ベースを問わずすべての PR で走らせる
3. マージの後の積み直し（残りの段の rebase とベースの付け替え）は GitHub に任せ、人間も Claude も手で行わない
4. 下の段へコミットを足したときの上の段の積み直しは、`gh stack` を使えるセッションでは `gh stack` で行う
   `gh stack` を使えないセッションでは rebase で行い、main 以外の名前付きブランチへの `--force-with-lease` は Claude が訊かずに叩いてよい
5. マージは毎回人間が判断し、押すのはスタックの最下段にある未マージの PR だけにする
6. Claude がスタックへ PR を足す手段は `gh stack` にする
   `gh stack` を使えないセッションでは、Claude はベースを一つ下の段にした PR を作り、人間が PR のヘッダの「Add to stack」でスタックへ入れる

## 理由

- 各 PR の差分が一段分に収まる
- GitHub がマージの後の rebase とベースの付け替えを行うので、段がマージされるたびの手の積み直しが要らない
- 上の段でマージを押すと下の未マージの段がまとめて main へ入り、main への push ごとに起きる本番デプロイと migration が段ごとに分かれない
- #64 の段は migration を段ごとのデプロイを挟む前提で割っているので、段を一つずつ入れる条件は人間がマージを押す PR の選び方でしか守れない
- merge コミットで積み直すと、下の段が動くたびに上の段すべてに取り込みのコミットが増える
- lease は他者が後から push した ref を上書きせずに失敗する
- Claude は画面を操作しないので、UI の「Add to stack」を Claude の手段にできない

採らなかった案:

- **列を一つの PR にまとめる**
  レビューの単位が列全体になる
- **merge コミットで積み直す**
  複数人で同じスタックへ push するなら採る
- **マージの後の積み直しも rebase と `--force-with-lease` で手で続ける**
  GitHub が同じブランチを rebase するので、手の積み直しと二重になる
  スタック機能を使わなくなったら採る
- **main 以外への `--force-with-lease` の例外を外し、毎回人間に訊く**
  `gh stack` を使えないセッションでは、下の段を直すたびに上の段の数だけ諾否が要る
  Claude のすべてのセッションが `gh stack` を使えるようになったら採る
- **人間が UI で積み直しも追加も行い、Claude は PR を作るだけにする**
  `gh stack` を使えるセッションでも人間の手が段ごとに要る
- **`gh stack` を `.claude/settings.json` の allow に足す**
  `gh stack sync` が内部で行う push の形を一次資料で確かめていないので、既定の判定（訊く）に置く
  挙動を確かめたら足すかを決め直す

## 帰結

- `docs/ROADMAP.md` の横断規約「1 セッション = 1 スタック」から、マージの後の rebase とベースの付け替えの手順が外れ、マージを押す PR を最下段に限る
- `CLAUDE.md` の git 節の `--force-with-lease` の例外が、下の段を直したときの積み直しで `gh stack` を使えないセッションに絞られる
- `check.yml` の pull_request は、ベースを絞らないまま変えない
  スタックの上の段のベースは一つ下の段のブランチのままである
- `guard-force-push.sh` は、main 以外への lease 付き push を人間に回さない判定を変えない
  フックは `gh stack` を使えるセッションかを知らないので、使い分けは `CLAUDE.md` の git 節が持つ

## 覆る条件

- 一つのスタックへ複数の人やセッションが push するようになったら
- Claude のすべてのセッションで `gh stack` を使えるようになったら
- GitHub のスタック機能で、上の段のマージが下の未マージの段をまとめて入れなくなったら
- GitHub のスタック機能を使わなくなったら
