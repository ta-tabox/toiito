# 0017. `status` の値域を、比喩を外して組み直す

- **状態**: 採用
- **決定日**: 2026-08-30
- **関係する ADR**: 0016

## 文脈

`status` の値域に、二つの問題が同時に見つかった。

**一つ目は、値が比喩を持っていたこと。**
6 値のうち `composting`（堆肥化）と `fermented`（発酵）が中心メタファーから直接取られていた。
0016 で比喩をコンポスターから醸造へ移したところ `composting` が乗らなくなり、**比喩を選び直しただけで migration が 1 本出た**。
比喩は選び直しうる（0016 自身が「覆る条件」を二つ持っている）が、enum の変更は本番の DB とアプリの両方を動かす。
変わる頻度の違うものが同じ層に置かれていた。

**二つ目は、`closed` の割り残し。**
2026-07-19 に旧 3 値の `closed` を「二つの別物を潰している」として `promoted`（別の置き場へ書き出した）と `discarded`（棄却）へ割った（`ARCHITECTURE.md`「問いの状態機械」）。
常用の中で、**実際は三つ潰していた**ことが分かった。
書き出した / 捨てた / **解決して閉じた**、の三つである。
三つ目に置き場が無いので、解決して手元から下げたい問いを `discarded` へ流すしかない。
`discarded` は積極的に追わないという判断で、削除に近い。
解決して閉じることとは別物である。

## 決定

値は比喩を持たない一般語で持ち、比喩は UI のラベルだけが持つ。
併せて `resolved` を足し、7 値にする。

| status | ラベル | 意味 | 旧 |
|---|---|---|---|
| `new` | 仕込み中 | 仕込んだが、まだ材料が付いていない | `composting` |
| `stocked` | 発酵 | 材料が付き、蒸留に入れる | `fermented` |
| `resolved` | 一旦閉じた | 答えが出て閉じた。別の置き場へは書き出していない | —（新規） |
| `exported` | 結晶した | 答えが出て、別の置き場へ書き出した | `promoted` |
| `holding` | 持ち続ける | 答えが出ないことは欠陥ではない | `open` |
| `permanent` | 閉じない問い | 閉じないことが正しいので、閉じ候補として催促しない | `perennial` |
| `discarded` | 棄却 | 積極的に追わないという判断だけを指す | 据え置き |

ラベルの正は `VISION.md`「語彙」節。
**比喩が動いたらラベル列だけが動き、値の列は動かない。**

移行は #125（`status` を一般語へ組み直し、`resolved` を足す）が運ぶ。

## 理由

**比喩を選び直すたびに migration が出るのは、層の置き方の誤りである。**
器の名前を替えただけで DB の値の綴りを決める段が生じたので、0016 の作業がそれを実証している。
値が答えるべきは「アプリがこの問いをどう扱うか」であって、「いま何の比喩を使っているか」ではない。

**6 値すべてを組み直したのは、境目を残さないためである。**
比喩由来なのは 2 値だけだったので、その 2 値を替えれば当面は動く。
採らなかったのは、**残る 4 値が「たまたま一般語だった」だけで原則の適用を受けていない**からで、境目が語の見た目にしか無い状態は次の書き手に伝わらない。
`promoted`（何から何への昇格か語が言わない）を `exported` にし、`open` と `perennial`（どちらも「閉じない」で語からは差が付かない）を `holding` と `permanent` に割ったのは、この機会に意味を語へ寄せられるからである。

**`resolved` を足すと、`discarded` の位置づけも確定する。**
足す前は、解決して閉じたい問いの行き先が `discarded` しか無く、棄却でないものを棄却として記録することになっていた。

**VISION の「暫定解に逃げない」とは衝突しない。**
逃げ道になるのは、閉じる以外の選択肢が無いときである。
`holding`（答えが出ないことは欠陥ではない）と `permanent`（閉じないことが正しい）が並立しているので、閉じるのは選択であって既定ではない。

**UI ラベルは一般語にしない。**
画面の語まで一般語にすると、`VISION.md` が「仕込みは気軽に」と言っている手触りが失われる。
比喩が仕事をするのは人間が読む側で、機械が突き合わせる側では邪魔にしかならない。

**採らなかった案。**

- **`composting` だけを `mashing` へ移す**（#125 の当初の内容）。
  1 値で済み migration も小さい。
  採らなかったのは、次に比喩が動いたときに同じ作業がまた出るからで、これは原因でなく症状への対処である
- **enum を触らず UI ラベルだけ差し替える**。
  migration が要らない。
  採らなかったのは、DB の値と画面の語が食い違ったまま残るからで、`status` を読む人が値と表示のどちらを意味の正と取るかで迷う
- **`exported` を畳んで `resolved` 一つにする**（書き出したかどうかは status で持たず、昇格を実装するときに別の列で持つ）。
  status の軸が「問いが生きているか」一本に揃うので、設計としては綺麗である。
  採らなかったのは、`ARCHITECTURE.md` が「発酵の終点は一つではなく、結晶と持続が並立する」と書いており、**外部化が終点の一つとして意味を持っている**からで、畳むとその区別が status から消える
- **`archived` を足す**（理由を問わず手元から下げる）。
  採らなかったのは、2026-07-19 に `closed` を廃した理由と同じ形になるからで、理由を語が言わない値は次に別物を潰す

## 帰結

- `VISION.md`「語彙」節の `status` 表が、値とラベルを別の列として持つ。
  比喩の変更で動くのはラベル列だけになる
- #125 の範囲が、1 値の改名から**改名 6 本と追加 1 本**へ広がる。
  Postgres の enum は `ALTER TYPE ... RENAME VALUE` で改名でき `ADD VALUE` で足せるので、同じ migration に収まる。
  データの入れ替えは要らない
- `ARCHITECTURE.md`「問いの状態機械」の表と、「`closed` が二つの別物を潰しており」の一文（三つへ直す）は #125 が同時に追随する。
  あの文書が持つのは現況なので、enum が動く前に書き換えると現況の正が現況と食い違う
- 以後、新しい状態を足すときは一般語で足す。
  比喩側の呼び名は `VISION.md` のラベル列が持つ

## 覆る条件

- **`status` を人間が直接読む場所ができたとき**。
  いまは値がコードと DB にしか出ないので、この層分けが成立する。
  API を公開して値がそのまま外へ出るなら、値の読みやすさが表示の都合と衝突するので決め直す
- **昇格（`extensions/fermentation-and-outlets.md` の工程 6）が実装され、書き出したかどうかを別の列で持てるようになったとき**。
  そのとき `exported` を `resolved` へ畳めるか問い直す
- 「一旦閉じた」が実際には `holding` と区別されずに使われたとき。
  区別が人間の側で立たないなら、値としては存在しないのと同じである
