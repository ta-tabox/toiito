# 0043. ペルソナをテーブルにし、当時の設定を発話が指す（0032 の改訂）

- **状態**: 採用
- **決定日**: 2026-09-15
- **関係する ADR**: 0008, 0017, 0021, 0025, 0030, 0032, 0035, 0036, 0037

**0032 を supersede する**。
動いたのは決定 8・9 で、0032 が #64 に残した論点のうち四つもここで決めた。
残りは 0032 の本文を複写している（ADR 規約 4）。
複写した決定は、規約 7 に合わせて表名と列名を決定時点の例へ移したが、意味は変えていない。
何がどう動いたかは下の「0032 から動いたところ」。

**0030 は supersede しない。**
`messages` に `user_id` を足さないので、0030 決定 2 は動かない（理由は「理由」節の「発話者」）。

**0021 も supersede しない。**
0021 の決定（深さをプロバイダの設定として持つ）は動かない（理由は「理由」節の「深さ」）。

## 文脈

`docs/ARCHITECTURE.md` は、ペルソナの可変化を次の二箇所で先送りしている。

| 節 | 記述 |
|---|---|
| 技術スタック（確定事項） | 固定ペルソナ二体。MVP は可変化しない（発酵後に再検討） |
| 二体 AI のオーケストレーション | 具体派（`ai_a`）と抽象派（`ai_b`）の固定二体 |

#64（二体のペルソナをセッション単位で設定できるようにする）が、発酵後の再検討にあたる。
固定二体では、問いの種類によらず同じ観点からしか問いを扱えない。
合成関数にパラメータを渡す案（`composePersona(id, params, custom?)`）は、ペルソナの数が二体に固定されたままになるので、2026-08-30 に採らないと決めた。

ペルソナをレコードにすると、決めることが四つ出る。
四つのうち二つは既存の ADR と重なる。

| 論点 | 重なる ADR | 重なり方 |
|---|---|---|
| 既定のペルソナを全員で共有するか、利用者ごとに複製するか | 0030 決定 1 | ペルソナを二つ目の所有のルートと見込んでいるが、既定のペルソナの持ち主は決めていない |
| 編集できるペルソナで、過去の発話から当時の定義をどう復元するか | なし | |
| 発話者の enum の `ai_a` / `ai_b` が消えた後、発話者をどう表すか | 0030 決定 2 | 発話者を「種別 + 参照先」に分けると `messages.user_id` を足す案が出るが、0030 は `sessions` / `messages` / `memos` に `user_id` を持たせないと決めている |
| 「思考: 具体 ↔ 抽象」のようなパラメータを、レコードの列にするか | なし | |

0032 は四つの論点を決め、さらに次の四つを決めずに #64 へ残した。

| 論点 | 0032 が決めなかった理由 |
|---|---|
| 深さ（`effort`）を版の列にするか | 0021 が深さを Anthropic 固有の設定と決めており、列にするとプロバイダ固有の値がレコードに入る |
| 既存の `messages` を削除するか、既定のペルソナの版へ寄せるか | #64 本文の「本番のレコードは作り直してよい」（2026-08-30）は本番が止まる前提の判断で、本番はその後も動き続けている |
| パラメータの軸と各軸の値域 | 0032 が決めたのは持ち方だけだった |
| システムのユーザーと既定のペルソナの行を、migration と `pnpm seed` のどちらが作るか | 本番にも行が要るので、開発用の seed だけでは足りない |

四つを決めると、0032 決定 8（パラメータと自由記述の持ち方）と決定 9（既定のペルソナの設定の正の置き場）が動く。

## 決定

### テーブルの形

1. **ペルソナを、同一性を持つ表と設定の版を持つ表の二段にする。**
2. **版の表は、ペルソナと版番号の組を一意にし、主キーは単一の id にする。**
3. **版の表に、親の版を指す列を持たせない。**
   版はペルソナごとの連番で、分岐を許さない。

決定時点の例は次のとおりで、現況は `web/prisma/schema.prisma` が持つ。

| 表 | 列（抜粋） | 持つもの |
|---|---|---|
| `persona` | `id`, `user_id` | 同一性。#75（ペルソナに、セッションを跨いだ記憶を持たせる）の記憶を紐づける先 |
| `persona_config` | `id`, `persona_id`, `version`, 三つの軸, 自由記述, 合成済みの全文 | 設定の版。`@@unique([persona_id, version])` |
| `messages` | `speaker`, `persona_config_id` | 発話の時点の版を指す |

### 既定のペルソナと利用者のペルソナ

4. **既定のペルソナは、システム所有のユーザー行が持つ。**
   ユーザー行の email は到達不能なアドレスにし、ペルソナの持ち主の列は NOT NULL のままにする。
5. **利用者が既定のペルソナを編集した時点で、利用者所有の新しいペルソナを作り、編集後の設定をその版 1 にする。**

| ペルソナ | 持ち主 | 見える利用者 | 編集したとき |
|---|---|---|---|
| 既定 | システムのユーザー | 全員 | 利用者所有の新しいペルソナを作る |
| 利用者所有 | その利用者 | 本人だけ | 同じペルソナに次の版を足す |

repo 層は、持ち主が現在のユーザーかシステムのユーザーであるペルソナを返す。
決定時点の例として、システムのユーザーの email は `system@toiito.invalid` の形である。

### 発話者

6. **発話者は種別と参照先の版で表し、発話の表にユーザーを指す列を足さない。**
7. **発話の種別は、人間と AI の 2 値にする。**

| 種別 | 参照先の版 | 発話者の辿り方 |
|---|---|---|
| 人間 | NULL | 発話 → セッション → 問いの持ち主 |
| AI | NOT NULL | 発話 → 版 → ペルソナ |

種別と参照先の版の対応は Prisma スキーマで表明できないので、check 制約として migration の SQL に置く。
決定時点の例として、発話の表は `messages`、種別は `speaker`（`human` / `ai`）、参照先の版は `persona_config_id`、足さない列は `messages.user_id` である。
現況は `web/prisma/schema.prisma` が持つ。

### パラメータとシステムプロンプト

8. **版は、パラメータ・自由記述・合成済みのシステムプロンプトの全文の三つを持つ。**
   パラメータは次の三つの軸で、どの軸も順序を持つ 5 段階の enum にする。

| 軸 | 1 の端 | 5 の端 | 発話に出る違い |
|---|---|---|---|
| 抽象度 | 具体 | 抽象 | 例となる場面を問う ↔ 背後の前提と構造を問う |
| 異論の強さ | 受容 | 対抗 | 相手の言葉に沿って問いを重ねる ↔ 反例と異論を正面から出す |
| 発散と収束 | 発散 | 収束 | 周辺の問いを増やす ↔ 問いの焦点を一つに絞る |

9. **文言の節は、軸と段階の組ごとに一つ持ち、軸の組み合わせごとには持たない。**
10. **システムプロンプトは、共通の節・パラメータの節・自由記述を合成した全文とし、版を作るときに合成して版に残す。**
    AI の呼び出しに渡すのは、版に残した全文である。
11. **共通の節は、「答えを与えない」を実装する禁止事項と材料の供給規律の二つとし、コードが持つ。**
    共通の節は全ペルソナの合成に必ず入り、利用者は編集できない。
12. **既定のペルソナのパラメータと自由記述は、文言の節と同じくコードが正を持つ。**
    版の表が持つのは、コードで合成した結果の記録である。
    決定時点の例として、`web/src/personas/*.md` の文面が共通の節・パラメータの節・既定の二体の自由記述へ分かれる。
    現況は `web/src/lib/personas.ts` が持つ。

| 欄 | 持ち方 | 前例 |
|---|---|---|
| パラメータ | DB の enum・TS の値域配列・絞り込み関数の三つ | `QuestionStatus`（`web/src/lib/question.ts` の `QUESTION_STATUSES` と `isQuestionStatus`） |
| 自由記述 | 文字列 | `web/src/personas/*.md` の、共通の節とパラメータの節を除いた文面 |
| 合成済みの全文 | 文字列 | なし |

### 深さ

13. **思考の深さはペルソナの設定に持たせず、アプリ全体で一つにする。**
    当時の深さは、モデル名と同じく版に残らない。
    決定時点の例として、系統ごとの二つの環境変数（`TOIITO_ANTHROPIC_EFFORT_CONCRETE` / `TOIITO_ANTHROPIC_EFFORT_ABSTRACT`）が一つになる。
    現況は `web/README.md` が持つ。

### 既存の発話と行の作り方

14. **既存の AI の発話は消さず、移行の時点で本番が使っていたシステムプロンプトの全文を既定の二体の版 1 として残し、そこへ寄せる。**
    具体の発話は具体の既定のペルソナの版 1 へ、抽象の発話は抽象の既定のペルソナの版 1 へ寄せる。
    版 1 の全文は合成の結果でなく、移行の時点のシステムプロンプトそのものである。
15. **システムのユーザー・既定の二体・版 1 は、既存の AI の発話を寄せる migration が作る。**
    AI の発話が一件も無い DB では、migration は行を作らない。
16. **版 1 より後の既定の版は、同期が作る。**
    同期とは、コードで合成した既定の各ペルソナの全文が最新の版と違うときに次の版を足し、システムのユーザーと既定のペルソナが無ければそれらも作る処理である。
    同期の書き込みは repo 層の関数を通し、本番ではデプロイの migration の後に実行する。

## 理由

### テーブルの形

- **二段に分ける**: `messages` は immutable なので、編集できる定義をペルソナの id だけで指すと、過去の対話を読み返したときに当時の設定を復元できない。
- **同一性を別の表に残す**: #75（ペルソナに、セッションを跨いだ記憶を持たせる）の記憶は、版をまたいで続く持ち主を要する。
- **問いの原型と同じ形にする**: `docs/ARCHITECTURE.md`「原型と現在の形」は原型を書き換えずに現在の形を別に持つ形を採り、#57（再訪で過去セッションが読めなくなる。メモが指すセッションごと設計し直す）も過去を当時の姿で読めることを要求した。
- **主キーを単一の id にする**: `messages` からの外部キーが 1 列で済む。
- **親の版を持たない**: 分岐を許さなければ版の前後は版番号の大小で分かり、親を辿る再帰クエリも要らない。

採らなかった案。

- **ペルソナの表に版番号の列を足し、1 枚の表でペルソナと版番号の組を一意にする**: `messages` からの外部キーが 2 列になり、ADR 0030 が全テーブルへ `user_id` を持たせる案を退けた条件と同じ費用を負う。
- **`messages` に設定のスナップショットを持たせる**: 同じ設定が発話の数だけ複製され、ある設定で話した発話を設定から検索できなくなる。

### 既定のペルソナと利用者のペルソナ

- **システム所有のユーザー行を作る**: ADR 0030 決定 4（持ち主のいない行を作らない）が、二つ目の所有のルートであるペルソナにも当たる。
- **email を到達不能なアドレスにする**: ログインは Google OAuth だけ（ADR 0036 決定 3）なので、実在しないアドレスのユーザーとしてログインする経路が無い。
- **ユーザー行を一行作る形には前例がある**: ADR 0037 決定 6 は、migration で既定のユーザーを一行作り、既存の問いをそのユーザーへ寄せた。
- **編集で新しいペルソナを作る**: 既定のペルソナの下に利用者の版を足すと、ペルソナに紐づく #75 の記憶が全利用者で一つに混ざる。
- **既定の改善が複製へ届かないことを受け入れる**: 届く形（全員が既定の 1 レコードを参照し続ける形）では利用者がペルソナを編集できず、#64 の「自分のものを作る」を満たせない。

採らなかった案。

- **ペルソナの持ち主の列を nullable にし、NULL をシステム所有と読む**: NULL が「持ち主がいない」と「入れ忘れ」を同じ値で表し、DB が入れ忘れを拒否できない。
- **`is_default` のような真偽値を別の列に置く**: 二つの列が同じ事実を表し、`is_default` が真なのに利用者を持ち主に持つ行を作れる。
- **既定のペルソナをソースコード上の定義として持ち、利用者ごとに最初から複製する**（#64 の本文にあった案）: 編集していない利用者の分まで、同じ設定の行が利用者の数だけ増える。

### 発話者

- **発話の表にユーザーを指す列を足さない**: 一つのセッションで話す人間は一人なので、人間の発話者はセッションから問いの持ち主で一意に決まり、列を足しても新しい事実が入らない。
- **ADR 0030 決定 2 の条件が同じく当たる**: 発話者としての `user_id` も値の出所が親の行なので、0030 が退けた「親の `user_id` を書き込み経路の各所でコピーし、コピーし忘れがずれになる」形になる。
- **所有権の列と区別する手段が無い**: スキーマ上は所有権の `user_id` と同じ 1 列になり、「この列は所有権ではない」という約束を repo 層の規律だけで守ることになるので、機械が検査できない。
- **種別を NOT NULL の列として持つ**: 参照先の版が NULL の行が人間の発話なのか入れ忘れなのかを、check 制約が種別を見て区別できる。
- **check 制約を migration の SQL に置く**: Prisma スキーマは列の間の対応を表明できず、`memos_anchor_range_check` も同じ置き場にある。

採らなかった案。

- **種別 + 参照先の版 + `user_id`**（#64 の本文にあった案）: 所有権の列と同じ 1 列が `messages` に入り、ADR 0030 決定 2 を supersede することになる。
- **種別を持たず、参照先の版が NULL の行を人間の発話と読む**: NULL が「人間の発話」と「AI の発話で参照先の版を入れ忘れた行」を同じ値で表し、DB が入れ忘れを拒否できない（ペルソナの持ち主の NULL をシステム所有と読む案を採らなかった条件と同じ）。
- **種別を持たず、`user_id` と参照先の版のどちらか一方だけが値を持つ check 制約を置く**: 入れ忘れは拒否できるが、`messages` に `user_id` が入るので、ADR 0030 決定 2 を supersede することになる。

### パラメータとシステムプロンプト

- **軸を複数持ち、段階で持つ**: 二値の軸が一つだけでは既存の二体の差しか表せず、問いに合わせて相手の傾向を選び直せない。
- **5 段階を書き分けられる見込みがある**: 特性を 9 段階の程度の語で書き分けたプロンプトで、12 モデル中 11 モデルの性格検査の得点が、指定した段階と強く相関した（Serapio-García ほか 2023, arXiv:2307.00184。ρ ≥ 0.80）。
- **抽象度を軸にする**: 既存の二体の差（具体への引き下ろしと抽象への引き上げ）がこの軸の両端に当たる。
  解釈レベル理論は抽象度を連続量として扱い（Trope & Liberman 2010, Psychological Review 117(2)）、行為同定理論も「どうやって」と「なぜ」の水準を区別する（Vallacher & Wegner 1987, Psychological Review 94(1)）。
  心理的距離が抽象度を上げるという個別の効果には追試の失敗があるが、この軸が使うのは抽象度を連続量として扱う枠組みだけである。
- **異論の強さを軸にする**: 少数者の異論は発散的な思考を促し（Nemeth 1986, Psychological Review 93(1)）、役として割り当てた反論より本気の異論の方が多くの思考を引き出す（Nemeth, Brown & Rogers 2001, European Journal of Social Psychology 31(6)）。
  推論は、相手の論を評価する対話の中で精度が上がる（Mercier & Sperber 2011, Behavioral and Brain Sciences 34(2)）。
- **発散と収束を軸にする**: 発散的思考と収束的思考は別の操作として区別され（Guilford 1967, The Nature of Human Intelligence）、答えに早く閉じたがる傾向は認知的閉合欲求として測られてきた（Kruglanski & Webster 1996, Psychological Review 103(2)）。
- **収束の端でも答えを出さない**: 収束は問いの焦点を絞る操作に限り、ADR 0035 の「一方向に閉じた材料を出さない」はどの軸のどの段階にも効く。
- **値へ比喩を持ち込まない**: 比喩は選び直すことがあるが、enum の値の変更は本番の DB に migration を要する（ADR 0017）。
- **DB の enum・TS の値域・絞り込み関数の三つで持つ**: DB の enum と TS の値域がずれると `tsc` が失敗する。
- **節を軸と段階の組ごとに持つ**: 組み合わせごとに持つと 3 軸 5 段階で 125 節になるが、軸と段階の組ごとなら 15 節で済む。
- **合成済みの全文を版に残す**: 節の文言の正はコードにあるので、文言を直した時点で、同じ値を持つ過去の版の意味が変わる。
  全文を版に残せば、過去の発話が当時渡した文面をレコードだけで復元できる。
- **パラメータも版に残す**: 生成した文面だけを残す形と違い、後からパラメータだけを変えた版を作れる。
- **自由記述を併せて持つ**: パラメータの節が表せるのは軸に沿った傾向だけで、口調や扱う領域のような軸の外の指定は文章で書くことになる。
- **共通の節をコードが持ち、利用者に編集させない**: ADR 0035 は「答えを与えない」を禁止事項と材料の供給規律の節で実装すると決めており、二つの節を自由記述に含めると利用者のペルソナで消せる。
- **既定のペルソナの正をコードに置く**: 節の文言の正がコードにあるので、既定のパラメータと自由記述もコードに置けば合成の材料が一箇所にそろい、既定の文面の改訂がコードの差分としてレビューされる。

採らなかった案。

- **思考の向きの 1 軸を二値で持つ**: 両端の節を既存の md から切り出せ、新しく書く文言が無い。
  相手の傾向を一方向の二択でしか選べないので採らなかった。
- **論理と体験の軸**（Pacini & Epstein 1999, Journal of Personality and Social Psychology 76(6)）: 体験の端が抽象度の具体の端と振る舞いが近く、組み合わせによって二つの軸が同じ指示を重ねる。
- **分析と包括の軸**（Nisbett, Peng, Choi & Norenzayan 2001, Psychological Review 108(2)）: 抽象の手筋（変数を分解する・別領域の同型を持ち込む）と重なる。
- **時間の向きの軸**（Zimbardo & Boyd 1999, Journal of Personality and Social Psychology 77(6)）と**促進と予防の軸**（Higgins 1997, American Psychologist 52(12)）: 抽象度と独立に動くが、議論の効果についての根拠が異論の強さと発散と収束ほど直接でない。
- **軸を持たず、自由記述だけにする**: 利用者のペルソナを暖と寒のどちらで描くかを決める材料がレコードに無くなる（`docs/DESIGN.md`「話者の描き分け」は具体を暖、抽象を寒で描く）。
- **パラメータを生成の材料に留め、生成した文面だけをレコードに残す**（0032 が採らなかった案）: 後からパラメータだけを変更できなくなる。
- **節の文言をコードにだけ置き、全文を版に残さない**: 列は増えないが、文言を直すと、過去の版が渡した文面を git の履歴からしか復元できない。
- **節の文言を表にし、節ごとに版を持つ**: 復元はレコードだけで済み全文の複製も無いが、節の表とその版の採番が増える。
- **禁止事項と材料の供給規律を自由記述に含める**: 利用者のペルソナで ADR 0035 の不変条件が保証されない。
- **md を初期レコードの中身にだけ使い、以後の既定の正をレコードに置く**（0032 決定 9）: 既定の文面を直すたびに DB の行を手で直すか migration を書くことになり、コードの節を直しても既定のペルソナに反映されない。

### 深さ

- **深さをペルソナの設定に持たせない**: #64 が求めるのはペルソナの話し方の設定で、深さを利用者に選ばせる要求は出ていない。
- **0021 を supersede しない**: 0021 の決定は深さをプロバイダの設定として持つことで、深さをペルソナから切り離す決定 13 はその決定を動かさない。
  系統ごとに深さを解決する形は、ペルソナが固定二体だった時点の実装の例と読む。
- **当時の深さを版に残さない**: モデル名も版に残さずアプリ全体の設定が決めているので、深さも同じ置き場にそろえる。

採らなかった案。

- **版の列にする（Anthropic の値域）**: プロバイダ固有の値がレコードに入り、二つ目のプロバイダを足すと既存の値を読み替える手段が要る。
- **プロバイダに依らない深さの軸を足す**: 利用者がペルソナごとに深さを選べるが、0021 が退けた独自の語彙への正規化になる。
- **抽象度の段階から深さを決める**: 既定の二体はいまの深さのまま動くが、利用者が抽象度を変えると、画面に出ないまま深さも変わる。

### 既存の発話と行の作り方

- **既存の発話を消さない**: メモは発話を削除時に拒否する外部キーで指しているので、発話を削除するにはメモも削除することになる。
- **消さずに寄せる前例がある**: ADR 0037 決定 6 は、既存の問いを migration が作る既定のユーザーへ寄せた。
- **移行の時点の全文を版 1 にする**: 移行より後の文面の版へ寄せると、過去の発話がその文面で話したように記録される。
- **移行の時点より前の改訂は区別しない**: システムプロンプトの改訂が本番へ届いた日時は DB に無く、境目の発話を正しく割り当てられない。
- **migration が版 1 までを作る**: 既存の発話を寄せる UPDATE の前に参照先の行が要り、`pnpm seed` は本番で実行を拒否する。
- **AI の発話が無い DB では migration が行を作らない**: 版 1 の全文は既存の発話を寄せる先としてだけ意味を持つ。
- **版 1 より後の版を同期が作る**: 既定の正はコードにあるので、コードの合成結果から版を作れば、本番・Preview・テストで同じ関数が同じ行を作る。
- **同期をデプロイの migration の後に実行する**: 書き込みを利用者のリクエストの経路に入れない。

採らなかった案。

- **既存の発話を削除する**: 本番の対話とメモが消え、過去の分はメモからセッションを逆引きできなくなる。
- **合成した最初の既定の版へ寄せる**: 版の数は減るが、過去の発話が移行より後の文面で話したように記録される。
- **システムプロンプトの改訂ごとに版を起こし、発話の作成日時で割り当てる**: 当時の文面に近づくが、割り当てがコミット日に依るので境目の発話はずれうる。
- **既定の版をすべて migration が作る**: 既定の文面を変えるたびに合成済みの全文を SQL に写すことになり、コードの節と SQL の全文が二箇所になる。
- **利用者のリクエストの中で、既定の版が無いか古ければ作る**: デプロイの手順は増えないが、リクエストの経路に書き込みが入り、同時のリクエストで版番号が衝突するとリトライが要る。
- **`pnpm seed` が作る**: 本番では seed が実行されない。

## 覆る条件

| 起きたこと | 覆る決定 | 要るようになるもの |
|---|---|---|
| 一つのセッションに複数の人間が入る設計になる | 決定 6 | 人間の発話者を指す `messages.user_id` |
| ペルソナから別系統を派生させたくなる | 決定 3 | 親の版を指す列 |
| 既定のペルソナの改善を、既存の複製へ届けたくなる | 決定 5 | 既定の新しい版を複製へ適用する仕組み |
| 段階を変えても発話が変わらないと、実キーでの人間の判定で分かる。プロンプトで動くのは自己申告の得点で、振る舞いは一貫して変わらないという報告がある（Han ほか 2025, arXiv:2509.03730） | 決定 8 | 段階の数か軸の選び直し |
| 軸の組み合わせで節の指示がぶつかり、組み合わせごとの文言が要るようになる | 決定 9 | 組み合わせごとの節か、パラメータから文面を生成する形 |
| 利用者が、禁止事項か材料の供給規律を自分のペルソナで変えたいと求める | 決定 11 | ADR 0035 の不変条件を利用者のペルソナでどう保つかの決め直し |
| 利用者が、ペルソナごとに深さを選びたいと求める | 決定 13 | 深さの軸と、0021 が退けた独自の語彙への正規化の再検討 |
| 同期がデプロイに遅れて、既定のペルソナが古い版で動く実害が出る | 決定 16 | 同期をデプロイより先に済ませる経路 |
| 削除機能を入れる | 決定 1 | ペルソナを削除したときに、`messages` が指す版をどう扱うか（ADR 0030 の覆る条件と同じ問い） |

## この ADR が決めないこと

未決の論点は ADR にしない（規約 5）ので、次の二つは issue に残す。

| 論点 | 残す先 | 決めない理由 |
|---|---|---|
| 一つのセッションに立てるペルソナの数と発話順 | #8（発話周期の可変化（具体／抽象のバランス）） | 発話周期は #8 の対象である |
| 各軸の段階ごとの文言と、既定の二体の段階 | #64 | 文言は実キーで段階を変えて試しながら書く |

## 0032 から動いたところ

- **決定 8 が動いた**。
  0032 はパラメータの持ち方（enum と自由記述の両方）だけを決め、軸と値域を #64 に残していた。
  0043 は三つの軸と 5 段階を決め、節を軸と段階の組ごとに持つこと・合成済みの全文を版に残すこと・共通の節をコードに置くことを加えた（決定 8〜11）。
- **決定 9 が動いた**。
  0032 は、既定のペルソナの設定の正がレコードに移るとして、md を初期レコードの中身にだけ使うと決めていた。
  0043 は既定の版を同期がコードの合成から作ると決めたので、既定のペルソナの正はコードに残る（決定 12・16）。
- **0032 が #64 に残した四つの論点を決めた**。
  深さは版に持たせずアプリ全体で一つにする（決定 13）。
  既存の発話は移行の時点の全文の版へ寄せる（決定 14）。
  パラメータの軸と値域は決定 8 が持つ。
  行を作る経路は migration と同期に分ける（決定 15・16）。
- 0032 の帰結の `pnpm seed`（システムのユーザーと既定のペルソナの行を作る）は、migration と同期に置き換わった。
- 決定 1〜7 は動いていない。
  表名と列名は、規約 7 に合わせて決定時点の例へ移した。
- 0032 の理由節が参照していた 0029 と 0031 は、それぞれ改訂版の 0036 と 0037 に置き換えた。
  参照した決定は改訂版でも動いていないので、参照の意味は変わらない。
