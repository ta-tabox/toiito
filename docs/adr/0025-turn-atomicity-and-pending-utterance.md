# 0025. 一往復は成立してから書き、成立前の発話は別表で預かる

- **状態**: 採用
- **決定日**: 2026-09-02
- **関係する ADR**: 0003, 0020

## 文脈

`speakAction` は human → ai_a → ai_b を順に `addMessage` しており、トランザクションで囲っていない。
ai_b の呼び出しで例外が出ると、その回の human と ai_a は既にコミット済みなので、ai_b だけ欠けた turn が残る（#119（一往復の途中で AI 呼び出しが失敗すると、欠けた turn が残る））。
利用者が同じ文言で再送すると human の発話が二重に積まれ、以後の対話が歪んだ文脈の上で進む。

失敗経路は #120（AI 呼び出しに上限時間を持たせる）が入って出揃った。
`callPersona` が投げるのは、API キー未設定・非 2xx・`maxTokens` での打ち切り・本文が一文字も無い・上限時間の超過の 5 つである。
上限は `sendWithTimeout` が一体あたり既定 120 秒で切る。

`DESIGN.md`「残す摩擦」は、この件を三行で押さえている。
**「二体が必ず両方喋る」は残す側**、**「途中で失敗して欠けた turn が残る」と「何が起きたか分からない沈黙」は直す側**である。
左の列は削らないと定めた列なので、欠けた turn を仕様として受け入れる形は最初から取れない。

`messages` は immutable（追記のみ）で、メモのアンカーが本文のオフセットを指している。
どの形を採っても、この不変条件は動かせない。

## 決定

三つ決める。

### 1. 一往復は、二体が両方返ってから 3 行を一トランザクションで書く

AI 呼び出しはトランザクションの外に置く。
`Transcript` は `{ speaker, body }[]`（`web/src/lib/ai/prompt.ts`）なので、途中の発話は DB を経由せずメモリで足す。
握るのは書き込みのあいだだけで、外部 API の待ち時間には接続を握らない。

### 2. 送信された発話本文は、成立の前から別表（`pending_messages`）で預かる

`messages` へは入れない。
一往復が成立したとき、3 行の書き込みと**同じトランザクションで**保留行を消す。

- **保留行が在ることが、「前回の一往復が成立しなかった」という状態そのもの**になる。
  失敗の理由は持たない
- **リトライは新しい入力からでなく、保留行の本文からプロンプトを組む**
- 保留は 1 セッションにつき 1 件（`session_id` に unique）。
  保留が在るあいだも発話フォームは出し、新しく発話すれば保留は差し替わる（これが破棄の口を兼ねる）
- この表は `messages` と違って可変である。
  immutable の不変条件は `messages` にだけ掛かる
- `user_id` は持たない（0020 決定 1。所有者は `sessions` から辿る）

### 3. 発話本文に 4000 字の上限を置く

textarea の `maxLength` と lib 側の検査の両方で表明する。

## 理由

### 一往復をまとめる形として、AI 呼び出しごと囲む案を採らなかった

囲む案（`$transaction` の中で `callPersona` を待つ）を落とした条件は三つある。

- 本番の `DATABASE_URL` は Neon のプーラー経由（`DEPLOY.md`）。
  一体 120 秒 × 2 の待ちのあいだ、サーバー側の接続を握り続けることになる
- Prisma のインタラクティブトランザクションは既定 5 秒（`timeout`）で打ち切る。
  240 秒超へ引き上げる設定を書くことになる
- `tx` を `db.ts` の外へ出すか、AI 呼び出しを `db.ts` の中へ入れるかのどちらかになる。
  前者は 0003 の禁止則「Prisma を repo 層の外へ出さない」に当たり、後者は永続化層が外部 API を叩く形になる

呼び出しを先に済ませる形なら、三つのどれも起きない。
**加えて、いまより保持するものが減る**。
現状は ai_a を書いた直後に `listMessages` を読み直して ai_b へ渡しているので、ai_b の待ちのあいだ ai_a の本文が二部（変数と、DB から読み直した複製）メモリに居る。
transcript をメモリで足せば同じ文字列を指すので複製が消え、DB の往復も 1 回減る。

### 打ち消す行を足す案を採らなかった

`messages` に列を足して既存行を落とす形は、「追記のみ・編集しない」が破れる（`db.ts` に初めて update が生える）。
打ち消しを別の行として足す形は immutable を保てるが、`listMessages` が畳み込みを持ち、UI と transcript の両方がそれを通ることになる。

どちらにも共通して、**打ち消された発話にメモが付いていた場合の扱いが新しい問いとして開く**。
実際に起きるのは ai_a が残って ai_b が落ちた形なので、利用者が ai_a にメモを付けてから失敗に気づく順序はありうる。

そして #64（二体のペルソナをセッション単位で設定できるようにする）と一番噛む。
列を足す形は #64 が `speaker` を作り直すのと同じ表を同時に触り、tombstone 行の形は「発話者のいない行」を要求するので `persona_id` を NOT NULL で立てられなくなる。

### 欠けた turn を明示的に扱う案を採らなかった

`DESIGN.md` の**残す側**「二体が必ず両方喋る」を、仕様の側から壊す。
加えて欠けた turn が以後の transcript に入り続けるので、#119 が症状として挙げた「歪んだ文脈の上で進む」を飲む選択になる。
採るなら `DESIGN.md` の表を先に書き換える必要があり、その判断はしていない。

### 再送を弾く案は、不要になったので採らなかった

human が `messages` へ入らなくなるので、二重投入の口がそもそも閉じる。
弾く仕組みは、欠けた turn を残す案（打ち消し・明示）を採った場合にだけ要る補助だった。

### 保留の置き場を、ブラウザでなく DB にした

消える主体がサーバーなので、保留はサーバー側に置かないと目的を果たさない。
ブラウザ側（フォームの再描画・`sessionStorage`）に置くと、タブを閉じる・別の端末から開くで消える。
**サーバーの都合で消えた入力を利用者に打ち直させない**というのがこの決定の目的なので、消える理由の側と別の場所に置く必要がある。

### 保留の置き場を、`sessions` の nullable な列でなく別表にした

列を足す形の方が変更は小さい。
落とした条件は、`listSessionsWithKeywords` が `select` を書かない `findMany` で、結果を `...session` のまま `SessionWithKeywords` へ広げていることである。
`sessions` に本文の列を足すと、**セッション切り替え口を描くたびに、並ぶセッションの数だけ最大 4000 字の本文を引く**。
しかもドメイン型 `Session` に載るので UI まで届く。
別表なら、保留を読むのはリトライの口を描くときだけになる。

### 上限を 4000 字にした

`DESIGN.md`「残す摩擦」の線引きは注意の向き先である。
**書いている途中で止まる上限は、道具そのものへ注意を奪うので妨害の側に落ちる。**
したがって上限は摩擦として使わず、通常の使用では当たらない高さに置く（実測では S0 の人間発話が最大 180 字。4000 字は全角 34 字換算で約 118 行）。

止めたいのは、暴走した貼り付けと、いま効いている唯一の境界が Next の `serverActions.bodySizeLimit` の既定 1MB だけであることの方である。
`speak-form.tsx` の textarea に `maxLength` は無く、`speakAction` にも `addMessage` にも長さの検査は無い。

## 帰結

- **成立しなかった一往復では ai_a の応答を捨てる**（呼び出し 1 回ぶん、1 分前後）。
  再生成すればよいものとして許容した。
  捨てないのは人間が入力した本文だけである
- **`messages` に turn の同一性を持たせる必要が無くなった**。
  「欠けた turn を名指しする」「同じ turn の再送を弾く」のどちらも要らないため。
  #64 が `speaker` を作り直すのと交差しない
- **一往復を回す手順は lib 層へ降りる**。
  Server Action は単体テストから直に呼べないので、#119 の完了条件（ai_b の失敗時の `messages` を検証するテスト）はいまの形では書けない（`HARNESS.md`「テスト可能性の設計制約」1）
- **その lib 関数は、AI の失敗を例外でなく結果値で返す**。
  `actions.ts` に判断を置かない規約に加えて、Server Action が投げると Next の既定のエラー画面へ落ちて保留の状態を描けなくなるため（`web/src/app/` に `error.tsx` は無い）
- **画面に、応答が得られなかったことと「もう一度試す」の口が要る**。
  `DESIGN.md`「残す摩擦」の直す側「何が起きたか分からない沈黙」がここで埋まる
- 失敗の 5 経路は画面では区別しない。
  区別が要る側（運用）は `logCall` の 1 行が持つ
- **3 行の書き込みが、関数の実行時間の天井に一番近い位置へ寄る**。
  一体 120 秒 × 2 と立ち上がりの約 10 秒で、Vercel Hobby の 300 秒に対して余裕は約 50 秒になる。
  書き込み自体はミリ秒なので当面は問題にならないが、`timeoutMs` を上げるときはここが先に折れる
- `pending_messages` は追加の表なので migration が要る。
  本番は main への push を起点に流れる（0008）

## 覆る条件

- **AI 応答のストリーミング（#9（ストリーミングの spike）/ #10（ストリーミングの実装））が入ったら、決定 1 と 2 をまとめて決め直す。**
  「完成した本文が揃ってから書く」という前提そのものが動くため
- **上限 4000 字が通常の使用で当たるようになったら上げる。**
  当たった時点で、それは事故の防止でなく妨害の側へ回ったということである
- **保留が 1 セッション 1 件で足りなくなったら**（未成立の発話を複数並べたくなったら）決定 2 を組み直す
- **`messages` へ turn の同一性を持たせる別の理由が出たら**、打ち消す案と明示する案が再び選択肢に戻る。
  同一性はこの決定が回避した費用であって、否定した概念ではない
- **ai_a を捨てるのが高くつくようになったら**（一体あたりの単価か所要時間が大きく動いたら）決定 1 を、成立しなかった呼び出しの結果を残す形で決め直す
