記録日: 2026-09-02。
状態: **見送り（設計は棚に置く）**。
出所は #9（ストリーミング化 spike（設計を書く））で、実装の受け皿は #10（ストリーミング実装（SSE））。
本体 MVP には含まれておらず、常用後の判断事項として開いていた。

この文書は二つのことを書く。

## この拡張が立つ側 — 摩擦表への当て

`DESIGN.md`「残す摩擦」が線引きの原則を一行で持っている。

> 問いへ向かう注意を止めるものは残し、道具そのものへ注意を奪うものは直す。

同じ節の表は、左列（残す・仕様）の先頭に「AI の応答待ち 15〜27 秒」を置き、右列（直す・妨害）の先頭に「何が起きたか分からない沈黙」を置いている。
待ちそのものは仕様で、待ちが不透明であることだけが欠陥だという線引きである。

**ストリーミングは待ち時間を消さない。**
総所要は変わらないか、SSE の枠と client 側の描画のぶんだけ増える。
変わるのは見せ方だけなので、この拡張がどちらの列に触るのかは、見せ方の変化がどちらの効果を持つかで決まる。

右列（沈黙の不透明さ）は**既に別の手で解けている**。
`SpeakForm` の送信ボタンは待ちの間に「二体が応答中」へ変わり、三つの点が位相をずらして明滅する（#2（発話フォームのローディング表示）で入った）。
止まっているのではないことは、これで見えている。

残るのは左列である。
本文が流れ始めれば、待ちは「待ち」でなく「読み」になる。
それは待ちの体感を消すということで、左列に置いた摩擦を削ることに当たる。
`DESIGN.md` は左列について「削る提案が来たら、それは改善ではなく効果の除去である」と書いている。

**よってこの拡張は、既定では見送る側に立つ。**
入れるなら、左列の一行を削るという判断を先にしなければならない。

## 結論 — 見送りを勧める

四つある。

**一つ。技術的な必要が無い。**
実行環境の上限は 300 秒（Vercel Hobby / fluid compute の既定。`DEPLOY.md`）で、一往復の実測は 15〜27 秒である。
上限の 5〜9% で、切れる心配は無い。
一体あたりの上限も 120 秒が入った（#120（AI 呼び出しに上限時間を持たせる））ので、不透明な失敗の側も塞がっている。

**二つ。当初の実施理由のうち一つ目が、常用後の実測に支持されていない。**
旧プランが実施を確定させた理由は「transcript は全量渡しの設計なので対話が育つほど同期待ちは伸びる——常用が進むほど確実に重くなる」だった（`git show 9a94b72^:PLAN-rationale.md` の S5 節）。
これは**推論であって計測ではない**。
`ROADMAP.md`「順序の理由」が #7（MVP 到達判定・常用開始）を先へ回したのも同じ読みで、常用を先に始めれば必要性が実測で裏付く（あるいは裏付かない）という判断だった。

裏付いていない。
`DESIGN.md` は常用開始（2026-08-29）と MVP 到達判定（2026-08-30）の後、2026-08-31 に起こされ、そこで待ちを左列へ置いた。
9 月 1 日の改稿では表そのものが触られている（入力欄の行が指す issue を替えた）のに、この行は残っている。
常用中の違和感は #109（スマホの入力）・#112（発話が途中で切れる）・#113（呼称と effort）・#147（スマホで発話を選んでもメモが作れない）・#160（メモ入力欄でのズーム）・#161（選択箇所から離れた入力欄）として issue になっているのに、**待ちについては一件も立っていない**。
観測器は働いていて、そこに引っかかっていない。

**三つ。二つ目の実施理由（ポートフォリオとしての見せ場）は残るが、設計原理を曲げる理由にはならない。**
`ROADMAP.md` は同じ理由について「正当だが、常用開始を遅らせる理由にはならない」と既に一度線を引いている。
延長すると、見せ場は設計判断を曲げる理由にもならない。
見せ場が要るなら、SSE を実装したことより「反快適性という原理から、技術的に可能な改善を見送った」という判断のほうが読ませる材料になる。
その判断はこの一枚と `docs/adr/` が既に担っている。

**四つ。仮に入れても、利得が出る保証が無い。**
利得が出るのは TTFT（発話本文の最初の一文字が出るまでの時間）が短いときだけである。
このアプリは `claude-sonnet-5` を叩いており、`thinking` を指定していない（`web/src/lib/ai/anthropic.ts`）。
Sonnet 5 は `thinking` を省くと adaptive で走るので、思考は常に有効である。
そして `thinking.display` の既定は `"omitted"` で、思考ブロックは中身が空のまま流れる。

思考の深さは系統で分かれるが、有無は分かれない。
`output_config.effort` が付くのは `settings.effort` が truthy のときだけで、`DEFAULT_EFFORT` は `concrete: undefined` なので、既定では抽象側（ai_b）にだけ `medium` が付く。
具体側（ai_a）は指定を持たず API の既定（high）で走るので、**深いほうが指定の無い側**になる。
どちらも思考は走るから、この非対称は沈黙の長さを変えるだけで、沈黙の有無は変えない。
つまり**思考が終わるまで、ストリーミングにしても画面は沈黙したままになる**。
一往復の 15〜27 秒のうち何割が思考なのかは測っていないので、沈黙がどれだけ縮むかは分からない。

### この判断の限界

「待たされたか」は L5（人間の官能）でしか測れず、Claude 側は間接証拠しか持っていない。
上の二つ目は「待ちについて issue が立っていない」という不在からの推論であって、人間が待ちを苦痛と感じていないことの直接の確認ではない。

**人間が「待つのが苦痛だった」と言うなら、この結論は覆る。**
その場合に読むのが後半の設計で、spike をもう一度回さずに済むよう書き切ってある。

推論で開き直さないよう、測れる形で置く。
一つでも満たしたらこの判断を破棄し、#10 を開き直す。

2. **`input_tokens` の増加に対して `duration_ms` が伸びている**。
   当初の実施理由「対話が育つほど重くなる」はこの相関そのもので、同じログの二つの欄で検算できる。
   伸びていなければ、幅を作っているのは出力の長さであって文脈の量ではない（`DEPLOY.md`「引き受けている非対称」は後者と読んでいる）
3. **人間が待ちを苦痛と言った**。
   このとき `DESIGN.md`「残す摩擦」の左列から「AI の応答待ち 15〜27 秒」を落とす判断が先に要る。
   表を残したままストリーミングを入れると、正が二つに割れる

**開き直すときは、実装の前に TTFT を一度測る。**
`stream: true` で一回叩き、`content_block_delta` のうち `delta.type` が `text_delta` である最初の一件までの経過を出すだけでよい。

`effort` を下げれば TTFT は縮むが、それは応答の質を落とす取引なので別の判断になる。

## SSE のイベント設計

置き場は `web/src/app/api/speak/route.ts`（POST）。
リクエストは `{ questionId, sessionId, body }` の JSON、レスポンスは `text/event-stream`。

| event | data | いつ |
|---|---|---|
| `human` | `{ id }` | 人間の発話を保存した直後 |
| `start` | `{ speaker }` | 一体の呼び出しを始めた |
| `delta` | `{ speaker, text }` | 本文の断片が届いた |
| `commit` | `{ speaker, id }` | 一体分を保存し終えた |
| `error` | `{ speaker, message }` | 一体分が失敗した |
| `done` | `{}` | 一往復を終えた |

順序の契約は `human` → (`start` ai_a → `delta`* → `commit` ai_a) → (`start` ai_b → `delta`* → `commit` ai_b) → `done`。
ai_b は ai_a への応答であることに意味がある（`ARCHITECTURE.md`「二体 AI のオーケストレーション」）ので、ai_a の `commit` より前に ai_b の `start` は出ない。
**並列化しない。**

`speaker` を全イベントに載せるのは、受け手が「いま誰の枠へ書くか」を直前のイベントの記憶でなくイベント自身から決められるようにするため。

`delta` に累積本文でなく断片を載せるのは、累積を毎回送ると転送量が発話長の二乗になるため。

`commit` が `id` を返すのは、メモのアンカーが `message_id` を要るため（`web/src/app/actions.ts` の `createMemoAction`）。
逐次描画の最中の本文にはメモを付けられない。
付ける先の行がまだ無いからで、これは仕様として受け入れる。

`error` を流したらストリームを閉じる。
#119（一往復の途中で AI 呼び出しが失敗すると、欠けた turn が残る）はストリーミングでも解けず、むしろ「画面に出ていた本文が、再読み込みで消える」という新しい形の欠けが加わる。

## ストリーミング版のシグネチャを、どの層へ足すか

三層ある（ADR-0021（AI のスコープでモジュールを切り直す））。
`AiProvider#send`（`provider.ts`・抽象）、`AnthropicProvider#send`（`anthropic.ts`・HTTP の作法）、`callPersona`（`index.ts`・規約）。

**置き換えでなく並置する。**
`send` を反復子へ変えると、確定した本文しか要らない呼び出し（将来の要約・タイトル生成など）まで反復を書くことになる。

- `AiProvider#sendStream(system, userContent, signal)` を abstract で足す
- `AnthropicProvider#sendStream` は `stream: true` で叩き、`content_block_delta` のうち `delta.type` が `text_delta` のものだけを拾って yield する。
  `thinking_delta` は捨てる（画面に出さない）。
  `input_tokens` は `message_start` の `message.usage`、`stop_reason` と `output_tokens` は `message_delta` が運ぶ
- 戻り値の型は `AsyncIterable<string>` **でなく** `AsyncGenerator<string, ProviderResponse>` にする。
  #9 の本文は前者で書いているが、それだと `stop_reason` を返す口が無くなる。
  打ち切りの判定を捨てられないのは #112（AI の発話が途中で切れる・空で保存される）が実害として出たからで、`stop_reason` を見ない経路を新設すると同じ穴を開け直すことになる
- `callPersonaStream(call, question, transcript): AsyncGenerator<string, string>` を `index.ts` へ足す。
  yield が断片、return が確定本文

規約層が持つもの（フェイク・記録・上限・打ち切りと空本文の拒否）は同じだが、**掛かる位置が変わる**。

- **上限**: 今は `sendWithTimeout` が `await provider.send(...)` を包んで `timeout.aborted` を見ている。
  ストリームでは例外が反復の途中で出るので、try/catch を反復の側へ移す。
  `AbortSignal.timeout` は本文の読み出し中も効き続けるので、一体あたり 120 秒という上限の意味は変わらない
- **打ち切りと空本文の拒否**: 断片は既に画面へ出た後で判明する。
  **拒んでも画面からは消せない。**
  確定を拒んだときは `error` で「この発話は保存されない」と明示する。
  同期版との最大の差はここにある
- **記録**: `duration_ms` に加えて TTFT を足す。
  入れた後も利得が出続けているかを測れる

フェイクは `fakeStream(id, transcript): AsyncGenerator<string, string>` を `fake.ts` へ足し、`fakeResponse` の文字列を三つ程度へ割って yield する。
割る位置は文字数でなく決め打ちにする（決定的であることがフェイクの存在理由）。
**遅延は入れない。**
E2E を遅くする理由が無く、逐次に届くことは順序で検証できる。

## Server Action からの移行手順

不変条件を先に置く。
逐次性を並列化しない。
`messages` は immutable のまま。
最後にサーバー描画の確定版へ戻る。

1. `api/speak/route.ts` を新設する。
   中身は `speakAction` の手順そのままで、書き出しだけ SSE にする。
   **`speakAction` は残す**（両方が動く状態を作る）
2. `SpeakForm` を `action` でなく `onSubmit` で fetch する形へ変える。
   `useFormStatus` は親フォームの Server Action を見るものなので使えなくなり、pending は自前の state になる
3. 逐次描画の受け皿を決める。
   既存の `messages.map` はサーバー側で描いており、ストリーミング中の発話は DB にまだ無い。
   **サーバー描画の列の下へ、client 側の「生成中の枠」を継ぎ足す**形にする。
   列そのものを client component へ移さない——メモの配線が `MessageBody` を通じて全発話に掛かっており、client 化すると memos の受け渡しごと動く
4. `done` を受けたら `router.refresh()` を呼び、サーバー描画の列を確定版へ差し替える。
   client 側の仮枠を捨てるのは refresh の完了後にする（前後で本文が一瞬二重になるのを避ける）
5. 実機で一往復を通し、体感が改善したかを人間が判定する
6. 肯定なら `speakAction` を消す。
   否定なら route ごと落とす。
   フォームを元へ戻せば済む形を 4 まで保っておく理由がこれ

## DB 書き込み — 確定時に一括

途中経過を保存しない。
`messages` は immutable（`ARCHITECTURE.md`）なので、空の行を先に作って後から埋める形は採らない。

保存の順序は同期版と同じで、人間発話 → ai_a 確定 → ai_b 確定。
ai_a の行は ai_b の呼び出しより前に要る（`listMessages` で transcript を組み直すため）ので、ここは動かない。

途中で失敗したときに残るのは「人間発話だけ」か「人間 + ai_a」で、これも同期版と同じである（#119 の対象）。

## 楽観的更新の範囲

**人間の発話のみ。**
送信した瞬間に自分の言葉が列へ出るのは道具の応答であって、AI の応答ではない。

AI 側は楽観的更新をしない。
`delta` が来て初めて枠を出す。
「これから喋る」を先に見せると、失敗したときに画面から枠を消すことになり、出したものを引っ込める挙動が増える。

## #6 のシナリオ 1 の改修

`web/e2e/dialogue.spec.ts` は `toHaveCount(2)` と `nth(0)` / `nth(1)` で確定後の並びを見ている。
逐次描画では途中で 1 件しか無い瞬間があるので、そのままだと待ち方に依存する。

- `toHaveCount(2)` は残す。
  Playwright の expect はリトライするので、最終状態の検証としては正しいまま
- `router.refresh()` が効いていることを、リロードせずに本文が残ることで見る。
  ここが落ちると「画面には出たが保存されていない」を見逃す
- 逐次性そのものを E2E で見るのは**やめる**。
  ai_a の枠が出た時点で ai_b がまだ無いことを確かめる形は書けるが、フェイクに遅延を入れない以上は競り合いになる。
  逐次性の正はサーバー側の順序にあり、それは lib のテストで見るのが正しい

## #8（発話周期の可変化）との競合と、着手順序

#8 の B 案（オーケストレーション改修）は発話順を可変にし、片方が黙れるようにする。
上のイベント設計は「ai_a → ai_b が必ず両方出る」を順序の契約として持っているので、B が入ると契約が変わる。

**結論は #8 が先。**
#8 が決めるのは誰が何回喋るかで、#10 が決めるのはそれをどう流すかなので、構造が動くうちに流し方を固めるとイベントの契約から作り直すことになる。

ただし #8 は A 案（ペルソナ文言の調整）から始める設計になっており、A で足りれば構造は動かない。
その場合この競合は消える。

**#119（欠けた turn）も先。**
ストリーミングは「画面に出ていた本文が保存されずに消える」という欠け方を足すので、欠けた turn の扱いが決まっていない状態で入れると、決まっていない状態が二種類になる。

着手順序は #119 → #8 → #10。

## 開いている問い

- ストリーミングは待ちを「読み」へ変える。
  それは待ちを消すことなのか、待ちの質を変えることなのか。
  この文書は前者と読んで見送りを勧めたが、実機で流れる本文を見るまで確かめようがない
- 流れてくる文を追うことは、読み終えてから次を読むことより急ぐことに似ている。
  スローダウンという原理と衝突しないかは、使うまで分からない
- 思考の時間は流しても沈黙のままである。
  `effort` を下げれば沈黙は縮むが応答は浅くなるので、ストリーミングを入れるという判断は `effort` を下げるという判断と繋がっている。
  片方だけを動かすと、もう片方が黙って効く
