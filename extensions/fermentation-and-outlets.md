# 拡張構想: 発酵（培地）と出口（確定・分割）

記録日: 2026-07-19。状態: **構想（未着手）**。
出所は fermentary で実際に行った蒸留セッション一回分の観測——18日寝かせた問いを
人間と AI で深め、常設化・概念2本の切り出し・派生問い2本の新設まで到達した実例。
本体 MVP（PLAN.md S1〜S4）には含めない。着手判断は MVP 常用後。

同枠の先行構想: `graph-view.md`（本文書の末尾で接続する）。

## 出発点: toiito に無い工程

実地の一回を分解すると、問いが深まるまでに7段あった。

| # | 工程 | toiito |
|---|------|--------|
| 1 | 捕捉（問いを投げる） | ある |
| 2 | **発酵**（材料を自動で寄せる） | **無い** |
| 3 | **原型の照合** | 2026-07-19 に部分実装（`current_form`） |
| 4 | 蒸留（対話） | ある（本体） |
| 5 | **出口の確定** | 2026-07-19 に部分実装（status 6値） |
| 6 | **昇格**（別の器へ書き出す） | **無い** |
| 7 | 逆引き・堆積 | MVP で実装中（メモ） |

そして問いを実際に動かしたのは **2 と 5** だった。1・4・7 は土台であって
中心ではない——材料が無ければ議論は始まらず、確定しなければ形にならない。

これは MVP のスコープへの批判ではない。4 と 7 が無ければ 2 も 5 も乗る場所がない。
順序は正しい。ただし **toiito の中心的価値は対話そのものより、その前後にある**
可能性が高い、というのが実地からの見立て。

## D. 培地（culture）— message でも memo でもない第三の型

VISION「リンキングを支える」の実体。問いに付随する**材料**であって、
誰かの発話ではない。

実地で機能した培地の書式がそのまま仕様になる:

```
培地（付与日）
  内部交差   — 自分の過去の問い / メモ。「なぜ関係するか」を一行添える
  外部       — 調査。境界つき・最大5件・出典 URL 必須・対立を必ず含む
  異種同型の芽 — 別領域と同じ形に見えるものを候補として。断定しない
```

**スキーマ案**（memo_links と同じく先にテーブルだけ切る手もある）:

```
cultures
  id, question_id, kind(internal/external/isomorph),
  body, source_url, created_at, created_by(auto/human)
```

設計上の要点:

- **付与は非同期**。投入した問いに対し、後から材料が付く（人間が見ていない間に
  発酵が進む、が中心メタファーの実装）。付与時に `status` を
  `composting → fermented` へ進める＝状態遷移条件が初めて定義される
- **外部材料は上限つき**。VISION の最重要制約は「知識を出さない」ではなく
  「一方向に閉じた材料を出さない」（ARCHITECTURE の該当節）。件数上限・対立の
  同梱・出典必須が、その検査可能な形
- **培地は破棄しない**。問いが変形して材料が的外れになっても消さない——
  実地では、誤った語のために採られた培地が、正しい語で立て直した別の問いの
  材料としてそのまま生きた

## E. 問いの分割（question_links）

実地では1つの問いが3つになった。親子・派生を辺として持つ。

```
question_links
  id, from_question_id, to_question_id, kind(split/derives/tension), created_at
```

**規律（実地で確定したもの）**: 分割は出口ではない。「分割したので元は役割を
終えた」を認めると、確定されない問いがキューに残る抜け道になる。
**分割元は必ず6状態のどれかへ確定させ**、切り出した問いは `composting` で
新規に立つ。UI もこの順序を強制する（分割フォームは元の status 選択を必須にする）。

## F. 昇格（問いの外へ出す）

実地では、問いから概念2本が結晶して別の器（fermentary の notes）へ出た。
toiito 内で完結させるなら「結晶ノート」の型が要る。ただし fermentary との
二重管理になるため、**VISION の開いた問い「fermentary questions.md との関係」が
先に決着する必要がある**。現時点の当たり:

- toiito = 対話と発酵の器（過程）
- fermentary = 確定した概念の住処（結果）
- `promoted` の実体は「fermentary へ書き出した」ことの記録でよく、
  toiito 側に本文を持たない（膜の一行判定に従う）

この線なら二重管理が起きない。ただし toiito 単体で完結して使いたいなら別の解が
要る——**未決**。

## graph-view.md への接続（開いた問いへの答え）

`graph-view.md`「開いている問い」に**メッセージをノードにすると長文で意味を
失う。要約ラベル？ それともメモだけをノードに？** とある。

実地の一回をグラフにすると答えが出る。ノードにすべきはメッセージでもメモでも
なく、**問い・培地・出口**だった:

```
    [問い（原型）]
        ├── 培地（内部交差2・外部4・同型の芽1）
        ├── 派生問い A（判定基準）      ← split
        ├── 派生問い B（語りと癒し）    ← split
        ├── 結晶した概念 A             ← promoted
        └── 結晶した概念 B             ← promoted
```

7ノード。読める。メッセージは辺の文脈に潜らせ、ノードにはしない
（長文で意味を失う問題は「ノードにしない」で解ける）。
Phase 3 のメタグラフでキーワードがハブになる構想は生きるが、**培地の外部材料も
同じくハブになる**——同じ研究が二つの問いに引かれていたら、そこが接続点。
